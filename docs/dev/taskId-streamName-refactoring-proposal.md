# TaskId vs StreamName Refactoring Proposal

## Current State Analysis

After analyzing the codebase, I've identified several confusing patterns in how identifiers are used throughout the progress view and agent execution logic:

### Current Identifiers and Their Usage

1. **`taskId`** (UUID-based, unique)
   - Generated by `AgentHistoryManager.addToHistory()` using `randomUUID()`
   - Used for history tracking and linking executions to history entries
   - Passed from `executeCommand.ts` → `executeAgent.ts` → `ProgressViewProvider.setTaskState()`
   - Stored in `ProgressStateManager._taskIds` map: `Map<string, string>` (streamId → taskId)

2. **`streamId`/`fullStreamId`** (deterministic, human-readable)
   - Generated by `getStreamId()` function: `${agentName}@${model}: ${inputFileName}`
   - Used as the primary key for UI tabs, logging, and state management
   - Also called `channelId` in `BaseAgent.getTaskId()` (confusing naming!)
   - Used for deduplication of execution jobs (prevents running same task twice)

3. **`streamName`** (in logger contexts)
   - Used by channel loggers for output channel identification
   - Same value as `streamId` but different semantic context

### Problems Identified

1. **Naming Confusion**:
   - `BaseAgent.getTaskId()` actually returns a `streamId`
   - `taskId` and `streamId` are used interchangeably in some contexts
   - `streamName` vs `streamId` semantic overlap

2. **Inconsistent Usage**:
   - Some functions expect `taskId` (UUID) but receive `streamId` (human-readable)
   - Progress view uses `streamId` as primary key but stores separate `taskId` mapping
   - Agent execution logic mixes both concepts

3. **Poor Semantic Clarity**:
   - Not clear which identifier serves which purpose
   - Difficult to understand the relationship between the two

## Proposed Solution

### New Naming Convention

| Current Term              | New Term      | Purpose                                           | Format                       | Example                                  |
| ------------------------- | ------------- | ------------------------------------------------- | ---------------------------- | ---------------------------------------- |
| `taskId` (UUID)           | `executionId` | Unique execution identifier for history tracking  | UUID                         | `"a1b2c3d4-e5f6-7890-abcd-ef1234567890"` |
| `streamId`/`fullStreamId` | `streamTabId` | UI tab identifier and execution deduplication key | `${agent}@${model}: ${file}` | `"polish@sonnet37: paper.tex"`           |
| `streamName`              | `streamTabId` | Same as above (eliminate redundancy)              | Same as above                | Same as above                            |

### Refactoring Plan

#### Phase 1: Rename Core Functions and Variables

1. **In `BaseAgent.ts`**:

   ```typescript
   // OLD
   protected getTaskId(): string {
     // returns streamId format
   }

   // NEW
   protected getStreamTabId(): string {
     // same implementation, clearer name
   }
   ```

2. **In `ProgressViewProvider.ts`**:

   ```typescript
   // OLD
   public setTaskState(streamId: string, taskState: TaskState, taskId?: string): void
   public getTaskId(streamId: string): string | undefined

   // NEW
   public setTaskState(streamTabId: string, taskState: TaskState, executionId?: string): void
   public getExecutionId(streamTabId: string): string | undefined
   ```

3. **In `ProgressStateManager.ts`**:

   ```typescript
   // OLD
   private _taskIds: Map<string, string> = new Map();

   // NEW
   private _executionIds: Map<string, string> = new Map(); // streamTabId → executionId
   ```

#### Phase 2: Update Function Signatures

1. **In `executeAgent.ts`**:

   ```typescript
   // OLD
   export async function executeAgent(
     agentConfig: Partial<AgentConfig>,
     context: vscode.ExtensionContext,
     taskId?: string,
   ): Promise<void>;

   // NEW
   export async function executeAgent(
     agentConfig: Partial<AgentConfig>,
     context: vscode.ExtensionContext,
     executionId?: string,
   ): Promise<void>;
   ```

2. **In progress event emissions**:

   ```typescript
   // OLD
   emitProgress('setTaskState', {
     streamId: fullStreamId,
     taskId,
     taskState: agentConfigToTaskState(config),
   });

   // NEW
   emitProgress('setTaskState', {
     streamTabId: streamTabId,
     executionId,
     taskState: agentConfigToTaskState(config),
   });
   ```

#### Phase 3: Update Storage Keys and Documentation

1. **In `stateManager.ts`**:

   ```typescript
   // OLD
   TASK_IDS = 'texra.taskIds',

   // NEW
   EXECUTION_IDS = 'texra.executionIds',
   ```

2. **Add comprehensive documentation**:

   ```typescript
   /**
    * Stream Tab ID: Human-readable identifier used for UI tabs and execution deduplication
    * Format: "${agentName}@${modelName}: ${inputFileName}"
    * Example: "polish@sonnet37: paper.tex"
    *
    * Purpose:
    * - Primary key for UI stream tabs
    * - Prevents duplicate executions of the same task
    * - Used for logging channel identification
    */
   type StreamTabId = string;

   /**
    * Execution ID: Unique UUID for each execution instance
    * Format: UUID v4
    * Example: "a1b2c3d4-e5f6-7890-abcd-ef1234567890"
    *
    * Purpose:
    * - Links executions to history entries
    * - Enables tracking of multiple executions of the same task
    * - Used for audit and debugging purposes
    */
   type ExecutionId = string;
   ```

### Migration Strategy

#### Step 1: Add Type Aliases (Non-breaking)

```typescript
// Add to a new types file
export type StreamTabId = string;
export type ExecutionId = string;

// Temporary backwards compatibility
export type TaskId = ExecutionId; // @deprecated - use ExecutionId
```

#### Step 2: Gradual Refactoring

1. Update internal implementations while maintaining old public APIs
2. Add deprecation warnings to old methods
3. Update all internal calls to use new naming
4. Update tests and documentation

#### Step 3: Public API Migration

1. Release new APIs alongside old ones
2. Provide migration guide for any external consumers
3. Remove deprecated APIs in next major version

### Benefits of This Approach

1. **Clear Semantic Distinction**:
   - `executionId`: Unique per execution, used for history/audit
   - `streamTabId`: Deterministic per task configuration, used for UI/deduplication

2. **Improved Developer Experience**:
   - Function names clearly indicate what type of ID they expect
   - No more confusion about which ID serves which purpose
   - Better IntelliSense and type safety

3. **Maintainable Codebase**:
   - Consistent naming throughout the codebase
   - Easier to onboard new developers
   - Reduced cognitive load when reading code

4. **Future-Proof Design**:
   - Clear separation of concerns
   - Easy to extend with additional identifier types if needed
   - Better support for features like execution comparison, retry logic, etc.

### Implementation Timeline

- **Week 1**: Phase 1 - Core function renaming and type definitions
- **Week 2**: Phase 2 - Update function signatures and event emissions
- **Week 3**: Phase 3 - Storage keys, documentation, and testing
- **Week 4**: Final testing, migration guide, and cleanup

This proposal provides a clear path forward to eliminate the confusion between `taskId` and `streamId` while maintaining backwards compatibility and improving code clarity.
