### Retry-owner gap (owner-selector vs retry-count decided in different places)

- **EP-1 (medium) — `texra.model.retry.maxAttempts` is inert for Anthropic/OpenAI/OpenAIResponse.** Mechanism: `isAutoRetryManagedByProvider→true` (`modelHandlerAnthropic.ts:277-279`, `modelHandlerOpenAI.ts:223-225`, `modelHandlerOpenAIResponse.ts:1076-1078`) makes `ModelInvocationNode.ts:83-88` skip the flow retry that is the _only_ reader of `maxAttempts` (`RetryState.ts:24-32`), and the constructors never pass `maxRetries` (`grep maxRetries` in modelHandlers = 0) → the SDK default of 2 (`openai@6.45.0/client.d.ts:182`, `@anthropic-ai/sdk@0.110.0/client.d.ts:198`) is the sole owner. `package.json:879` literally promises "Set to 0 for no automatic retries" — false for the three most-used providers. Google (base default `false`, `ModelHandler.ts:698-700`) and OpenRouter 429/408 still honor it. **Net-neutral fix:** correct the `package.json`/`coreSettings.ts` description to say provider-managed, and align the `RetryState.ts:25` fallback (`1`) to the canonical `coreSettings.ts:89` default (`0`). **Rejected trap:** do NOT set `maxRetries:0` at the constructors while leaving the owner-selector `→true` — that yields zero retries from _both_ owners (no transient resilience). Owner-selector and count must be decided together. (Sub-path caveat: OpenAIResponse background transients _do_ honor `maxAttempts` via `requiresFlowAutoRetry` at `ModelInvocationNode.ts:76`.)

- **EP-2 (medium) — OpenRouter 5XX delegated to the SDK with no cap (~1h backoff inside one visible attempt).** Mechanism: `modelHandlerOpenRouterNative.ts:130-138` builds `new OpenRouter` with no `retryConfig`, so the SDK default `maxElapsedTime:3600000` governs (`@openrouter/sdk@0.13.31 chatSend.js:54`, `retries.js:7-10`), and `:140-152` deliberately defers `statusCode>=500` to it. A transient 5XX reads as a hang. **Fix (+1..+3 LoC):** add `retryConfig:{strategy:'none'}` (or a bounded backoff) and let the flow own 5XX with in-band, visible attempts. **Rejected trap:** do NOT merge the OpenRouter handler into OpenAI's to "share" retry config — the split is a per-provider SDK fact.

- **EP-4 (low, new) — desktop's retry approval-handler override is inert dead code + a misleading comment.** Because `requestRetry` short-circuits to cancel (a _downstream consequence of the EP-R2 decline-the-panel design_), the retry `ApprovalRequestHandler` desktop constructs (`desktopAgentExecution.ts:282-297` = `()=>undefined`) is never shown/resolved/replayed, and its pending-guard contribution (`progressBackendUiConfig.ts:176`) is permanently false; the builder comment `:37-40` misattributes the cancel to this transport. Real callers are extension-only (`extensionHostInteractions.ts:140/220/272`, `ProgressViewProvider.ts:479`). **Fix (~0 LoC):** give it an accurate "documented no-op (cancel handled in `requestRetry`)" comment, or wire real transport when desktop adopts the panel. **Rejected trap:** do NOT delete the retry key from the handler-set type — `buildApprovalRequestHandlerSet` (`progressBackendUiConfig.ts:47-49`) intentionally requires host-supplied retry/agentProposal transports; the wart is the stub+comment, not the contract.

### Throw-vs-return violations

- **UICPL-02 (medium) — headless `texra run` treats a routine provider failure as an unexpected CLI crash: prints it twice AND solicits a bug report.** Mechanism: reflection/tooluse flows re-throw on `shared.lastError` (`runReflectionFlow.ts:331-340`, `runToolUseFlow.ts:430-443`); `classifyAgentError→'unexpected'` emits an error toast → stderr (print #1, `runtimeHost.ts:98-105`→`logSinks.ts:148-155`); nothing in `run→command→runCli` catches the `AgentError` (`isCliError` requires `name==='CLIError'`, `dispatch.ts:31-37`) so it reaches `bin/texra.ts:16-24` → "TeXRA CLI failed:" (print #2, same message) + `formatCrashReportLine` "please report it" (print #3). The bin comment "this catch only fires on UNEXPECTED crashes" is provably false. **Fix:** have `executeCliRequest`/the run command consume the classified terminal error into an exit code (it already reads `terminalStatus`, `runExecution.ts:235-239`) instead of rethrowing; reserve bin's crash-report for genuinely unclassified throws. This _is_ the throw-vs-return violation — a classified routine failure thrown to the crash boundary rather than returned as an exit code. **Rejected trap:** do NOT add a global CLI error-classification framework in bin — `classifyAgentError` already exists; consume it at the boundary.

### Duplicate error-surface ownership (error UI-coupling)

- **UICPL-03 (medium, host-neutral base) — two ERROR transcript rows per failure, no single owner.** One `RetryState` op-row (`:265` retryable _or_ `:330-335` non-retryable — mutually exclusive) **plus** the lifecycle run-row (`AgentRunLifecycle.ts:418-421`), same run trace → `StreamLogStore`, both in `TRANSCRIPT_MESSAGE_TYPES`, distinct text → no dedup → 2 rows in **every** host; the planned `reported` gate was never applied (grep = none). **Fix (0..−3 LoC):** demote one emitter to debug (single visible owner). **Rejected trap:** do NOT thread a `reported` boolean across the retry→flow seam if it nets +LoC.

- **UICPL-01 (medium, CLI extension of UICPL-03) — CLI renders a 3rd, verbatim-duplicate row.** The host `.catch` calls `appendLocalErrorTranscript(toErrorMessage(rethrown AgentError))` (`chatSessionController.ts:213-220,338`), text-identical to the lifecycle row, and local synthetics are explicitly exempt from `subscribeStreamLog.ts:407` dedup → renders twice. (The `requestShowError` toast goes to _stderr_, not a transcript row, so the transcript count is op-row + lifecycle-row + local-catch-row = 3.) **Fix (−1..−3 LoC):** gate `appendLocalErrorTranscript` to pre-start failures only (no stream resolved) — post-start relies on the core stream-log row. **Rejected trap:** do NOT add a cross-host transcript dedup reducer or move TUI error rendering into core — delete the redundant host-side write.

- **UICPL-04 (low) — desktop auto-declines every retryable failure and mislabels it "Retry cancelled by user" with no dialog.** `desktopHostInteractions.ts:130-132` returns `{action:'cancel'}` where it should return `{action:'deny'}`; `RetryState.ts:311-319` records the user-cancel string + terminalizes CANCELLED with `lastError` unset (`:372-374`), so `terminalResultToast` returns null (`terminalResultPresentation.ts:41` `!event.error` guard) and credential-exhaustion goes unexplained. The `'deny'` path (`:293-309`) exists precisely for "no human to approve." **Fix (~0 LoC):** return `{action:'deny'}` (+reason) → routes to FAILED → surfaces via the wired error dialog. **Rejected trap:** do NOT just relabel the string (the fix is action semantics, which also restores the dialog); do NOT ship a retry panel with a dead `USE_OWN_API_KEY` button.

### Ownership seams (instruction channel + duplicate abort predicate)

- **EP-3 (medium) — `requestShowInstruction` has one consumer (extension); CLI degrades it to a debug log, desktop drops it; shared text hardcodes "extension settings".** Only handler: `agentEventListeners.ts:147`. CLI falls through to `ensureLogger().debug` (`runtimeHost.ts:126`, swallowed under `quietLogs :116`); desktop handles only `requestShowError`. So the actionable missing-api-key toast (`terminalResultPresentation.ts:48-60`, `SET_API_KEY`+`OPEN_CONFIGURATION_GUIDE`) and the missing-output-files notice (`OutputNode.ts:319-324`) never reach CLI/desktop, and `MISSING_API_KEY_MESSAGE` (`terminalResultPresentation.ts:31-32`) wrongly tells every host to use "the extension settings" — a VS-Code-flavored leak into host-neutral `@shared`. **Fix (additive per-host):** add a `requestShowInstruction` handler to CLI `runtimeHost` + the desktop progress switch (or fold instruction into the existing `requestShowError` path there); de-hardcode `:31-32`. **Rejected trap:** do NOT build a shared cross-host instruction reducer or a new subscribe surface — add the missing per-host consumer to the existing `runtimeHost.emit` path, mirroring `requestShowError`.

- **EP-5 (low, new) — a second abort predicate survives.** `errorPredicates.ts:2-4` `isAbortError` (name-only) has one live caller, `childRunLoop.ts:255` inside `isCleanInterruption` (`signal.aborted || … || isAbortError(err)`), plus a barrel export `index.ts:13`. Canonical `isUserAbort` (`errorPatterns.ts:18`) is a strict superset (tagged `user_abort` OR class-name `APIUserAbortError` OR `name==='AbortError'`); the narrower predicate misclassifies a tagged/class-name child-run abort whose `.name!=='AbortError'` when `signal.aborted` isn't yet observed. **Fix (−4..−6 LoC):** replace the call with `isUserAbort(err)` and delete `isAbortError` + its barrel export. **Rejected trap:** do NOT fold the settled internal DOMException branch in `providerErrorFormat.ts` into `isUserAbort` — that branch is inside the normalization core (correct); only the out-of-core `isAbortError` is the duplicate.
