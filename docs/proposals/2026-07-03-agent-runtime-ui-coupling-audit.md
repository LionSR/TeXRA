**Scope:** How `src/agent/`'s runtime emits state/events, and how the three UI hosts (VS Code extension webview, Electron desktop, CLI/Ink TUI) consume and act on it. Triggered by a felt sense that the codebase runs "dual or even multiple systems" between agent runtime and UI, with a request to find the severest problems and prioritize LOC-reducing, non-abstraction-adding fixes.
**Method:** 10-pass investigation — 3 initial scouts (emission surface, front-end bridges, existing abstraction/proposal docs) → 3 adversarial verifiers (is the duplication real, or justified divergence? is the "fix" actually LOC-negative?) → 3 root-cause hunters (is there one systemic redesign underneath the symptoms?) → 1 contradiction-resolver (a source doc's own sections disagreed with each other on one finding; resolved by direct re-investigation). Explicitly designed to avoid this repo's known trap: "extract shared abstraction" refactors that look clean but net-_add_ LOC when call sites diverge for real reasons (see `project_refactor_loc_lesson.md`).
**Related:** `docs/proposals/2026-06-10-error-pipeline-and-ownership.md`, `2026-06-07-dependency-injection-cleanup.md`, `2026-05-31-tui-extension-sharing.md`, `2026-06-10-session-handle-7d-design.md`, `2026-06-10-lifecycle-status-ownership.md` — this audit builds on and cross-checks all five rather than re-deriving their findings.

## TL;DR — verdict

There is no single mega-unifying redesign hiding underneath the symptoms. Two candidate "big fixes" were explicitly tested and rejected: merging the `AgentEvent` trace and `ProgressEventBus` taxonomies into one system, and formalizing "two canonical host-adapter topologies" as new interface types. Both would be LOC-neutral-to-negative at best, complexity traps at worst — see "Rejected alternatives" below.

The closest thing to a root cause is a **discoverability/naming mismatch**: the directory CLAUDE.md documents as "host-neutral orchestration for the main, progress, and settings views" (`src/controllers/`) turns out to only handle _inbound_ UI→runtime requests. The actual _outbound_ runtime→UI event-consumption code lives in a differently-named sibling, `src/controllers/progressView/backend/` — a deliberate relocation from issue #5451 (2026-06-07, "Unify the progress-view backend across extension + desktop"), which chose "shared core" as the destination rather than aligning with the later-established `controllers/` convention. That naming gap has already caused the project's own internal audits to miss it twice: once in a sharing roadmap (`2026-05-31-tui-extension-sharing.md`) that silently omitted this directory when cataloging "the host-neutral layer," and once in the confirmed bug that is finding #1 below.

**As of the original writing, 4 of the 5 candidate findings remained open** (all now closed — see Status) — the 5th (dead `ClipboardHost`/`TerminalHost` ports) was fixed by PR #6883 while this audit was in flight, and that same PR made partial progress on finding #4 (folded 4 _other_ module-level setters into `Platform`, per `2026-06-07-dependency-injection-cleanup.md` Step 1) without touching the one setter this audit flags. This repo iterates fast on exactly this territory — re-verify line numbers against current `HEAD` before acting on anything below.

## Verified findings (issues filed)

### 1. Desktop never force-closes crash-orphaned transcript groups or distinguishes resumable streams on restart

**Issue:** [#6887](https://github.com/LionSR/TeXRA/issues/6887)

Desktop's `DesktopStreamSnapshotStore` (`packages/desktop/src/main/desktopStreamSnapshot.ts`) force-normalizes restored streams to `STOPPED` on relaunch — so it does _not_ show stuck-RUNNING ghosts (an earlier framing of this bug, sourced from a self-contradicting line in `2026-06-10-lifecycle-status-ownership.md`, overstated the symptom; this was corrected by direct re-investigation before filing). But the module's own docstring admits scope: _"Live re-establishment of agent runtimes is intentionally out of scope here — that's tracked as a Phase 2 follow-up."_ Concretely, desktop startup never calls `detectWaitingStreams` (can't tell resumable-from-flow-record from truly-dead — blanket-labels everything `STOPPED`) or `endRunningTaskGroups`/`StreamLogStore.endRunningGroups` (never force-closes a transcript log group left open by a crash — reopening that ghost stream renders a permanently incomplete `GROUP_START` with no `GROUP_END`). The extension calls this repair sequence once, from `packages/extension/src/extension.ts:499` (`await progressViewProvider.cleanupTasksAfterRestart()`). Desktop already instantiates the _identical_ host-neutral `ProgressBackend`/`ProgressEventHandler`/`StreamLogStore` graph (`packages/desktop/src/main/desktopAgentExecution.ts:232`) — it just never invokes the repair call on it.

Related closed work confirms this is a real, previously-tracked gap that was never fully closed: #5596 ("Desktop ghost restore should use the backend snapshot store," closed 2026-06-08) fixed a _different_ bug — a redundant private `StreamSnapshotStore` reader — but did not add the repair-on-restart call. #5452 ("Desktop: enable real run-resume") is the adjacent resume-capability issue.

**Fix:** one startup call in `packages/desktop/src/main/index.ts` (near where `DesktopStreamSnapshotStore` is opened, `app.whenReady()`) running the same `detectWaitingStreams` + `endRunningTaskGroups` repair against desktop's existing `ProgressBackend` instance, mirroring `extension.ts:499`. ~10-30 LOC, no new abstractions.

**Bundled root-cause fix (near-zero risk):** rename `src/controllers/progressView/backend/` → `src/controllers/progressView/outbound/` — pure mechanical path-alias swap, ~39 line touches across 15 files (verified count at audit time), one regex, zero behavior change. Makes CLAUDE.md's "controllers = host-neutral orchestration" claim actually true. Also rename `DesktopStreamSnapshotStore` (confusingly similar to the actually-shared `src/transcript/StreamSnapshotStore.ts`) to something like `DesktopRestoredStreamStore` (~13 line touches) — real, dated naming friction (created a month before the shared store, on top of an already-occupied conceptual space), no confirmed bug from it, cheap to fix.

### 2. CLI bypasses the shared `ProgressAgentProposalController` for approval/proposal orchestration

**Issue:** [#6888](https://github.com/LionSR/TeXRA/issues/6888)

Extension and desktop both route every proposal action (`setup`/`approve`/`reject`) through one shared controller, `src/controllers/progressView/ProgressAgentProposalController.ts` (113 LOC). CLI reimplements this by hand in 2 places — `packages/cli/src/chat/tui/state/subscribeApprovals.ts:408-417` (`dispatchProposal`) and `packages/cli/src/runtime/approval/eventDispatch.ts:66-72` (`dispatchApprovalDecision`, case `showAgentProposal`) — calling `runCoordinatorBridge.resolveProposal` directly. Direct, confirmed consequence: the CLI cannot do `setup` proposal actions the other two hosts support.

This fits a well-established pattern the team has been actively closing: #6692 ("Route progress-view approval resolution through session coordinators," closed 2026-06-30) fixed the _extension's_ equivalent direct-`runCoordinatorBridge` bypass for retry/plan-approval actions, explicitly ruling _"This issue should not create a shallow pass-through object. The new boundary should either enforce a real invariant or remove direct global coupling from the host UI layer."_ PR #6682 (referenced by #6692) did the same for CLI's _non-proposal_ approval types via `installTuiApprovals`. Proposal resolution specifically was left out of both. An existing 4-rung fix plan (`docs/proposals/2026-05-31-tui-extension-sharing.md`) has rungs 1-2 landed (shared `ApprovalDecision` schema, shared `approvalPolicy.ts`), rungs 3-4 not.

**Fix:** Rung 3, approve/reject subset only (verified the controller's dependencies are plain callbacks, not webview-message-shaped — no adapter needed): construct one `ProgressAgentProposalController` in each of the 2 CLI call sites, stub `getPendingProposal`/`restoreTaskState` as the doc itself proposes (`restoreTaskState → false` initially). ~20-40 LOC, mechanical, low risk. Full `setup`-action parity is separate, larger, genuinely new interactive-TUI feature work (~150-400 LOC, since the CLI has no editable-config-form equivalent today) — track as a follow-on, not part of this fix.

### 3. CLI's shared-bus usage is vestigial, and headless `texra run` silently never persists stream sidecars

**Issue:** [#6889](https://github.com/LionSR/TeXRA/issues/6889)

`createCliRuntimeHost` (headless CLI's `AgentRuntimeHost`, `packages/cli/src/runtime/runtimeHost.ts`) never touches the shared `bus` — confirmed via full-file read and repo-wide grep (zero matches). `StreamSnapshotStore` (`src/transcript/StreamSnapshotStore.ts`) is the sole persister of todos/plan/usage/output-files sidecars, and its `subscribe(bus)` method has exactly one real production caller in the entire codebase: the CLI's interactive TUI (`packages/cli/src/chat/tui/runChatTui.tsx:413`). Extension and desktop populate the same store through _direct method calls_ inside their own bus handlers, never via `subscribe()`. Net effect: a stream driven through headless `texra run` produces empty todos/plan/usage if later viewed in desktop/extension/CLI-TUI. Degrades gracefully — execution state itself (the `getExecutionStore()`/TaskState checkpoint store, used by `texra resume`/`texra history`) is entirely unaffected; only _display_ state is empty on cross-host restore.

Separately: CLI TUI's `wrapRuntimeHost` mirrors events onto `bus` _purely_ to feed that one `StreamSnapshotStore.subscribe(bus)` call — nothing else in CLI touches `bus` (`subscribeStreamLog`/`subscribeStreamStatus`/`subscribeApprovals` all use separate in-process signal emitters). And desktop's `DesktopProgressEventBridgeImpl` has an internal inconsistency with no technical justification: 5 event types handled via a direct synchronous call inside `handleProgressEvent`, 3 handled via a separate, redundant `bus.on()` registration in the same class's constructor (`packages/desktop/src/main/desktopProgressEventBridge.ts:141-164` vs `:175-223`).

**Fix (single combined change, high confidence — the most confidently net-negative-LOC fix in this audit):**

- Add the 3 missing mutator calls (`addOutputFiles`, `updateMissingOutputs`, `updateCompileFailures`) directly into CLI's existing `applyToState` switch (`subscribeRuntimeHost.ts`) — the store reference is already reachable via `ChatSessionControllerInit.snapshotStore`.
- Delete `StreamSnapshotStore.subscribe()`'s now-dead pub-sub-shaped API (~64 LOC) and CLI's `bus` mirroring/imports (`wrapRuntimeHost`, `runChatTui.tsx`).
- Wire headless `texra run` (`runExecution.ts`) to construct + flush a `StreamSnapshotStore` directly against its `AgentRuntimeHost` — fixes the actual persistence gap, ~15-30 LOC.
- Merge desktop's 3 stray `bus.on()` cases into its existing direct-call switch, ~15-25 LOC saved.
- **Net estimate: −40 to −45 LOC.**

### 4. `setToolEditApprovalHandler` — one of the remaining ambient-approval-ownership module globals

**Issue:** [#6890](https://github.com/LionSR/TeXRA/issues/6890)

`docs/proposals/2026-06-07-dependency-injection-cleanup.md` (audited 2026-06-07, addendum 06-10, not fully implemented) documents 22 module-level `set*` singletons and a fat `AgentCore` context bag. PR #6883 (2026-07-02, landed during this audit) folded 4 of them — `setLinterProvider`, `setAddCriticismSink`, `setToolMissingHandler`, `setToolNotificationHandler` — into typed `Platform` ports, and de-duplicated 3 flow nodes' reads of `runtimeHost`/`streamId`/`executionId` via `RunContext`, both explicitly citing that doc. `setToolEditApprovalHandler` was **not** among them — re-verified at current `HEAD`: still a bare module-level singleton (`src/tools/approval/toolEditApproval.ts`), still written from 4 files across all 3 hosts (`packages/cli/src/chat/tui/state/subscribeApprovals.ts:153,175`, `packages/cli/src/runtime/approvalAdapter.ts:86,90`, `packages/desktop/src/main/desktopToolEditApproval.ts:66,150`, `packages/extension/src/frontend/approval/nativeToolEditApproval.ts:386`). The DI-cleanup doc's own description: _"the active session's approval channel, currently a single module global mutated by whichever host UI is active."_ This is the same disease as finding #2, one layer down the stack — ambient runtime state owned by "whichever UI happens to be running" instead of resolved once at a composition root.

A prior, narrower issue (#5903, "CLI tool-edit approval handler is owned outside the runtime host lifecycle," closed 2026-06-12) fixed a related-but-distinct problem: CLI's headless command entrypoints sharing one lifecycle for installing/restoring the handler and hooking it to the progress-renderer prompt boundary. It did not fold the setter itself into a typed port — the module-level-global architecture this finding flags is unchanged by that fix.

**Fix:** fold `setToolEditApprovalHandler`/`getToolEditApprovalHandler` into a typed `Platform` port (or a `RunContext`/`SessionHandle`-scoped field, if the approval channel is meant to vary per concurrent session rather than per-process — worth deciding explicitly, since today's global-mutation pattern silently assumes one active session per process). This is scoped, incremental work within the existing DI-cleanup plan — do not attempt the full 22-setter/context-bag split as a single change; track the remainder (context-bag split into `RunIdentity`/`DelegationPolicy`/`AgentDefinition`/ambient, per the doc's steps 1-5) as a separate, larger tracking item. LOC delta for just this setter: small and likely near-neutral (this is about correctness/concurrency-readiness, not deletion).
