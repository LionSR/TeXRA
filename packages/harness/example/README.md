# Packed-tarball examples

Runs [`@texra-ai/llm`](../../llm/README.md) and [`@texra-ai/harness`](../README.md) the way a consumer off the registry gets them: both packages are packed into `.tgz` tarballs, installed into a fresh directory outside the repository with `npm install`, type-checked with `skipLibCheck: false`, and executed by `node`. Every import specifier is a published package subpath (`@texra-ai/llm`, `@texra-ai/llm/node`, `@texra-ai/harness`, `@texra-ai/harness/node`, `@texra-ai/harness/plugins`, `@texra-ai/harness/schemas`, `@texra-ai/harness/transcript`), never a workspace path alias.

None of the examples need a provider API key or network access: `01-llm-turn.ts` supplies in-process `fetch` handlers to `bindModel`, and `02`–`10` use `_support.ts`, which builds `nodePlatform` and provides the harness's `ModelFetch` beneath `Sessions.layer` with an in-memory Anthropic Messages SSE fetch that answers each request with the example's next scripted turn.

Set `TEXRA_EXAMPLE_MODEL` to a `provider/model` string (for example `anthropic/claude-sonnet-5-5`) to run `02`–`10` against that real route instead: `_support.ts` then supplies no fetch, the harness's own transport carries the requests, and the provider's API key comes from its usual environment variable (`<PROVIDER>_API_KEY`, such as `ANTHROPIC_API_KEY`). The checks an example makes on its scripted turns (request counts, the exact replies) hold only on the in-memory model.

```bash
corepack pnpm --filter @texra-ai/harness run example:packed
```

The harness's `typecheck` (part of the repository's `npm run typecheck`) also type-checks these files in the workspace, with this directory's `tsconfig.json` over the declarations the build writes to `dist/` (`../tsconfig.example.json` maps each published subpath to its declaration), so a change that breaks an example fails before a push. Only `example:packed` installs the tarballs and runs the examples.

## Real-model acceptance

`acceptance.ts` is the harness's acceptance against a real model. Nothing in it hands the model a script: each scenario states a task in plain words, the model reads the tool descriptions and writes the programs itself, and the checks read only outcomes, calls, child runs, facts and artifacts, never exact text or request counts, so they hold for any competent model.

| Scenario       | What the model does, and what is checked                                                                                                                                                                                                                                                                                                                                                                                        |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `codemode`     | From an agent file: a script that outlines `draft.tex` through a plugin's script module, runs two `self()` review rounds (the second chosen from the first's structured verdict) and counts its finished children with `executions` SQL over `runs`. Checks the calls, two completed children each ending with a structured verdict that names a section, every section title in the return and the SQL count against the view. |
| `plugin`       | The `acme-notes` package's agent: a script over its `builtIn:notes` module. Checks the import, the `note_add` calls, both notes as version-1 facts of the plugin, and the return.                                                                                                                                                                                                                                               |
| `crash-resume` | A second process runs a script that waits on a sign-off tool after its first `self()` round and is killed with SIGKILL once that child's result is committed; this process resumes the run. Checks that exactly one round was committed before the kill and did not run again, a second round completed after the resume, and the script finished from its saved source.                                                        |

It packs and installs like the ladder, then runs `acceptance.ts` instead of `npm start`. It needs a route and that provider's key; a route without its key is recorded as skipped and sends nothing. It spends money, so it runs only by hand, never in CI:

```bash
TEXRA_EXAMPLE_MODEL=deepseek/deepseek-flash \
  corepack pnpm --filter @texra-ai/harness run example:acceptance
TEXRA_EXAMPLE_MODEL=anthropic/claude-haiku-5-5 \
  corepack pnpm --filter @texra-ai/harness run example:acceptance
```

Each run writes its evidence (`_evidence.ts`) to a new directory, `.agents/docs/evidence/<date>-harness-real-model/<provider>-<model>-<HHMM>/` (`TEXRA_ACCEPTANCE_OUT` names another): `summary.md` and `run.json` (route, model, harness version and commit, each scenario's result, failed checks, tokens and the spend the runs report), and per scenario `config.json`, `scripts/` (every program the model wrote), `conversation.json`, `children.json`, `runs.json`, `calls.json` (each tool call with how it ended), `outputs/` (script returns, run end, reply, facts) and `result.json`. Each scenario's session database is copied to `store/`, which git ignores.

| `06-views-and-transcript.ts`     | `session.view.subscribe`, `sessionActivity`, `attentionOf`, `acceptsFollowUp`, `TranscriptRow` formatting (`rowHeadline`, `elideText`), and `ToolRowModel` sections.                                                                                                                                                                                                                                                                                                                                                                                  |
| `07-programmed-path.ts`          | An agent file from the agent directory, started by name (same system text and tools as the inline persona); a plugin tool with a script module (`scriptModules`); a `script` that imports the module, runs `self()` twice with a JSON Schema and reads `structured`, then reads its own calls back with `executions` SQL: the plugin call's structured result from `tool_calls` (`columns`, `rows`, `more`, a long cell), each child's status from `runs` joined to the call that launched it, and a write refused.                                   |
| `08-crash-and-resume.ts`         | A real crash: spawns itself as a child process, kills it with SIGKILL once a `self()` result is committed (seen through `session.view.events`) while its script still waits, then resumes the run here: the finished child is not run again, the script continues from its saved source, and the run completes.                                                                                                                                                                                                                                       |
| `09-goal-strategies.ts`          | Two goal strategies on one kernel: a plan run as a goal on the default strategy (`builtIn:goal`: forked rounds, the previous report), then on a plugin's script module selected by `goal.strategy` (fresh rounds with `fork: false`, every earlier report). Each completes two `self()` rounds, and its run's structured output decodes with `GoalResultSchema`: `needs_user` and `spend_cap` pauses with their rounds and spend.                                                                                                                     |

Run with it; reopen without it, where the run's fact reads as written with why (`unavailable`) and `session.resume` is refused as `pluginUnavailable`; reopen with it, where the fact reads interpreted, unchanged, and the run resumes on a message sent under an `id` and waits on its `followUp.receipt`. |

## How `scripts/example-packed.mjs` runs

1. Copies `package.json`, `tsconfig.json`, `_support.ts`, `acceptance.ts` with `_evidence.ts`, and `01-*.ts`..`10-*.ts` into a temporary directory outside the repository.
2. Runs `pnpm --filter @texra-ai/llm pack` and `pnpm --filter @texra-ai/harness pack` into that directory as `llm.tgz` and `harness.tgz`, and `npm pack acme-notes/` as `acme-notes.tgz`.
3. Runs `npm install --no-audit --no-fund` (plain `node_modules`, no workspace lockfile).
4. Runs `tsc -p` with `strict: true`, `moduleResolution: "nodenext"`, and `skipLibCheck: false`.
5. Runs `npm start` (executing `01` through `10` in order), or with `--acceptance` `node acceptance.ts`, and removes the temporary directory on success.
