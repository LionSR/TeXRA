## 回答一：问题「有哪些 AI 工具真的能帮到科研和论文写作？」（主版本：发布向）

利益相关：本人是 TeXRA 的开发者。下面先讲不依赖任何产品的通用经验，最后一段才说自己的工具，大家自行判断。

先说结论：判断一个 AI 工具对科研有没有用，标准只有两条：它是否工作在你真正干活的地方（你的 .tex 文件、你的编辑器、你的终端），以及它的每一步产出是否可以被你检查和拒绝。满足不了这两条的，新鲜感过去之后都会回到吃灰状态。

通用经验，按任务分：

1. 语言润色。网页版聊天模型改一段话没问题，但复制粘贴回 .tex 时最容易出事：数学公式被悄悄改写、\cite 和 \ref 被吞、个人风格被洗成 AI 腔。无论用什么工具，养成习惯：AI 改完先跑 latexdiff，看红蓝对照 PDF 再合并。
2. 文献调研。要求 AI 给出可点击的来源（arXiv 编号、DOI），给不出来源的“经典文献”默认当作编造处理。
3. 推导检查。对模型说“再检查一遍”基本无效，它会顺着自己的错误再走一遍。有效做法是换独立上下文重问，或者接 Wolfram 这类计算工具做数值验证。

然后是利益相关的部分。我自己写代码有 Copilot、Cursor、Claude Code，回头写论文却只剩浏览器标签页里的聊天框和无穷无尽的复制粘贴，落差大到忍不了，所以做了 TeXRA，最近刚公开发布。一句话：它是面向论文的 AI 工具，在 VS Code 和终端里直接操作你的 .tex 文件，所有修改以 latexdiff PDF（红色删除线、蓝色新增）的形式等你批准，确认前不碰你的文件。内置 44 个 agent，我自己最常用 polish（润色）、correct（只修错别字和语法，刻意保留你的风格）、review（检查推导，可调用 Wolfram 验证）、latexFixer（修编译错误）。国内同学关心的模型问题：支持 DeepSeek、GLM、Kimi、Qwen、MiniMax 自带 key 接入（加密存储），GitHub 或 Google 登录含免费额度，学术研究者还可以申请 Researcher Access Program 的免费托管额度。

诚实的局限：它不替你想 idea；超长文档的全局一致性仍要人盯；模型会犯的错它照样会犯，所以“每个 diff 必须人工批准”是强制流程而不是可选项。官网 texra.ai，VS Code 应用市场搜 TeXRA，命令行 npm i -g @texra-ai/cli。如果你现在的复制粘贴流程用得很顺，那也没必要换。

## 回答二：问题「AI 能可靠地检查数学推导吗？」（长青版，无发布措辞）

利益相关：本人是 TeXRA 的开发者，回答后半部分会提到它。

先说结论：把推导直接扔给聊天模型问“对不对”，不可靠；但把模型放进带计算验证工具、且每个结论都能被你复查的流程里，它已经是一个相当称职的第一遍审稿人。不可靠和可靠之间，差的不是模型，是流程。

裸聊天为什么不可靠，三个原因：

1. 顺从性。你的推导写得越自信，模型越倾向于回答“推导正确”。
2. 注意力盲区。长推导里恰恰是单个负号、下标错位这类机械错误最容易被漏掉。
3. 自我验证失效。模型检查自己生成的推导时，会沿同一条错误路径再走一遍。

不依赖任何特定产品的有效做法：

1. 拆步验证：一步一问，不要整页推导一次性扔进去。
2. 数值交叉检验：关键等式让它代入具体数值，或用 Wolfram、SymPy 做符号验证，数值对不上立刻暴露。
3. 双模型独立检查：两个模型的分歧处往往就是问题所在。
4. 反向提问：“请找出这段推导中的错误”比“请检查这段推导”的召回率高得多。

我们在 TeXRA 里把这套流程产品化了。review agent 检查推导正确性时会调用 Wolfram 工具做符号和数值验证；research agent 负责解析推导和数值实验。举一个我们演示用样例文档里的完整流程：review 在一处推导里抓到一个传播了三行的符号错误（sign flip），先用 Wolfram 验证了正确形式，再把修正以 diff 的形式提出来，红蓝对照 PDF，作者确认后才写入文件。verifyFix agent 跑“验证、修复、复验”三阶段循环。想走更硬的路线，还有 5 个 Lean 4 agent 支持形式化验证。

但局限必须说清楚：

1. 它擅长机械性错误（符号、系数、漏项、量纲），对“这个引理的条件是否足够强”这类深层问题，产出的是值得人工复查的疑点，不是判决。
2. Wolfram 能验证的是可计算的等式，抽象论证部分仍然依赖模型本身的判断。
3. 假阴性永远存在：AI 没报错，不等于推导没错。

所以正确的定位是投稿前多一道筛子，不是正确性的最终担保，最终责任在作者。工具在 texra.ai，VS Code 市场搜 TeXRA，或 npm i -g @texra-ai/cli。

## 回答三：问题「如何把 AI 整合进 LaTeX 写作工作流？」（长青版，无发布措辞）

利益相关：本人是 TeXRA 的开发者。先讲普适原则，再讲我们的实现。

先说结论：LaTeX 加 AI 的工作流，核心不是选哪个模型，而是三条工程原则：改动可视化（latexdiff）、改动可回滚（git）、改动可批准（人审每一个 diff）。三条都满足，用什么模型都不会太糟；缺一条，再强的模型也会坑你。

通用做法，不管你用什么 AI：

1. 论文必须进 git，AI 介入前先 commit，这是唯一可靠的后悔药。
2. 任何 AI 修改后，跑 latexdiff 生成红蓝对照 PDF 再看。肉眼 diff .tex 源码会漏掉数学模式里的细微改动。
3. prompt 里写明约束：“不要动 \cite、\ref、\label，不要改 preamble”，否则一次编译错误能折腾半天。
4. 任务分层：修错别字是一类任务，重写段落结构是另一类，混在一个 prompt 里两头都做不好。

TeXRA 就是把这套流程做成了产品：VS Code 插件（Cursor、Windsurf 也能装）加终端 CLI。典型的一天：

1. 改完一节初稿，跑 polish agent 润色；只想修错别字语法就用 correct agent，它刻意不动你的行文风格。输出不直接写文件，而是进入版本化暂存区并自动生成 latexdiff PDF：红色删除线、蓝色新增，只显示有改动的页。看完逐条接受或拒绝。
2. 编译挂了，latexFixer agent 读编译日志定位修复，连 latexdiff 产生的 DIF 标记损坏也能修。
3. 终端党可以全程命令行：texra run polish --input - 支持 stdin 管道，能写进脚本；texra chat 是交互式 TUI。
4. 想被狠狠批一顿，criticize agent 用 \criticize{意见}{严重度}{置信度} 在源码里插入行内批注，像一位不留情面的审稿人。

成本（国内同学最常问）：支持 DeepSeek、GLM、Kimi、Qwen、MiniMax 等自带 key（加密存储），GitHub 或 Google 登录含免费额度（用量在设置里可见），学术研究者可申请 Researcher Access Program 的免费托管额度，免费额度用完会自动回落到你自己的 key。

局限说在前面：几百页书稿级别的全局重构还做不到，要按章节喂；agent 偶尔会过度润色，这正是 correct 和 polish 被拆成两个 agent 的原因；它的安全设计建立在“你会认真看 diff”之上，打算盲点接受的话，这套设计对你无效。

官网 texra.ai。安装：VS Code 市场搜 TeXRA，或 npm i -g @texra-ai/cli，或 brew install texra-ai/tap/texra。

## 加餐一：问题「用 AI 修改、润色自己的论文，算学术不端吗？」（长青版，伦理角度）

利益相关：本人是 TeXRA（一个论文 AI 工具）的开发者。这个问题学术用户反复问我们，所以认真答一次。结论对用不用我们的工具都成立。

先说结论：界线不在“用没用 AI”，而在两件事：你是否对每一处改动负完全责任，以及你是否遵守目标期刊和所在机构的披露政策。

讲理由。学术不端的实质是署名者对内容不负责：编造数据、编造引用、署名你没有验证过的结论。语言润色本身一直存在：导师改、合作者改、付费润色服务改，从来没人因此被认定不端。AI 润色在性质上属于同一类，前提是你逐句确认过改动。真正危险的是三类行为：让 AI 编造文献引用；把 AI 生成而你未验证的推导直接署名；对明确要求披露 AI 使用的期刊隐瞒使用。

可操作的建议：

1. 投稿前查目标期刊的 AI 政策。主流出版社多数允许 AI 辅助语言编辑但要求声明，且一致禁止 AI 署名。政策各家不同，以你的目标期刊和所在机构为准。
2. 保留修改记录，能说清“AI 提议了什么、我接受了什么”。
3. 推导、数据、引用这类事实性内容，AI 碰过的必须自己重新验证一遍。

这也是我们做 TeXRA 时的核心立场：AI 辅助，作者保持控制和责任。落到设计上：每处修改以 latexdiff 形式（红色删除线、蓝色新增）等待批准，确认前不写入文件；运行历史可检索，需要披露时拿得出完整记录；review、criticize、verifyFix 这些 agent 的定位是审稿和纠错，不是代写。我们希望它让论文更严谨，而不是更容易蒙混。

局限也直说：工具管不了动机。一个决心把 AI 产出直接署名的人，任何产品设计都拦不住。最终的判断和责任在作者本人，这一点没有任何工具能代替。

## 加餐二：问题「AI agent 现在能自主跑多长的科研任务？无人值守靠谱吗？」（v0.38 版本向）

利益相关：本人是 TeXRA 的开发者。

先说结论：跑几个小时不停手在技术上已经成立，但“靠谱”取决于两道闸门：花费闸门（预算到阈值自动暂停，等批准再继续）和写入闸门（所有产出以 diff 形式等人审）。无人值守不等于无人负责。

先讲通用观察。长程 agent 的典型失败模式不是中途崩溃，而是勤奋地跑偏：对目标的理解出现一度偏差，然后用几十次工具调用把这个偏差执行得非常彻底，事后看 transcript 会发现每一步局部都合理。所以约束自主性的正确位置不在“限制它能做什么”，而在“它做完之后什么能落地”：钱花到哪个量级要人批，文件改成什么样要人批，中间过程可以放开让它跑。

具体到 TeXRA：v0.38 起 Odyssey 自主模式默认开启，给定目标后 agent 持续推进直到自己声明完成，预算达到阈值自动暂停，批准后继续。配合这一版的几个新东西：Software Engineer 团队预设（团队里每个成员可以跑不同的模型，旗舰推理模型当 orchestrator，子任务交给 DeepSeek V4 Flash 这类又快又便宜的）；以及 Claude Fable 5 支持（always-on adaptive thinking）。终端里 texra multi-agent run 起一个团队，进度实时显示，可以聚焦到单个 subagent 看它的完整过程，确认后放行。

什么任务适合交给自主模式？共同特征是边界清晰、结果可验证：修编译错误直到通过、对推导逐条做数值验证、按审稿意见清单逐项修改并生成 diff。不适合的是“帮我把这篇论文写好”这种开放目标。目标漂移在长程任务里仍然真实存在，这是当前所有 autonomous agent 的共同局限，不是哪家产品能例外的。

我们的取舍是宁可多打扰一次：花费升级之前先停下来要批准，宁愿你多点一次“继续”，也不要你早上醒来发现 agent 跑了一整晚不需要的东西。

官网 texra.ai，VS Code 市场搜 TeXRA，CLI 安装：npm i -g @texra-ai/cli 或 brew install texra-ai/tap/texra。
