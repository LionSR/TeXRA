# Catch-clause migration census

> **Status:** measured on `main` at `2884b49` on 2026-09-06. Production scope
> only: `src/` and `packages/*/src/`, excluding tests, harness scripts, and
> `dist`. 1059 clauses in 415 files. Classification by agents, with an
> independent check of every fourth entry; the per-slice agreement rates are
> in section 4. This is the census that Phase 0, item 6 of
> [`.agents/docs/proposed/architecture/2026-08-26-effect-4-runtime-migration.md`](../../proposed/architecture/2026-08-26-effect-4-runtime-migration.md)
> asks for. No production code changes accompany it.

## 1. Why this census exists

P12 of the Effect migration PRD makes one claim about the current code: a
`catch` clause does not say what it is for. The survey behind the PRD counted
884 production catch clauses from the syntax tree and did not treat the count
as a defect, because filesystem and SDK boundaries throw, best-effort
projections must not replace primary outcomes, and sandbox errors cross
JavaScript realms. The defect is that the syntax hides which of several
meanings a given clause carries: translating a boundary error, recovering from
a typed condition, implementing cleanup, aggregating secondary failures,
converting an exception into control flow, or hiding a defect. Because the
meaning is supplied only by local control flow, cancellation can be caught as
an ordinary error, the same failure can be logged at several levels, and each
clause has to preserve primary-error precedence by hand.

The migration does something different with each meaning, so it needs to know
the meaning before it rewrites the site. That is the whole purpose of this
document: one row per clause, one category per row, and the target the PRD
assigns to that category. The seven categories, with the target each one
collapses into, are quoted from P12 as the classifiers received them:

- **boundary-translation**: converts a thrown/rejected value at a system
  boundary (fs, SDK, provider, network, subprocess, sandbox realm) into a
  domain result or typed error. Target: `Effect.tryPromise` / `Effect.try`
  with a `Data.TaggedError` adapter at the edge.
- **typed-recovery**: handles a specific, anticipated failure and continues
  with an alternative outcome (fallback value, retry, alternate path). Target:
  typed E channel with `catchTag` / retry with a `Schedule`.
- **cleanup**: the catch exists to release, close, restore, or undo something
  and usually rethrows or finishes a finally-like duty. Target: `Scope` /
  `acquireRelease` / `Effect.ensuring`.
- **best-effort-projection**: a secondary, non-authoritative side effect
  (logging, telemetry, UI refresh, cache warm, notification) whose failure
  must not affect the primary outcome; loud at warn or documented as an
  accepted exception. Target: forked or ignored effect with an explicit log,
  or the accepted-exception list.
- **failure-aggregation**: collects errors from several attempts or siblings
  to report them together or choose a first failure. Target: `Cause`
  composition / `Effect.all` with mode `'either'` or `'validate'`.
- **control-flow**: uses exceptions for ordinary branching (parse-or-default,
  exists-or-not, cancellation sentinel checks, "not found means create").
  Target: `Option` / `Either` or a typed E, never a throw.
- **defect-suppression**: swallows or downgrades an error that indicates a bug
  or an unexpected state (empty catch, catch-and-continue with no log, catch
  turning a defect into a default). Target: let it die, or fix the bug; this
  is the list the silent-degradation rule cares about.

The category counts sum to 1059. Twenty-three of the `control-flow` entries

the swallow `CLAUDE.md` warns about on persisted data, and the appendix names
each one as a schema combinator so the migration can decide them together.

Independently of category, 161 of the 1059 clauses are **silent**: they
neither log nor rethrow nor return a value that carries the error. This is the
population the silent-degradation rule in `CLAUDE.md` and §15 of the review
checklist care about. Most of them sit in `control-flow` (ENOENT-means-absent
probes, parse-or-default) and `best-effort-projection` (documented cosmetic
writes), and all 18 `defect-suppression` entries but three are in it. The
silent column in Appendix A is the fastest way to find them.

## 3. The deletion plan

The owner's second ruling on the migration ("fully embrace Effect; no
pass-throughs, no adapters", recorded against R1 in
`.agents/docs/proposed/architecture/2026-08-26-effect-4-runtime-migration.md`) decides what this
census is for. A catch clause is **not** translated into an Effect
equivalent. It is deleted, unless it is one of exactly two things:

1. **The single wrap at a genuine foreign boundary** — one `Effect.tryPromise`
   or `Effect.try` per foreign call site (`node:fs`, `fetch`,
   `node:child_process`, a provider SDK, the VS Code API, Electron IPC, the
   SQLite driver), with one mapper into a tagged error.
2. **A typed recovery** — a branch that inspects the failure and continues,
   which `Effect.catchTag` expresses directly.

Everything else in the tree is a clause that exists because a `Promise` had
no failure channel. Once the surface above it is Effect-typed, the clause has
nothing left to do and the migration's job is to delete it, not to find it a
new spelling. A converted file that still contains a catch is a leftover,
which is what the `catch:effect-importer` row of
`config/ratchets/effect-migration-baseline.json` measures: for a file the
migration has passed through, that row must be **zero**, not smaller.

Read against that rule, the 1,059 clauses divide as follows.

| Category               | Count | Under the ruling                                                                             |
| ---------------------- | ----: | -------------------------------------------------------------------------------------------- |
| typed-recovery         |   182 | **Survives as code** (`catchTag`, or `retry` on a `Schedule`)                                |
| boundary-translation   |   330 | **Collapses** to one wrap per distinct foreign boundary; every downstream re-wrap is deleted |
| cleanup                |   124 | **Deleted** — `Scope` / `acquireRelease` / `ensuring` replace the clause outright            |
| best-effort-projection |   206 | **Deleted or made loud** — no silent survivor                                                |
| control-flow           |   147 | **Deleted** — `Option` / `Either` / a typed `E`, never a throw                               |
| failure-aggregation    |    52 | **Deleted** — `Cause` composes what the manual arrays built                                  |
| defect-suppression     |    18 | **Deleted or fixed** — none migrate                                                          |

So the honest target is not "1,059 clauses become 1,059 Effect
constructs". It is: **at most 182 survive as recoveries, plus one wrap per
distinct foreign boundary — a number far below 330, because the same
foreign call is caught repeatedly on its way up.** Every other row in
Appendix A is a deletion with a name and a file path.

What that means per category, and where the work concentrates:

**boundary-translation (330) — collapse, don't relocate.** The clause already
turns a foreign throw into a domain value, so the rewrite is mechanical; the
discipline is that only the _lowest_ clause on a call path survives. Where
three tools each caught the same `fetch` rejection and re-wrapped it as a
`ToolError`, the ruling leaves one `Effect.tryPromise` at the fetch and
deletes the two above it. It concentrates in `packages/cli` (71: command
handlers writing to stderr and setting an exit code, and the
`doctor`/`models`/`resumeExecution` commands), `src/tools` (63: `ToolError`
wrapping in `delegation/`, `lean/`, `zotero/`, `web/`), the two GUI hosts
(`packages/extension` 44, `packages/desktop` 32, nearly all of them
`showLoggedErrorMessage` or `showErrorMessage` at a command boundary), and
`src/agent/workflowScript` (21, the realm boundary and the checkpoint
journal). Each lane reports its own collapse ratio in its PR body; a lane
that converts N clauses into N wraps has not followed the ruling.

**typed-recovery (182) — the only category that survives as code.** A typed
`E` with `catchTag`, or `Effect.retry` on a `Schedule` where the clause is
already a retry. These are the clauses whose category depends on reading the
branch inside the catch: the same `try` can rethrow on abort, retry on one
SDK code, and fall back on another. Concentrated in
`src/agent/modelHandlers` (26: media upload fallbacks, compaction retries,
`handleCreateResponseError` branches), `src/tools` (25: probe-and-default in
`setup/`, `github/` polling backoff, lease-lost repair in `delegation/`),
the extension host (16), `src/auth` (11: pending-sentinel returns in the
OAuth device flows), and `packages/cli` (13). Even here the count should
fall: a fallback that fires on _any_ failure is not a typed recovery, it is a
best-effort projection wearing a `try`.

**cleanup (124) — zero survive.** `Scope`, `acquireRelease`, and
`Effect.ensuring` run the release on success, failure, **and** interruption,
which the `try`/`finally` never did. Concentrated in `src/agent/runtime`
(25: lease release, resource dispose, and rollback in `childRunLoop`,
`executeAgent`, `resumeRun`, `SessionHandle`), `src/tools` (21:
`childStream` rollback, `leanSession` teardown, temp-file removal),
`packages/cli` (13), `packages/desktop` (12), and `src/transcript` (11:
staged-deletion rollback and writer close). Many of these hand-preserve
primary-error precedence, which is exactly the bookkeeping `Exit` and `Cause`
delete.

**best-effort-projection (206) — no silent survivor.** CLAUDE.md's rule is
that a fallback masking a failure must be loud or not exist, and 161 of the
tree's handlers are silent today. Under the ruling each of these becomes
either an explicit `Effect.ignoreLogged` / a forked effect with a warn-level
log, or nothing at all — and a lane may not convert a silent catch into a
silent `catchAll`, which is the same defect in new spelling. Concentrated in
`packages/desktop` (48: `reportAsyncError` and `reportBackgroundError` on
dialog and IPC promises, `desktopSupabaseAuth` notifications),
`packages/extension` (32: refresh rejections in `extension.ts`, `setup.ts`
registrations), `src/agent/runtime` (26: listener and hook fan-out in
`SessionHandle`, `HostInteractions`, `AgentRunLifecycle`), and `src/tools`
(20).

**control-flow (147) — deleted.** The bulk is ENOENT/ENOTDIR-means-absent on
filesystem probes and parse-or-default on JSON, URLs, and headers: an
`Option` or an `Either`, with no throw and no catch. Concentrated in
`packages/cli` (22) and `src/tools` (22), then `src/auth` (14),
`src/utils` (11: `baseFS`, `externalRoots`, `platformPaths`), and
`packages/extension` (11). The 23 Zod schema `.catch(default)` combinators
counted here are a separate matter: on persisted, security, accounting, or
lifecycle data a `.catch` turns corruption into a silent default, and if that
value feeds a later whole-file write it becomes permanent data loss. Those
are **defects to fix, not clauses to migrate** — ten of them sit on JWT and
session shapes in `src/auth`.

**failure-aggregation (52) — deleted.** `Cause` composition, or `Effect.all`
with mode `'either'` / `'validate'`; the manual failure arrays and
`throwAggregated` calls go with them. Concentrated in `src/agent/runtime`
(12: `runAgent`, `waitingTermination`, `HostInteractions` dispose),
`src/transcript` (10: `StagedDeletionCoordinator`, `TexraTranscriptRecorder`),
`packages/cli` (6, in `runExecution` and `subscribeApprovals`),
`src/agent/storage` (5), and `src/tools` (5).

**defect-suppression (18) — none migrate.** Each is fixed or allowed to die
in the defect channel; fifteen are silent. `packages/cli` (6:
`registerBuiltins` abort swallow, `imagePasteQueue`, `EntryErrorBoundary`,
`logSinks`, `runExecution` resumability at shutdown), `src/latex` (3:
`labelSearch` and two `LatexMediaManager` extraction swallows), `src/utils`
(3, all in `platformPaths` probe loops), and `packages/desktop` (2). This is
the short list to review before any further Effect code lands, because a
suppressed defect that survives the migration is a defect the defect channel
would have surfaced for free.

**Where to start.** The 18 defect-suppression clauses and the 23 Zod
`.catch` combinators are 41 rows that need a decision rather than a
conversion, and none of them depends on the migration's phase order. After
that, the highest-deletion-per-file areas are `src/agent/runtime` (cleanup 25

- aggregation 12) and `packages/desktop` (best-effort 48), neither of which
  has a lane yet.

## 4. Method and limits

**Finding clauses.** Candidates came from a text search, not the syntax tree
the PRD survey used. The pattern was `catch\s*[({]` or `\.catch\(` over every
`.ts` and `.tsx` file under `src/` and `packages/*/src/`, excluding
`*.test.*`, `*.vitest.*`, `__tests__/`, `src/test-kernel/`, harness scripts,
and `dist/`. That pattern matches `try/catch` clauses (with or without a
binding), promise `.catch(` handlers, Zod schema `.catch(` combinators, and
any comment line containing those characters. It is why this census counts
1059 rather than the PRD's 884: promise handlers and schema combinators are
in, and they are in on purpose, because the migration replaces `.catch(`
handlers with the same constructs as the clauses. Each grep hit was read in
context and either recorded as an entry or dismissed as a comment; section 4's
table reports both numbers per slice.

**Classifying.** The file list was split into ten slices of roughly 106
entries in path order (S1 opens at `packages/cli/src/bin/texra.ts` and S10
closes at `src/utils/text/xmlConversion.ts`). One agent per slice read every
hit and recorded file, line, kind (`try-catch` or `promise-catch`), the one
category from the P12 list, what the clause catches, what it does, and whether
it is silent. Zod schema `.catch(` hits were recorded with kind
`promise-catch` because no other kind existed; there are 23 such entries,
all under `control-flow` as one class (section 2), and the appendix names
each one as a schema combinator in its `catches` or `does` column. The
checker flagged one of them as not an exception clause; since its three
named siblings are structurally identical, all four keep the class rather
than one leaving it.

**Checking.** A second, independent agent re-read every fourth entry of each
slice with the same definitions and recorded agreement on the category alone.
The check also compared the entry count with the raw grep count for the slice
and listed any file the classifier had skipped. No slice skipped a file; every
count gap is explained by comment-line false positives, which the affected
rows note in place (S1: `chatSessionController.ts:444` and
`defineCliCommand.ts:34`; S8: `streamData.ts:63` and `PersistedState.ts:50`;
S9: `timeouts.ts:26`; S10: `StreamSummaryCacheStore.ts:78` and `:80`). One
comment-only hit, `MainViewStateRestoreController.ts:32`, was kept as an
entry and is labelled a false positive in its own row. Where the checker
disagreed and wrote down why, the reason is appended to the row's `does`
column in square brackets as `[checker: ...]`; the classifier's category is
kept so that the totals above are the classifier's, not a blend.

**What agreement below 0.8 means.** With every fourth entry checked, S8
(106 entries) has about 27 checks, so 0.815 is roughly five disagreements,
and S10 (71 entries) has about 18 checks, so 0.778 is roughly four. The disagreements the checker wrote up are
of one kind: a clause on the `typed-recovery` / `boundary-translation` border
(does a rethrow after tagging count as recovery?) or on the
`best-effort-projection` / `boundary-translation` border (is forwarding to
an `onError` callback a translation or a projection?). Those borders are
argued in the rows, not hidden, and none of them moves a clause into or out
of `defect-suppression`. The practical reading is that per-category counts
for `src/transcript` and `src/utils` (S10) and for `src/latex` and the first
half of `src/tools` (S8) should be treated as +-20 percent, and that an
implementer touching one of those areas should re-derive the category from
the P12 definitions before choosing the Effect construct, rather than trusting
the label. For the other eight slices the labels are good enough to size work
by.

**Other limits.** The census is a snapshot at `2884b49`; line numbers drift
with every commit and the file list is the durable part. The `silent` flag
records what the clause itself does, so a clause that returns a typed failure
the caller then logs is not silent even though nothing is written at that
line. Category is one per clause; a catch whose branches do two things
(rethrow on abort, fall back otherwise) was assigned the branch that is not
the rethrow, which is why so few entries are `cleanup` in the model handlers.
Nothing here measures how many of the 330 boundary translations would share
one adapter; that is Phase 1's service census, not this one.
