## 2. Core abstractions

1. **Session commit and the mutation line** (`session.ts:186-1336`, `transaction.ts:224-1145`). Owns every write. Invariant (spec §1 invariants 1-3, 7): one commit is atomic across entries, task records, submissions and documents; only adopted commits are observable; the line is held from callback through storage settlement and publication. What leaks: callers must order every table read before the first table write or get `ReadAfterWrite` (`transaction.ts:1081-1100`; spec §4 "Table rules"), must not await anything external inside a callback (§12 "Long transactions"), and must not call `snapshot()`/`getTask()` inside one or it hangs (§12 "Reads inside a commit"). Code that visibly works around the rule: `generation.ts:511, 807` ("Read before the first table write; only a failure uses it"), `scheduler.ts:390` ("Every table read before the first write"), `tool.ts:800-806`.
2. **Entries and derived context** (`types.ts` `EntryRecord`, spec §2 lines 139-150; `context.ts`). Owns the transcript. Invariant: entries immutable, IDs session-global and ordered; model context is a pure function of entries, heads and edits (spec §2.1, 10 steps). Leaks: entry kinds are strings by convention (`pi.user`, `pi.assistant`, `pi.system`, `pi.tool-result`, `pi.reset`, `pi.compaction` in `entries.ts:15-34`); `pi.` literals appear in 9 files; the "baseline system message" rule (spec §2.1 step 10) is known by `context.ts:185-221`, `prompt.ts` and `compaction.ts`.
3. **Task: durable phase state machine** (`types.ts:261` `TaskRuntime`, 35 members; spec §5.1). Owns one unit of recoverable work. Invariant: every transition is decided and written by one callback on the line (`scheduler.ts:252-256`); a checkpoint is replaced whole; a phase that returns without changing its checkpoint faults (`scheduler.ts:1810-1814`). Leaks: the 6-status `TaskState` union (`pending`, `running`, `waiting`, `sleeping`, `completing`, `terminal`; `types.ts:658-702`) is switched on in 8 files (`status ===` sites: scheduler 42, transaction 11, task-graph 8, live 6, tool 4, submissions 4, session 2, generation 2); `restarts` semantics are read by all three built-in tasks through `cutOffTooOften` (`live.ts:249-254`).
4. **Ownership tree, cascade and holds** (`scheduler.ts:230-256` comment, 766-874, 1924-1948; spec §5.5). Owns who may finish and who gets aborted. Invariants: abort flows down from durable intent; owned work holds its owner `completing`; the wait-for graph is acyclic (1946-1952). Leaks: the scheduler derives the tree from `TaskRecord.owner`/`background` and `ConversationRecord.owner`, so `transaction.ts:#validateOwners` (1015) re-checks the same rule at write time, and the `Transaction` exposes `stagedTasks()`/`stagedConversations()` (545-556) so the scheduler can build an `Overlay` (2470) of uncommitted candidates.
5. **Documents (Chord-tracked JSON)** (`documents.ts`, `transaction.ts:579-730`, spec §3). Owns mutable app state. Invariants: drafts revoked at callback settlement; every stored document is a state memory had; a `checkpointWhen` predicate decides base-vs-delta (`transaction.ts:997-1003`). Leaks: scope (`session`/`conversation`/`task`), `history` (`latest`/`rewindable`) and `fork` (`initial`/`current`/`asOf`) are persisted semantics a token must repeat exactly (`documents.ts:168-178` throws on mismatch); 8 helper exports are consumed by the session layer.
6. **`pi.live` document** (`live.ts:159-194`). Owns run control and presentation of the in-flight generation and tool round. Invariant: `run !== undefined` is "busy" (spec §6); a base is written whenever nothing runs (`live.ts:215-224`). Leaks: read or written in 6 files (`tx.doc(LiveDoc)` sites: generation 20, compaction 8, tool 5, live 3, submissions 1, harness 1) and mounted into every view (`view.ts:84-91`).
7. **Submissions and the inbox** (`submissions.ts`, `inbox.ts`, spec §6). Owns awaitable inputs. Invariant: `requestId` deduplicates per conversation (`transaction.ts:322`); boundaries place queued items deterministically by ID. Leaks: the lifecycle is written from four files (created `submissions.ts:252-317`; placed `inbox.ts:106,113`; settled `inbox.ts:101,175`, `live.ts:295,303`, `generation.ts:885`, `submissions.ts:158`).
8. **Registry, extensions and agent resolution** (`registry.ts`, `agent.ts:229-295`, `harness/types.ts:410-560`). Owns which tools, sections and hooks a conversation sees. Invariant: resolved once per phase from the committed `pi.agent` document and a registry snapshot (`scheduler.ts:2068-2076`); phases of one run may see different registries (spec lines 3150-3156). Leaks: the resolved `Agent` (10 fields) is handed whole to tool tasks (`tool.ts:329` picks `agent.tools` or `agent.callable`), to prompt rendering (`PromptInput.agent`) and to hooks; `pi.agent` stores names, so a selection edit `{ add, remove }` written to a child silently replaces an inherited array (§12 "Selection edits and copies").
9. **Storage contract** (`types.ts:1319-1419`, spec §10). Owns durability. Invariant: `commit(writes, adopt)` persists the batch atomically and calls `adopt(seq)` exactly once, synchronously, once durable and before its next commit (types.ts:1320-1327; conformance case `storage-conformance.ts:146`). Width: 16 methods (1 write, 1 `mintId`, 1 `close`, 13 reads: 5 cursor scans, 6 keyed lookups, 2 document reads); `StorageWrite` has 8 variants (`conversation`, `entry`, `task`, `submission`, `document.create`, `document.copy`, `document.change`, `document.retire`; types.ts:912-928). Documents are a delta log with caller-decided bases, not content-addressed (`store/commit.ts:318` passes `fingerprint: ""`). What leaks: every backend repeats the same validation (see §1), and the Session treats any storage throw as fatal, so backends must retry transient failures internally (spec lines 6026-6029).
10. **`ExecutionEnv` port** (`src/env/index.ts:212-377`). Owns the file/process world a tool sees; built per call by `HarnessOptions.env` from the conversation's `cwd` (`harness.ts:288-294`), so a rerun after recovery may see a different directory (§12 "Environment on recovery"). Width: 27 members plus 4 sub-port types. Leaks: nothing into the harness core (type imports only); tools reach it through `requireEnv` (`tools/env.ts:5-8`).

## 3. The loop

**Entry.** `Conversation.submit()` runs `admitSubmission` (`submissions.ts:226-320`): idle and empty inbox, it creates the `pi.live.run` and a `GenerationTask` in the same commit (`generation.ts:1140-1161`); busy, it appends an inbox item. The scheduler's commit observer sees the task row (`scheduler.ts:610-695`) and kicks a reservation pass.

**Reservation.** `#reserve` (`scheduler.ts:1452-1548`) is one commit on the line: for each candidate it checks waits, due time, cancellation above it, the restart limit (1496-1510), resolves and possibly migrates the definition (1572-1592) and writes `running`. Handlers then run off the line.

**Phases.** `#run` (1693-1718) loops: `#step` (1868-1903) opens a commit, re-reads the committed record from `#live`, applies `#decide` (1791-1830: abort mark, owner cancelled, uncaught error, handover, rule 6), and either returns the task to the loop or writes a fault; then the phase handler runs. A step that only continues makes no storage write (`session.ts:876-880` discards an empty transaction) but still takes a line pass.

**Generation** (`generation.ts:162-413`): `prepare` resolves agent and settings, derives the context (`runtime.context`), renders sections, plans `pi.system` deltas, checks compaction thresholds, and commits the request parameters as the `request` checkpoint (180-259). `request` first commits "clear leftover partial, set `generation.attempt`" (268-275), then streams (`streamResponse` 668-734) with partials committed deferred at most every `partialIntervalMs` (default 100 ms), then `classify` (736-834) in one commit: deferred poll, tool round, answer, overflow compaction, retry sleep, or failure. `retry` and `poll` are sleeping phases that re-sleep if run early (296-333). `tools` resumes after the `waiting` state and either starts the next sequential call (337-352) or `finishToolRound` (1042-1124), which creates the successor generation and hands over `pi.live.run` (1163). `finish`/`drain` run `afterRun` tasks.

**Tool** (`tool.ts:135-240`): `call` reads the call, validates, runs `beforeTool`, commits intent (`execute` checkpoint with final arguments and replay policy; 177-186), then executes (`run` 401-578) with the 23-member api, publishing output deferred, then `settle` (791-858) commits the result entry, slot, nested-call cleanup and the terminal outcome in one commit. `execute` is reached only by recovery (193-212).

**State.** Authoritative state is the committed rows: task records (status + whole checkpoint), `pi.live`, entries, submissions. In-memory state: the scheduler's `#live` mirror of every non-terminal task plus 18 further maps/sets (`scheduler.ts:280-350`), one volatile `Invocation` per running task (101-124: mode, `AbortController`, timers, watches), a per-conversation context cache (284), `PartialChanges` for the stream in flight. The code names the records as authoritative: "`#live` mirrors every committed non-terminal task record" (240-243); "Invocation mode is volatile and derived from the durable mark on reopen" (spec §5.4).

**Resume after a crash.** `open()` (`scheduler.ts:382-416`) scans the 5 live statuses, tracks every record, and rewrites each `running` task as `pending` with `restarts + 1` (400-404); `waiting`/`sleeping` stay; a reconcile pass then derives cascade marks and finalizes held outcomes (412-415, 766-820). Re-read: all live task rows; owner chains lazily (`#loadScopes` 876); context from entries (`context.ts:73-137`); `pi.live` on first access. Recomputed: abort marks below cancelled owners, `completing` finalization, blocked reasons, wake. Re-sent: nothing after a crash. A generation found with `restarts` set in `request` or `poll` treats the attempt as failed ("The host stopped while the model was answering"; `generation.ts:266-267, 319-321, 494-542`) and sleeps at `retry` or ends `interrupted`; a request a clean `close()` stopped is re-sent with the same pinned messages (spec §8.3), because close writes `pending` without a count (spec §5.1 lines 2254-2262). A tool in `execute` reruns only when stored and current replay policy are both `safe` (`tool.ts:193-205`), otherwise it writes an `interrupted` error result from the slot's partial output.

**Bounds.** Model retries: `attempt <= policy.maxRetries` (`generation.ts:798-805`, `DEFAULT_RETRY_POLICY` `agent.ts:20`); compaction uses the same policy (`compaction.ts:188-193`). Crash loops: `restartLimit` default 5 (`agent.ts:58`), checked by built-in phases via `cutOffTooOften` (`live.ts:249`) and by the scheduler for extension kinds (1496-1510). Turns: `maxTurns` at `finishToolRound` (spec §8.5). Spin: rule 6 faults a phase whose checkpoint did not change (1810-1814).

**The effect sandwich** (spec §5.2) sits in every phase handler: intent commit, effect, outcome commit. Cost in stored commits for one user turn with one tool call and a text answer: admit (1), reserve generation (1), `prepare` (1), `request` start (1), partials (deferred, folded into the next commit), classify + start round (1), reserve tool (1), tool intent (1), tool result (1), reserve generation from `waiting` (1), `finishToolRound` + successor (1), reserve successor (1), `prepare` (1), `request` start (1), answer (1): 15 storage transactions, each a full `Storage.commit` with synchronous adoption. Costs pushed to the author: split work at every effect so the post-effect part is its own phase (spec §5.6 "There is no sleep inside a phase"), make effects idempotent by a key stored in the intent (`spec.md:2211-2218`), return a changed checkpoint or fault, obey read-before-write inside callbacks, prefix memo names (§12), and never await the model inside a commit.

**Temporal decomposition.** (a) The submission lifecycle is split by when: admission in `submissions.ts`, placement in `inbox.ts`, settlement in `live.ts:290-318` and `generation.ts:882-895`. (b) The tool round is split by when across three files: start in `generation.ts:987-1040`, execution in `tool.ts`, finish in `generation.ts:1042-1124`, with slot bookkeeping in `live.ts:352-408` touched by all three. (c) Inside the scheduler the same predicate `#belowCancelled` is re-evaluated at four moments (reserve 1493, step 1802, observe 674 and 681, reconcile 808) because the cascade is applied in a later commit than the intent (`#reconcile` 766). (d) The generation's `prepare`/`request`/`retry`/`poll` split is a state machine, not a smell: each phase owns a durable checkpoint shape.

## 4. Durability and ownership

**Committed before shown.** `#runCommit` (`session.ts:849-946`): callback, `settleSuccess`, then `Storage.commit(writes, adopt)`; `adopt` runs `tx.adopt` and `#publish` (1060-1117) synchronously inside the storage's durable step, and only then do document watches, views, the scheduler and submission waiters see the commit. Host `observeCommits()` listeners run one microtask later (spec §4 lines 1856-1876). A throwing internal observer fails the session but the commit stands (938-944).

**Deferred commits** (spec §4.1; `session.ts:950-1058`, `transaction.ts:798-860,1222`). A commit marked `{ persistence: { kind: "deferred", withinMs } }` is held in memory only when every write is a change to an existing `latest`/`initial` conversation document; it is stored by the next normal commit that acquires that document (held ops go in front of its own, `takeHeld` 896), by the deadline timer (`#armHoldTimer` 1032), at close, or at unload. Only two writers use it: generation partials (`generation.ts:694-706`) and tool progress (`tool.ts:599-660`), both into `pi.live`; the invariant "every commit that consumes a streamed field reads `pi.live` and so stores it first" (spec §8.2) is maintained by hand in each consumer.

**Transaction boundaries.** One `Transaction` per commit; reads allowed only before the first table write; assembly (`transaction.ts:915-1013`) orders conversations and entries (pushed as written), submissions, tasks, document changes (checkpoint predicate last, 997-1003), then retirements; a terminal task retires its task-scoped documents by scanning storage inside assembly (937-962). `#validateOwners` (1015) rejects new owned work under a finishing owner.

**Who owns a conversation across processes.** Nobody durable. There is no ownership claim, lease, hostname, pid or liveness heartbeat anywhere in `src/` (the terms do not occur; the one "heartbeat" in the spec is the alarm cadence a Durable Object host arms for `wake()`, §5.6 line 2787). The spec's unit is "a Session owns one mutation line" (§1 line 50); ownership in the records (`ConversationRecord.owner`, `TaskRecord.owner`) is task attribution inside one session (spec §2 lines 283-290: "not an access-control capability"). A second process that opens the same storage runs `open()` and rewrites every `running` task as `pending` with `restarts + 1` (`scheduler.ts:400-404`), then reserves and runs those phases itself while the first process keeps its invocations: two writers, each charging the other's in-flight generation as a failed attempt. The only multi-opener provision is `HarnessOptions.readOnly` (`scheduler.ts:226-233, 347-349`, `session.ts:881-886`; spec lines 833-840 call it a viewer "of a session another process drives"), which loads live tasks as committed and refuses every commit. §13 lists "CRDT/offline multi-writer merge" as a non-goal, and the spec tells backends not to add "a second caller-facing commit mutex" (lines 5972-5973). At the storage level a second writer is not detected: SQLite serializes commits with `BEGIN IMMEDIATE` in WAL mode (`chord/src/sqlite/node.ts:157-176, 201-209`), but `mintId` is a per-process in-memory counter (`sqlite/storage.ts:214-218`), so a colliding conversation, entry or document ID fails the commit fatally in `checkGlobalIds` (670-691) while task and submission rows are upserts that silently overwrite (822-848); JSONL loads its state once at open (`jsonl/storage.ts:247, 274`) and never sees another writer. `StoreStorage` refuses a second opener on the same owner name, but only within one process (`store/storage.ts:111-115`). The README states the rule as a contract: "One process owns a storage at a time; there is no cross-process locking" (`README.md:881`), IndexedDB users must "use a Web Lock around its lifetime" (860-861), and "every process that opens one storage must use the same clock" (164). The test suite pins the second-opener behavior rather than preventing it (`test/harness-read-only.test.ts:127-142`); the only exclusivity test is in-process (`test/store-storage.test.ts:122`).

**Storage contract width.** `Storage` (`types.ts:1319-1419`): 16 methods (`commit`, `mintId`, `conversation`, `scanConversations`, `entry` x2 overloads, `findLatestHeadMarker`, `scanEntries`, `task`, `scanTasks`, `submission`, `scanSubmissions`, `submissionByRequest`, `findDocument`, `document`, `scanDocuments`, `close`); no `open` (each backend has its own static opener). `StorageWrite` has 8 variants. Record types: `ConversationRecord` 3 fields (types.ts:427), `EntryRecord` 8 (458), `TaskRecord` 15 base fields + `state` + `memos` (705-764), `SubmissionRecord` 10 fields over 10 type x status variants (496-599), `DocumentRecord` 8 (767), `StoredDocument` 4 (903). Seq strictly increases with gaps; all record kinds share one numeric ID namespace (spec lines 5911-5926). Failure model: any throw from `commit`, a read or `mintId` fails the session (`GuardedStorage` `session.ts:1511-1673`; spec §10.1), except `StorageRequestError` on an invalid read and an aborted read context (session.ts:1658-1660); JSONL adds a "poisoned" state after an uncertain append (`jsonl/storage.ts:839-847`) and defaults `fsync` off (77-80).

## 5. Extension model

**The unit is the extension** (`harness/types.ts:410-419`, 6 members: `name`, `tools?`, `sections?`, `hooks?`, `wraps?`, `tasks?`), an immutable in-process bundle; the registry is not persisted (spec lines 3022-3024). `Registry.install` replaces by name in place or appends (`registry.ts:73-80`) and validates names, section keys (`^[a-z][a-z0-9_-]*$`), the reserved `instructions` key and global task-name uniqueness (99-106); the three built-in tasks are always present and are not an extension (`registry.ts:10`). The seven helpers in `define.ts:16-62` are validation-free constructors: `defineExtension` and `defineTool` are identity functions; `section`, `hook`, `runEndTask`, `wrapTool`, `wrapSection` return literals, and `hook` binds to a task _name_ so hooks survive a task reload.

**Interfaces an author writes against** (member counts from `harness/types.ts`): `ToolRegistration` 12 members, 4 required (`name`, `description`, `parameters`, `execute`; 338-378); `ToolExecutionApi` 23 (247-332: 20 own, including `output`, `outputWindow`, `retainedOutput`, `diagnostic`, `details`, `commit`, `memo`, `createTask`, `executeTool`, plus `snapshot`/`snapshotAsOf`/`watchDoc`); `ToolExecutionResult` 7 optional fields (196-212); `ToolControl` 3 (`addTools`, `terminate`, `handoff`; 174-183); `HookApi` 8 (943-961); `PromptSection` 3 (394); `PromptInput` 5 (381); `Agent` 10 (499); `AgentState` 8 (450); `HarnessSettings`/`Settings` 12 (602, 648); `HarnessOptions` 12, 2 required (`models`, `registry`; 673-737); `Conversation` 13 (793-863); `RegistrySnapshot` 6 (422). One tool needs 4 types: `ToolRegistration`, `Extension`, `Registry` (passed as `HarnessOptions.registry`), and `ToolExecutionResult`; `ToolExecutionApi` may be ignored. There is no hook-name union; the effective set is 8 names, each with a fixed composition rule (spec lines 3288-3297): `beforeRequest` (replacement chain), `afterResponse`, `afterTools`, `afterRun` (observers), `onYield`, `beforeCompact` (first decision wins), `beforeTool` (argument replacement, first block wins), `afterTool` (result chain); call sites `generation.ts:279,360,770,838,1061`, `tool.ts:161,679,744`, `compaction.ts:141`. The vocabulary is open: any `defineTask<I,S,R,H>` declares its own hook record `H` (`types.ts:386`). Hooks run off the line, before the consuming commit, so a crash reruns them (spec lines 3285-3286); they share the task's memo namespace (spec §12).

**Agent resolution** is not the registry's job: `resolveAgent(state, snapshot, settings, report)` (`agent.ts:229-292`) reads the conversation's `pi.agent` document (`AgentDoc` 44-52: rewindable, fork `asOf`, names only), selects extensions (stored array exactly, else settings or install order plus `add` minus `remove`; 323-342), merges tools and sections later-wins-by-name (238-243), applies wrappers (a throw or rename deletes the target; 344-361), filters (`tools`, `callers`, `modelTools`; 267-320) and appends `instructions` last. It is memoized once per phase (`scheduler.ts:2067-2077`); the model comes only from `pi.agent` with no settings default (280).

**System prompt**: no durable sections; the positional `pi.system` entries are the only record of what the model saw (spec lines 4140-4168). Each `prepare` replays the transcript's system messages (`prompt.ts:9-19`), re-renders every section in agent order with no cache (25-48), and appends one entry only when the diff is non-empty (`planSystemEntries` 66-93; order-only change writes remove-all then re-add-all, 122-142); tool changes ride on the last planned entry (90-92).

**Code mode** is an ordinary extension tool, not a task kind: `createCodemodeExtension({ sandbox })` (`codemode/codemode.ts:255-272`) registers tool `codemode` (`callers: ["model"]`, `replay: "safe"`, 4 MiB / 100k-line limits, a Lark grammar for constrained sampling; 231-250), two hidden model tools `pi.codemode.models.*` (`models.ts:253-287`, at most 4 concurrent) and a `codemode` prompt section listing callable tools as TypeScript declarations within ~3,000 tokens. The sandbox is QuickJS (quickjs-wasi) in a `node:worker_threads` worker or a Durable Object (`packages/codemode/src/runtime/vm.ts:38`, `host.ts:33-88`, `remote.ts:273`); scripts get no timers, fetch, process or require. Each `tools.<name>(args)` becomes `api.executeTool(name, args, ctx, { key: "c<id>" })` (`codemode.ts:838`), which commits a `pi.tool.madeNestedCalls` memo then creates a nested `pi.tool` task, its `NestedCallDoc` member and a `pi.live.nestedTools` slot in one commit (`tool.ts:883-947`); the result is read back from `NestedCallDoc` (528-533) and never enters the transcript. Three documents hold run state: `pi.codemode.run` and `pi.codemode.journal` (task-scoped) and `pi.codemode.store` (conversation, rewindable, `asOf`); a rerun returns the stored result or replays the journal and refuses on a changed module version, VM fingerprint, passed deadline or divergence (spec lines 4398-4423). `src/harness` never imports `src/codemode`; code mode reaches into harness internals the other way (`NestedCallDoc`, `ToolTaskInput`; `codemode.ts:54, 786`).

**`ExecutionEnv`** (`env/index.ts:377`, `FileSystem` 212-288 + `Shell` 362-375): 27 members (25 methods, 2 properties, only `listFiles` optional), with sub-ports `BinaryReader` 4, `TextLineReader` 2, `DirReader` 2, `FileWatcher` 2; Node implementation `NodeExecutionEnv` (`env/node.ts:612`). Tools `read`, `write`, `edit`, `bash`, `powershell` (`tools/*.ts`) ship as extension `coding-tools` (`tools/index.ts:31-39`); none sets `replay`, so all are unsafe and are not rerun after a crash. The harness core imports only types from `src/env` (`ExecutionEnv`, `ShellOutputSkip`, `ShellOutputWindow`) and nothing from `src/tools`, `src/codemode`, `src/tool-search` or `src/images`; it contains no comparison against a tool name and no file or shell concept.

**What the kernel knows about the application's vocabulary.** The scheduler knows no task kinds and receives `settleOutcome`, `limitsRestarts`, `withdrawInputs` and `conversation` as callbacks (`scheduler.ts:191-256`; `harness.ts:232-250`). The Harness layer hardcodes three built-in kinds (`live.ts:238-246`), refuses to open a registry that lacks them (`harness.ts:581-587`), reserves the `pi.` prefix by convention only (`generation.ts:911`, `submissions.ts:207-209`; §12), and `settleSchedulerOutcome` (`live.ts:410-451`) branches on those kinds inside the scheduler's finalize commit (`scheduler.ts:862-864`). Entry kinds leak little: only 3 sites branch on an entry kind, all `SystemEntry.is` (`context.ts:188`, `prompt.ts:73,75`); the 61 `kind`/`type` discriminations in `src/harness` are on pi-ai content blocks (16), `ToolTaskInput.kind` (12, all in `tool.ts`), submission draft types (11) and Chord change kinds (11).

**Documents for app state.** `defineDoc`/`defineDocFamily` (`documents.ts:39-80`, 4 overloads each) return `{ definition }` with 8 fields (`kind`, `version`, `initial`, `migrate?`, `checkpointWhen`, `scope`, `history`, `fork`; `types.ts:57-89`; a family adds `family: true` and a seeded `initial`). Scopes: `session` (survives reopen), `conversation` (declares `history` latest|rewindable and `fork` initial|current|asOf), `task` (retires with the task, never forked). Writes happen only through a revocable draft from `tx.doc(token, ownerId[, key])` inside a commit (`transaction.ts:579-623`); the draft rejects once the callback settles, values must be strict JSON, and there is no authorization beyond holding the token (spec §3.4). Migration is lazy: a read migrates in memory, the first `tx.doc()` writes a current-version base (spec lines 1732-1765). Fork rules (§3.7): `asOf` copies the parent value at the fork entry's commit, `current` copies at fork time, `initial` copies nothing; a fork commit may not also write a parent's `current` document. Built-in documents: `pi.agent`, `pi.live`, `pi.inbox`, `pi.provider`, `pi.usage` (conversation-scoped) and the task-scoped family `pi.tool.nested-call`; code mode adds three.

## 8. Ideas worth evaluating for a durable Effect harness

1. **Deferred (held) commits for streamed progress.** A commit that only changes a presentation document may be adopted in memory, shown to watchers, and stored later: by the next normal commit that touches the document, by a deadline, or at close. Files: `session.ts:950-1058` (`#hold`, `#storeHolds`, `#armHoldTimer`), `transaction.ts:798-860, 1222-1241` (`holdable`, `takeHeld`, `storeHeld`), spec §4.1. Shape (illustrative): `commit(change, { persistence: { kind: "deferred", withinMs: 1000 } })`; held ops are prepended to the next stored delta of that document. In a row-log harness it would replace per-chunk progress rows with an in-memory projection flushed at the next real row or deadline. Risk from pi's history: the invariant "every consumer of a streamed field must read the document in its commit so the hold is stored first" (spec §8.2) is unenforced and maintained by hand in each consumer; the feature arrived unreleased (`CHANGELOG.md:106-107`) as the fix for persisting progress every 100 ms (`:299`), trading "a crash now loses up to about a second of streamed content instead of 100 ms" for "about 5.7x fewer storage transactions and 2.9x fewer disk writes with 32 streams over SQLite" (`:15`), and a commit observer that runs inside `adopt` "must only record it: no awaits, no Session calls, no throws" (`:107`).
2. **Restart counting with a close-versus-crash distinction.** Open rewrites `running` rows as `pending` with `restarts + 1` (`scheduler.ts:400-404`); a clean close writes them back without a count (spec §5.1 lines 2254-2262); any state change clears the count (`#commitState` 1938-1941); at `restartLimit` (default 5) a built-in task ends visibly with a `restart_limit` result (`live.ts:249-273`, `generation.ts:544-565`), and a generation found mid-request after a crash charges the attempt instead of resending (`generation.ts:266-267, 319-321, 494-542`). Shape: a `restarts` column on the run row plus one branch in the resume handler. In a one-program-per-run harness this replaces an unbounded "resume re-sends the request" loop with a bounded one and gives a crash-loop signal (`task_interrupted` report). Risk: every task running when the process died is counted, so a long innocent stream next to the culprit can end too (spec §5.4 lines 2516-2519); pi changed its mind twice in 20 days: 1.4.0 "parked" a task at the limit with a `retryTask()` to release it (`CHANGELOG.md:152, :163`), the unreleased version ends it visibly instead (`:83`), and "a request in flight at a crash was resent on open" became "charged as a failed attempt" (`:84`).
3. **Durable sleep with a host `wake()` contract.** A phase commits `{ status: "sleeping", until }` and the invocation ends; `wake()` returns `{ active, at }` from memory so an evictable host arms one alarm (spec §5.6; `scheduler.ts:462-505, 1349-1373, 2547-2553`). Shape: `sleepUntil(until, checkpoint)` resolving when stored, not when due; phases that wake early re-sleep (`generation.ts:296-300`). Replaces in-memory retry timers in a retry loop so backoff survives restart and eviction. Risk: every sleeper must re-check the clock (a replacement host's clock may be behind, `generation.ts:319-323`), and without `onWake` the scheduler keeps a Node process alive for the earliest sleep. History: 1.4.0 removed the in-phase `TaskRuntime.sleep()` for `sleepUntil` (`CHANGELOG.md:148`), needed a SQLite schema v2 "that cannot be rolled back" for the `sleeping` status (`:150`), and had to stop arming eviction timers on Durable Objects because a pending timer kept the object from hibernating (`:181`).
4. **Ownership tree with `completing` holds and bottom-up abort.** Every task names an owner; a terminal outcome is stored as `completing` while owned work is live and finalized in a later commit; abort marks are derived from durable intent by a reconcile pass, so a crash between intent and cascade loses nothing (`scheduler.ts:766-874, 1924-1948`; spec §5.5). Shape: `owner` on the run row; `finalize` as a worklist over `completing` rows (`#finalize` 840-874). For a harness with child or peer runs this replaces ad-hoc cancellation of children. Risk: this is where pi's complexity concentrates: 19 index structures (280-350), overlay bookkeeping (2470), lazy chain loading (876-930), and the performance history the changelog records without naming the complexity class: "The scheduler no longer visits every live task on each pass: a chain of 500 owned tasks that took 12 s to settle takes 50 ms, 20,000 take 1.5 s" (`CHANGELOG.md:236`) and "ownership indexes are bounded by live work ... a queued input no longer makes the scheduler scan every queued submission" (`:237`), both in 1.2.0, eleven days after 1.0.0. The spec pins the resulting rules in 230 lines (§5.4-5.5), and `test/harness-structured.test.ts` (1937 lines) and `harness-ownership.test.ts` (1378) exist to hold them.
5. **Rule 6 and definition handover.** After each phase the scheduler compares the committed checkpoint with the previous one and faults the task if nothing changed (`scheduler.ts:1810-1814`); at every boundary it re-resolves the definition and hands the task back to `pending` if a newer compatible definition exists (1816-1829; spec §5.4 "hands over"). Shape: JSON-equal check on the checkpoint in the step commit; `migrate(input, checkpoint, fromVersion)` on the definition. Replaces manual version gates in a loop that resumes stored runs across deploys. Risk: pi had to exempt memos and document writes from "progress" (1938-1941), version-bumps every built-in task on checkpoint shape changes (`pi.tool` is at 3, `pi.live` at 3), and renamed the outdated-definition reason once already (`incompatible_task`, `CHANGELOG.md:88`).
6. **`requestId` admission and stale-head writes.** A submission carries an optional `requestId` deduplicated per conversation before any write (spec §6; `transaction.ts:322-328`), and a head-moving write older than the active range is settled `unanswered: stale` rather than applied (`inbox.ts:155-158`; spec §6 lines 2940-2960). Shape: `submit({ requestId })` returns the existing record; `isStale(boundary, entry)`. Replaces client-side retry guards and makes concurrent compactions order themselves by cut position. Risk: dedup is per conversation and per type only; reusing an ID across types rejects (spec §6 line 2888); the README's own recovery story depends on it ("reopen and resubmit with the same `requestId`", `README.md:914`), and the Durable Object test pins it across an eviction mid-stream (`test-workers/wake.test.ts:62-79`).

## 9. What pi-durable deliberately does not do

Non-goals (spec §13, lines 6390-6406): no whole-Session DOM; no visible-but-undurable publication beyond deferred commits; no kernel event journal or separately maintained event state; no session-scoped rewindable documents; no automatic checkpoint heuristic; no automatic third-party view mounting; no CRDT or offline multi-writer merge; no SQL translation of arbitrary Chord operations; no JSONL global compaction or corruption repair; no compatibility layer for earlier prototypes; no forced termination of non-cooperative extension code in-process.

Footguns (spec §12, lines 6216-6388) are stated as contracts "not invitations to add defensive machinery". The 46 bullets group as: transaction discipline (detached draft work, read after write, admission inside a commit, long transactions, reads inside a commit); run control (writing to a busy conversation, queued items after a failed run, busy after the answer, after-run tasks waiting on their own run, missing after-run tasks, fix loops, submissions from after-run tasks); compaction (spend per attempt, heads and edits lost during compaction, summary timestamps, raw head writes into the past); ownership (owned work holds its owner, work created by hooks, compensation and hooks in abort handlers, double-counted subagent spend); documents (explicit creation, family initialization, checkpoint starvation, wrong fork setting, schema stability, trusted immutable revisions, watch activation, buffered watches, watch stop, durable progress cadence, large terminal results); extensions (hook memo names, reserved `pi.` names, early resource disposal, guards left out of a selection, selection edits and copies, copies are one-time, environment on recovery, moving default selections, unstable prompt text); lifecycle (non-cooperative code at close, objects outliving the Harness, fatal storage errors, JSONL durability).
