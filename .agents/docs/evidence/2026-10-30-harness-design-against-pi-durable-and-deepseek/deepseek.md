## 2. Cordis as the composition model

**The plugin contract.** A plugin is one of three shapes sharing `Plugin.Base` (vendor/cordis/src/registry.ts:92-133): a function `(ctx, config)`, a class `new (ctx, config)`, or an object with `apply(ctx, config)`; `RegistryService.resolve` reduces all three to one callback key (222-228). `Base` has 5 optional members: `name`, `Config` (Standard Schema, validated synchronously only; fiber.ts:50-62 carries "TODO: async validation"), `inject`, `provide`, `intercept` (100-111); `Plugin.Transform` adds 2 (113-118). A `Service` subclass (vendor/cordis/src/service.ts:11-102) adds 9 hooks: `[Service.init]`, `check`, `config`, `invoke`, `extend`, `tracker`, `resolveConfig`, `[symbols.filter]`, static `provide`; plus `Config.merge` and the `@Inject` decorator (registry.ts:37-55). An author can touch 17 named members; the kernel services use 4 (`name` via `super(ctx, name)`, `static inject`, `static Config`, `[Service.init]`; agent-loop/src/index.ts:292-329, agent/src/index.ts:253, 297).

**Reversible effects, mechanically.** `fiber.effect(execute, label)` (vendor/cordis/src/fiber.ts:424-567): refuses while the fiber is `UNLOADING` (425-428), pushes an owner-visible wrapper into `fiber._disposables` before the body runs (526), accepts a disposer, a promise of one, or a sync/async iterable yielding disposers (372-404), moves each collected disposer into the effect's own list (454-456), and on dispose runs them in reverse, chaining async ones (437-447); a synchronous throw rolls back and rethrows (529-543). Fiber unload waits until no dependent retains its provisions (712-718) and then runs `Promise.all` over `_disposables.clear()` (720-730): fiber-level disposers start concurrently, so the "reverse registration order" promise (fiber.ts:71-72) holds only inside one effect. Every kernel registration returns such a disposer: `ctx.tools.register()` (tools/src/index.ts:148-152 through `ScopedLayers.effect`, scope/src/store.ts:226-262), `ctx.agents.setFactory()` (agent-loop/src/index.ts:336), `registerMessageProjection()` (session/src/index.ts:1081-1089). Ordered teardown is expressed by yielding exact disposer identities from a generator effect (agent-loop/src/index.ts:572-595); the JSDoc at docs/subsystems/core.md:790-798 warns that yielding a wrapper breaks the order. The local V6 hardening of fiber.ts closed three reentrant-disposal gaps in this mechanism (vendor/README.md:86).

**Services on ctx.** `Context` is a Proxy over `ReflectService` (vendor/cordis/src/context.ts:74; reflect.ts:143-219): a get walks the fiber chain for a provision under the isolation label (reflect.ts:163-179) and throws `cannot get required service ... without inject` (152, 173). `provide(name, value)` is itself an effect; a second provider for one label throws (291-307) and `notify` re-evaluates every fiber that injects the name (335-354). Keys are typed by declaration merging into `interface Context` (session/src/index.ts:39-41; tools/src/index.ts:32-36; agent-loop/src/index.ts:176-188). Optional seams are read with `ctx.get('approval')` (tools/src/pipeline.ts:436) or `ctx.get('sessionPersistence')` (agent-loop/src/index.ts:689): a missing provider is a runtime `undefined`, not a type error. Load order is emergent from `inject`: the epoch string `revision:implUid:...` changes when a provider's uid changes and drives reload/unload (fiber.ts:617-646); "Row order carries no load semantics" (packages/bundle/base/cordis.patch.yml:12-13).

**Dispatch modes.** Five (vendor/cordis/src/events.ts:31): `parallel` (allSettled, AggregateError, 191-196), `emit` (sync loop, 203-206), `serial` (await until bailed, 214-220), `bail` (228-234), `waterfall` (246-261): `next` is popped from the args, calls the next listener or the inner default, and throws on a second call (248-257). Listener filtering reads `thisArg[Context.filter]` (168-170), which is what scope carriers exploit.

**Scoped registration.** `createScope(ctx, key)` (core/scope/src/index.ts:137-148) mounts a no-op child plugin (121, 139) and returns `fiber.ctx.extend({ [kScope]: key })`; the loop mints one per agent with the live `Agent` object as key (agent-loop/src/agent.ts:147-148) and exposes it as `agent.ctx`. `ScopedLayers.effect(ctx, action)` reads `scopeOf(ctx)`: `undefined` goes to the eager global layer, anything else to a lazily created per-key layer whose undo deletes it when empty (scope/src/store.ts:231-262). `view()` merges global then chain, nearest last (tools/src/index.ts:199-227). `scopeTarget(base, key)` (scope/src/index.ts:170-189) builds a carrier whose filter admits untagged listeners and tagged listeners whose tag is the key or an ancestor, so events flow up the agent chain only; dispatch must pass the carrier (agent/src/dispatch.ts:95-150; pipeline.ts:198-200).

**Profiles, bundles, patches.** The composed tree is one root `cordis:include` row with ordered patch lists (boot/app-boot/src/index.ts:770-780): bundle layers in `dsh.profile.bundles` order, the profile's `cordis.patch.yml`, the home patch, `--patch` overlays, then an appended telemetry-disable patch (app-boot/src/profile-context.ts:74-84). `applyEntryPatches` (vendor/include/src/index.ts:57-127) clones, indexes ids through groups, appends `insert`s and indexes them (79-101), warns and skips an unknown id (109-113), then assigns every remaining key over the row (120-123): `config` is replaced whole, never merged (also base/cordis.patch.yml:6-10). dsh-base is 97 rows in one `insert` (base/cordis.patch.yml:15-534); sdk-minimal is 37 rows restating about 20 base rows by name (sdk-minimal/cordis.patch.yml:5-179, 95-96). A per-session service needs an `isolate` realm (`true` = local symbol, string = shared label; vendor/loader/src/config/isolate.ts:8, 49-68). The documented `preset` patch form (docs/architecture.md:25) has no handler in include, loader or app-boot; a preset row's `config.plugins` is replaced whole like any row (bundle/web-app/presets/cordis.patch.yml:1-3).

**HMR and reload.** Two module-replacement implementations exist, the vendored one (vendor/hmr/src/index.ts, 427 lines) and dsh's (boot/hmr/src/index.ts, 1,133 of 1,737 lines, `partialReload` 580-746); profiles use dsh's. A code reload evicts module caches, re-imports, `registry.delete(plugin)` disposes every fiber of that runtime, then re-plugins with the previous raw config (642-701; vendor/cordis/src/registry.ts:258-267); failure rolls caches back (717-737). Agents are scope fibers under the agent-loop fiber, so stopping it runs `FactoryOwnership.dispose`: every live agent is cancelled with `{ kind: 'disposed' }` and awaited (agent-loop/src/index.ts:95-108, 518); the running turn aborts and `turn/end` records `aborted` (agent.ts:196, 404-407). Recovery is an ordinary resume over the log: a configured agent with a stable `sessionId` resumes on remount (agent-loop/src/index.ts:263, 351); nothing claims automatic resume for SDK-created agents. A config-only change on an active fiber is `volatileOnly` when only volatile fields differ (vendor/loader/src/config/entry.ts:146-151) and commits references without remount (167-199); any other change goes through `fiber.update` and a restart (155-156; fiber.ts:768-819). Loader mutations are "eager, non-transactional" and "plugin activation failures can leave a partially applied tree" (vendor/README.md:88). Headless, SDK and ACP disable HMR (docs/architecture.md:27).

**Cost of one change.** Add one tool: the `tool-todo` package is 20 files (package.json, tsconfig, 3 src files, 8 locale JSONs, 3 README variants, 4 tests); outside it a base row (base/cordis.patch.yml:436-439) and dependency, `apps/cli/package.json:86`, web-app patch + package.json + 3 preset YAMLs, `tsconfig.host.json` and generated `tsconfig.base.json`, `python/sdk-runtime/package.json`, five regenerated docs (tool-catalog, config-catalog, event-producer-consumer, module-graph, dependency-catalog) and, because `todo/write` is persisted, persistence-catalog.md, persistence-schema.json and a `persistence-changes --record` pair (docs/cookbook/reviewing-persistence-type-changes.md:72-80); 130 snapshot files mention `todo_write`. The 81-line `timeout-policy` guard still touches about 29 files. Add one event: a `declare module` merge with an `@mode` JSDoc tag (tools/src/events.ts:6-18), the owning page's generated region, and `gen-doc-graphs`, which fails on an event with no dispatcher (scripts/gen-doc-graphs.ts:1572-1604); 101 `@mode` tags exist; no check compares the dispatch site's mode with the tag. Add one provider: a plugin with `inject = ['llm']` calling `ctx.llm.registerAdapter([...], adapter)` and 7 protocol obligations (docs/cookbook/adding-an-llm-adapter.md:9-35) plus the package checklist and a bundle row. Add one durable event type: no format bump (docs/cookbook/adding-a-session-format-version.md:23), one declaration merge, a recorded change. The recurring price is that every cross-cutting fact is a declaration merge plus a generated catalog: 88 events (docs/event-producer-consumer.md:13-100), 33 `SessionEventMap` merge files, 62 catalogued durable types.

## 3. The loop

Files: `core/agent-loop/src/agent.ts` (745 lines, class `ReactLoopAgent`), `index.ts` (838, the `AgentLoop` service: factory, create/resume, lifecycle transaction), `inbox.ts` (232), `runtime-context.ts` (169), `assistant-stream.ts` (140). Six source files, 2,130 lines; 14,860 test lines.

**Shape.** One driver per agent: `wakeDriver()` (agent.ts:230-251) starts `kick()` (268-281), which runs `while (await this.turn()) {}`. `turn()` (327-433, 107 lines) appends `turn/start`, loops over `preStep()` (283-317) and `step()` (435-610, 176 lines), appends `turn/end` in a `finally` (420-425), and returns true only when the inbox still has pending work (427-432). `step()` holds the retry loop (`while (true)`, 444) around `prepareRequest()` (613-653), `buildRequest()` (656-744), the stream (490-498), settlement (505-583) and `ctx.tools.execute()` (590-593). The flow in docs/architecture.md:83-104 matches the code.

**State.** Authoritative state is the session log; derived model history is `session.deriveMessages()` (session/src/index.ts:999-1020), frozen per request at agent.ts:728-734. The driver keeps four in-memory facts beside the log: `phase` (53-61: idle | maintenance | running with turn/step counters and an AbortController), `requestHeaderLogged` (126), `requestSurfaceGeneration` (128) and the assistant-stream revision counters (131-132). `phase.turn` is seeded from the `turnBoundary` projection at construction (index.ts:567) and then counted in memory (agent.ts:334, 340), so the projection (agent/src/index.ts:306-308) and the counter are two owners of "current turn" during a run. Model selection and the inbox are durable projections read through `ProjectionHandle.readerFor(session)` (index.ts:568-571; inbox.ts:26-64 is the pure `apply`).

**Inbox and claim.** Two durable lists (`next-turn`, `next-step`); `agent/inbox/spliced` and `model/selection` are session events declared by core/agent (agent/src/types.ts:110-121). Every mutation is one `agent/inbox/spliced` append (inbox.ts:215-223) followed by live `agent/inbox/inserted|discarded` emits (224-229); `claim()` (108-113) removes all `next-step` input plus one `next-turn` message through non-discarding splices and emits `agent/inbox/claimed`. `send(message, target, wakeup)` (agent.ts:170-177) is the one entry; `followup/steer/inject` are three one-line presets (179-189). A wake during maintenance or after an abort is latched (`wakeRequested`, 230-240) and replayed at convergence (216, 278).

**Pre-step.** `preStep()` claims the batch, reads `model.current()` (288), resolves the step tool set (`tools.resolve`, 292), assembles the prompt (294), then runs the `agent/pre-step` waterfall whose default returns `enter` with the claimed messages plus a runtime-context user message (296-306). Rejection closes the turn as `blocked` (348-351); an empty first enter closes it as `completed` with no step (356-359).

**Request build.** `prepareRequest()` seeds the config from the last logged header (`requestProposal`, 78-84, 624-629), runs the deprecated `agent/request` waterfall (630-633; listed as "undeclared" in docs/event-producer-consumer.md:108), refuses a route change (635-640), then `llm.prepareCall()` binds the adapter (644). `buildRequest()` logs `request/header` with reason initial/resume/change/series (675-691), a `developer/message` for tool additions and removals (692-706), `request/context` on route change (717-723), freezes the derived messages (727-734) and returns the `GenerateOptions` with the turn signal (735-742). The system prompt is reconciled by a separate projection (`SystemPromptProjection.project`, runtime-context.ts:93-117) that emits `system/message` replace/append commits (agent.ts:453-461); user messages are appended once per step on the first attempt (463-477).

**Streaming and settlement.** `AssistantStreamAttempt` (assistant-stream.ts:18-140) accumulates timed chunks and emits `agent/assistant-stream` frames (agent.ts:480-487). Success commits `assistant/message` with the embedded stream and usage (574-583); a failure or abort commits `assistant/attempt` (521-531, 544-547) or an `interrupted: true` message when text was delivered (505-519). The end frame carries the committed seq (`live.settle`), so the UI's live stream and the durable record are the same bytes (docs/architecture.md:124).

**Retries.** The loop itself has no attempt bound: after `assistant/attempt` it runs the `agent/request-error` waterfall (548-558) and `continue`s only when a listener returns `{ kind: 'retry' }` (560-563). Bounds live in listeners: `llm-retry` (5 retries, 500 ms to 10 s backoff, codes EMPTY_RESPONSE/RATE_LIMIT/SERVER/TIMEOUT/TRANSPORT, llm/retry-policy.ts:14-24; count kept in a durable `llmRetry` projection reset on `step/start`, llm-retry/src/index.ts:122-135, 216-220), `compaction-basic` (context overflow, its own in-memory `overflowRetries` WeakMap, compaction-basic/src/index.ts:213-241) and `compaction-image-offload` (unbounded, "spends no retry budget", index.ts:27-32) all listen (docs/event-producer-consumer.md:116); the first that returns without `next()` owns recovery. Retries do not repeat assembly or pre-step (docs/architecture.md:112); they re-run `prepareRequest` and `refreshContext` (445-450). The DeepSeek adapter additionally re-issues one HTTP request on a stale file id inside one `stream()` call (llm-deepseek/src/request-files.ts:135-142).

**Tool batch.** `tools.execute({ calls, signal, agent, log: { turn, step }, maxParallelToolCalls, toolSet })` (590-593); the executor appends `tool/call` and `tool/result` itself (tools/src/batch.ts:243-265). `additionalContexts` from tools are spliced into `next-step` (594-596), which is how a tool injects a follow-up user message; `concludesTurn` ends the turn (597). A failed batch throws `ToolBatchExecutionError` with partial results (598-603); the turn-level `catch` then appends synthetic error `tool/result`s for calls still pending (`ToolCallRecovery`, agent.ts:363-385; session/src/repair.ts:105-198) before `step/end`.

**Cancellation.** `cancel(cause)` clears the inbox unless `keepInbox` and aborts the phase's AbortController with the typed cause (191-197). The signal is checked at 16 `throwIfAborted()` points and passed to tools, `prepareCall`, pre-step listeners and the stream; `turn/end` records `{ kind: 'aborted', reason }` copied from `signal.reason` (94-109, 404-407). Disposal is "a disposed-cause cancel followed by quiescence" (index.ts:511-519).

**Resume after a crash.** `AgentLoop.resumeWith()` (index.ts:763-835): open the store handle for write first (789-794), `read(0)` the whole log (799), compute `interruptedTurnClosers(persisted)` (802), which appends a synthetic error `tool/result` for each unanswered `tool-call` (distinguishing `TOOL_NOT_STARTED` from `TOOL_OUTCOME_UNKNOWN`, with text telling the model to retry only idempotent work), then `step/end` and `turn/end { kind: 'interrupted' }` (repair.ts:14-98), append them through the same handle (803), build the `Session` from `[...persisted, ...closers]` (804-809), then `initializeAgent()` with `source: 'resume'`. Nothing is re-sent to the model: pending prompts are reconstructed from `agent/inbox/spliced` events and wait for the next wake. A fresh instance has `requestHeaderLogged = false`, so its first request logs `request/header` with reason `resume` (agent.ts:675-682). `assistant/attempt` retains the exact stream of every failed or cancelled attempt without adding model history (session/src/types.ts:358-363); a process loss before settlement leaves no attempt record (docs/architecture.md:124).

**Lifecycle transaction.** `initializeAgent()` (index.ts:465-656, 192 lines) fuses three abort owners (caller signal, owner fiber, factory teardown), memoizes a reverse teardown (498-545: cancel, whenIdle, scope.dispose, handle.close, detach registries) and runs setup inside `runMaintenance()` so queued input cannot start a turn before `agent/created` completes (621-649).

**Temporal decomposition and pass-throughs.** Runtime context is projected twice per step, in `preStep` (299-300) and again in `step` after `refreshContext` (446-450); only the step copy is appended (475-477). The system prompt is rendered in `step` (442) from an assembly built in `preStep` (294); header equality is computed in `toolsChanged()` (320-324) and again in `buildRequest()` (683). `followup/steer/inject` (179-189) and `AgentLoop.resume()` → `resumeWith()` (754-760) are one-line forwards.

## 4. Durability and ownership

**Event families.** `SessionEventMap` in the kernel declares 14 types (session/src/types.ts:287-436): `turn/start|end`, `step/start|end`, `user/message`, `developer/message`, `system/message`, `assistant/message`, `assistant/attempt`, `tool/call`, `tool/result`, `request/header`, `request/context`, `session/end-seed`; core/agent adds `agent/inbox/spliced` and `model/selection`. 33 non-test files merge the map; the generated catalog lists 62 durable types, 5 "surface" (message-producing) and 57 log-only (docs/persistence-catalog.md:165-). Only the 5 surface types carry `surfaceOp: 'append' | { op: 'replace', startSeq, endSeq }` and `sourceEventSeqs` (types.ts:447-486). The envelope is `{ type, seq, time, data, ignorable?, surfaceOp?, sourceEventSeqs? }` (501-524); a reader meeting an unknown type without `ignorable: true` must refuse (509-519). Experimental plugins write `plugin:*` records marked ignorable (session/src/index.ts:849-866).

**Append.** `Session.append(type, data, surfaceIntent)` (session/src/index.ts:806-837) snapshots `data` as lossless JSON, assigns `seq = log.length` and `time = Date.now()`, validates LLM-specific shapes and surface rules, pushes, then synchronously fans out `session/event` with per-listener containment (892-912). The hot path never blocks on I/O (765-767): the JSONL provider routes `session/event` into a 200 ms write-behind buffer (session-persistence-jsonl/src/storage.ts:36, 274-281, 549-553). `ctx.sessions.flush(session)` dispatches the parallel `session/flush` and rethrows the first failure (session/src/index.ts:1342-1358). `dsh-session-checkpoint-policy` awaits a flush before every `llm/stream`, before top-level `tools/execute` and at `agent/pre-step`, fail-closed (session-checkpoint-policy/src/index.ts:34-37, 58-82): a failed background append stops the next model call or tool body rather than the current append.

**Persistence interface.** `SessionPersistence` is an abstract `Service` with 5 methods, `create`, `open(id, 'read' | 'write')`, `flush()`, `stat`, `list` (session-persistence/src/index.ts:159-210; architecture.md:166 lists an `export` that does not exist). `SessionHandle` has 4 methods, `read(offset, length)`, `append`, `flush`, `close`, plus `Symbol.asyncDispose` and 4 fields (handle.ts:59-116). `storage-contract.ts` (151 lines) is the validator set every backend applies (35-150). Nine methods over a 5,706-line provider: deep by count, but the obligations (freshness, lazy materialization, best-effort append) are JSDoc prose (index.ts:124-143; handle.ts:45-58).

**JSONL format.** Layout `root/<projectKey(cwd)>/<escapedId>/session[.vN].jsonl[.zstd]` (session-persistence-jsonl/src/format.ts:199-269; session-format/src/filename.ts:5-17); default zstd, one checksummed frame for the header line and one per append batch (jsonl index.ts:1379-1394). The header line is `{ type: 'session', version, id, createdAt, cwd?, parentSession?, isSeeded, origin?, delegationDepth, agentPreset? }` (format.ts:83-98). `create` writes nothing; the first append materializes a `wx` temp file, fsyncs, publishes with `link()+unlink` (never rename; `EEXIST` means a concurrent materializer) and fsyncs the directory (index.ts:360-379, 1291-1315, 1361-1371). Appends open-write-fsync-close and truncate back on failure (1413-1451). A torn tail is detected per frame, partially decompressed with `ZSTD_e_flush`, and the write handle's first mutation truncates and rewrites the recovered rows (zstd.ts:21-38; index.ts:1047-1069, 1454-1463). Persistence inserts no `turn/end`: "Repair is the reader's job" (docs/subsystems/persistence.md:110).

**Format bumps.** `SESSION_FORMAT_VERSION = 4` (session/src/types.ts:90). `open` lists canonical generation files, sorts descending, takes the highest (jsonl index.ts:1549-1571), refuses a future version with "upgrade the harness" (602-616), and composes the build-static adjacent chain from the catalog (session-format-catalog/src/generated.ts:16-31: 5 codecs, 4 migrations). A read open serves the migrated events from memory; a write open stages `session.migration.<token>.tmp` (`wx`), writes, fsyncs, verifies in a worker thread, then `link()`s it as the successor; a loser compares digests or throws (generation.ts:728-768, 833-842, 896-938). One package per step: v0→v1 is 8 files / 2,721 lines plus 2,483 test lines, 1,060 of them a 49-case frozen payload switch (session-format-v0-to-v1/src/payload-validation.ts:17-20); v3→v4 is 16 files / 1,660 lines plus 3,073 test lines and a 350-line README spec. Four bumps in 15 days (v0 2026-09-03, v2 09-04, v3 09-08, v4 09-16; docs/persistence-changes/releases/README.md:51-56; docs/session-format-status.md:44-49), none since; 19 dated change records, 18 same-version (docs/persistence-changes/). A bump also costs the writer constant, catalog regen, a bilingual archived doc + schema JSON, snapshot successors and a release record (docs/cookbook/adding-a-session-format-version.md:33, 83-111).

**Model-visible means logged; projections.** `deriveMessages()` walks `surface.nodes` and maps each event through `deriveEventMessage` (session/src/index.ts:999-1030; surface.ts:120-152): `user/message` → data; system/developer/assistant → `data.message` (null when empty); `tool/result` → `data.message`; all else null, which is how `assistant/attempt`, turn/step and request events stay out of history. A content-changing plugin registers one pure `SessionMessageProjection { type, project(event, context) }` (surface.ts:35-47; session/src/index.ts:1081-1089, one owner per type); the only registrant is image offload (`MESSAGE_PROJECTION_EVENT_TYPES = {'image/offload'}`, known-event-types.ts:88-90), and detached readers get a hardcoded list (session-format-catalog/src/message-projections.ts:7). Compaction writes `compaction/start`, `compaction/summary`, a `user/message` checkpoint with `surfaceOp { op: 'replace' }` and `compaction/end` (compaction-basic/src/region.ts:210-245, 491-509); the replace removes shadowed nodes at append, so the model never sees compaction events.

**Projection seam.** `ctx.sessionProjections.register({ key, stateSchema, init, apply, wire?, stateVersion })` (session-projection/src/index.ts:81-131, 297-430) returns a `ProjectionHandle` with `stateOf`, `readerFor`, `dispose` (51-80). The registry subscribes to `session/event` once and folds every event through every unit; `snapshot(session)` is synchronous and returns client views at one `asOfSeq` (468-490; docs/subsystems/session-projection.md:108-138); `checkpoint`/`restoreFloor`/`hydrate` persist and restore `(sessionId, key, ver, seq, val)` rows through `session-projection-cache` (550-750). Kernel units: `turnBoundary` and `modelSelection` (core/agent), `inbox` (agent-loop), `sandboxMode` (sandbox-policy), `llmRetry` (llm-retry).

**Ownership across processes.** In-process, a tracker map makes a second `open(id, 'write')` throw `SessionAlreadyOwnedError` (storage.ts:395-432). Across processes, `SessionWriteLease` takes a non-blocking `flock(2)` on `session.lock` through a native addon (lease.ts:3-4, 34, 94); Windows uses a named kernel semaphore (win32.ts:140-146). No expiry, heartbeat or pid file: "A live but wedged holder keeps the lock until its process exits: there is deliberately no expiry" (lease.ts:10-13); the kernel releases on death. `SessionOwnershipLostError` is declared but "the shipped in-process backends never throw it yet" (session-persistence/src/errors.ts:56-57). Two openers: the second writer fails in both layers; readers never touch the lock, re-scan on each `read` and see the committed prefix (lease.ts:19; storage.ts:146-180; generation.ts:249-260). The log carries no liveness signal: `session/end-seed` tells inherited brackets from live ones, but "tolerating concurrent writers needs a signal beyond the log" (session/src/types.ts:429-433). The [lock contract and acquisition](https://github.com/deepseek-ai/deepseek-harness/blob/ce7073d51254c26cd63b22a60835b8f948deb447/packages/session/session-persistence-jsonl/src/lease.ts#L1-L96), rechecked 2026-10-30, establish cross-process write ownership: lack of expiry prevents taking the lock from a live stalled writer. TeXRA's per-aggregate claims differ in scope and recovery protocol; a per-session lock is still ownership and does refuse a second writer.

**Other stores.** Jobs are session events (`job/registered`, `job/settled`, known-event-types.ts:45-46) over an in-memory map. Schedule tasks, workspace state and the projection cache live in `storage-domain` over `storage-json` (one JSON file per unit) in the base bundle (bundle/base/cordis.patch.yml:182-189; storage/README.md:25-30); `storage-sqlite` exists (key/value JSON rows, WAL) but the session log never uses it (storage/README.md:38, 49). Credentials are a YAML file written under a file lock (credentials-local/src/index.ts:2-6, 44).

## 5. Extension model

**Tools.** `ctx.tools.register(definition, { when? })` places a `ToolDefinition` in the global layer or, through `agent.ctx`, in that agent's layer; scoped tools shadow globals and `restrict({ allow, deny })` intersects over inherited tools only (tools/src/index.ts:128-189; docs/subsystems/tools.md:163-180). Per step, `resolve()` evaluates `when` once and returns a frozen `ResolvedToolSet` that the loop disposes after the batch (264-297); `executable(name, scope, toolSet)` is the per-call lookup inside that set (251-255; pipeline.ts:70-74). The pipeline per call: `tools/pre-execute` waterfall → `ask` resolved by `ctx.get('approval')` (absent means deny, pipeline.ts:436-447) → monotonic `guard`s (`checkGuards`, index.ts:393-401; pipeline.ts:213) → `tools/execute` around-waterfall (timeouts, metrics) → tool body → `projectContent` → `tools/post-execute` waterfall (accept, replace, block, add contexts) → normalization → `finalizeContent` → frozen `tools/result` emit → `tool/result` row (docs/tool-execution-pipeline.md:6-64; pipeline.ts:190-232, 393-410, 476-510; batch.ts:243-265). Batches run exclusive calls as barriers and `isConcurrencySafe` calls in a rolling pool (batch.ts:2-5, 109-233). `ToolExecutor` is a second seam (`describe`, `execute`; executor.ts:64-85) selected per scope so PTC code mode can replace native execution (`setExecutor`, index.ts:325-350); the native executor is 35 lines over the shared pipeline (tool-executor-native/src/index.ts).

**Hooks and events.** 88 harness events are declared, 11 `agent/*`, 5 `tools/*`, 4 `session/*`, 4 `fs/*` (docs/event-producer-consumer.md:13-100); 11 undeclared strings including the deprecated `agent/request` (108-118). Durable extension points are session events, not Cordis events: durable facts "must survive a reload" go in `SessionEventMap` (architecture.md:71-73); `agent/*` and `tools/*` are live. The widest fan-in is `session/event` (31 listeners) and `agent/pre-step` (18); `agent/turn-stopping` is the one serial checkpoint that decides by data (listeners steer, the loop re-reads the inbox).

**Capability seams.** Three roles per seam: Service Definition, Provider, Consumer (architecture.md:136). Provider widths: `fs` 16 abstract methods mirrored 1:1 on the service plus `watch`, `sandboxMode`, `processPathFromHostPath` (fs/src/index.ts:116-367) and 3 intent waterfalls where "the first listener that returns an intent owns the decision" (59-82); `subprocess` 4 abstract (`resolveExecutable`, `terminalEnvironment`, `spawn`, `spawnTerminal`; subprocess/src/index.ts:133-162) with 8- and 9-member handles; `shell` 2 abstract (`resolve`, `execute`; shell/src/index.ts:84-93) over an 11-field request; `sandbox` 1 abstract `confine(argv, policy, signal)` returning `ConfinedArgv { argv, enforcement, denialSignatures, runnerFailureRules }` (sandbox/src/index.ts:103-124, 192); `subagent` 2 optional methods. The per-session sandbox mode is a log-only `sandbox/mode { mode, source? }` event (sandbox-policy/src/session-mode.ts:24-38) written by permission presets and child seeding; a one-call escalation goes through `ctx.approval.request` and lands as `approval/asked` + `approval/decided` rows (sandbox-policy/src/escalation.ts:172-204; user-approval/src/types.ts:44-58). A consumer wraps argv by calling `confine` in `execute()` and spawning the result, then classifies stderr with the returned signatures (bash-sandbox/src/index.ts:98-124, 187-188).

**MCP.** One plugin per server (mcp-client/src/index.ts:154-203); a connection owns client/transport generations and reconnects with bounded exponential backoff (connection.ts:29-41, 211-245); transports are stdio with a scrubbed env and streamable HTTP (transport.ts:31-45); `listChanged.tools.onChanged → refreshTools → enqueueSync` (connection.ts:263-305). Tools enter by registration, not per-call lookup: each sync builds a generation, disposes the previous and calls `ctx.tools.register` per tool under `mcp__<server>__<tool>` (tools.ts:81, 113-150), rolling back to none on a name conflict (151-158). MCP records no trust event of its own; permission flows through `tools/pre-execute` and the approval rows above. Unsupported: prompt templates, elicitation, tasks, resource subscriptions (docs/subsystems/mcp.md:101).

**Subagents.** A child is its own session created by `ownerCtx.agents.create({ sessionId: childId, parentAgent, meta: { parentSession, origin: 'subagent', delegationDepth }, seed? })` (subagent/src/manager.ts:913-922; child-agent.ts:143-153). The parent log receives exactly one event type, `subagent/catalog { childId, version, mode, label? }` (catalog.ts:28-46, 138-144); the child log gets `subagent/descriptor` plus seeded `sandbox/mode`, `approval/policy`, `permission/preset` with `source: 'delegation'` (manager.ts:890; child-agent.ts:270-278). The spawn tool returns `{ kind: 'activation', subagentId }` immediately (tool-subagent/src/index.ts:324-331); the result reaches the parent model as an injected user message with `source { kind: 'subagent-settled', form: 'notice' }`, delivered by `followup` when idle, `steer` when busy, `inject` when draining (manager.ts:1206-1218; continuation-messages.ts:140-173). Activations are "process-local, never durable" (manager.ts:131-132), one pool per root parent, `maxActiveSubagents` 8 (index.ts:186-198); a continuable child is cold-resumed on the next message by `agents.resume` after checking `header.parentSession` and descriptor mode (manager.ts:1349-1404). After a parent crash nothing re-materializes children; an in-flight child turn is lost and the child resumes only when messaged (README.md:209-211). Providers: `fork-in-process` seeds the parent's completed-turn prefix, `spawn-in-process` seeds nothing, both same-process and continuable; `claude-code`, `codex`, `acp` run external CLIs over `ctx.subprocess`, `dsh-sdk` runs a second dsh over stdio JSON-RPC; all four externals are one-shot and reject follow-ups `NOT_CONTINUABLE` (activation.ts:121-129).

**Jobs.** `ctx.jobs` is a 1:1 mirror of a 9-method provider (jobs/src/index.ts:103-195). A job's result reaches the model either as a tool result (`job_output`, `job_kill`; tool-jobs/src/index.ts:432-592) or as a completion notice `createUserMessage({ source: { kind: 'tool-jobs', form: 'notice' } })` delivered by `owner.followup` under a `maxConsecutiveWakes` budget or `owner.inject` (384-410). Lifecycle rows are `job/registered` and `job/settled`; a failed append only warns (jobs-local/src/index.ts:456-462), and `job/settled` may follow `turn/end` or never land at teardown (docs/subsystems/jobs.md:29-31). State is a process map (jobs-local/src/index.ts:1-5, 162); after a crash the job is forgotten and the log holds a `job/registered` with no settlement.

**Schedule.** Tasks are rows in `storageDomain` `schedule` v2 (schedule/src/storage.ts:134-137), one JSON unit file in the base bundle; `lastDelivery`, `deliveryHistory` and `pendingDelivery` are task-row fields written in one `put` (75-77; index.ts:290-294). `drive()` arms one unref'd timer for the next due task (runtime.ts:196-225); a due task resolves its target (`session` via the `schedule/resolve-agent` waterfall, `new` via `sessionController.create`), `agent.followup(createUserMessage({ source: { kind: 'schedule' } }))`, then `ctx.sessions.flush` (352-367, 425-479). Restart re-drives; overdue tasks deliver once for the latest due occurrence (257-262; domain.ts:625-640); a crash between flush and receipt write repeats the delivery, at-least-once (schedule/AGENTS.md:10). No remote-host tasks: "Host" is the local process (README.md:279).

**Extensions ("runtime self-modification").** Through `tool-cordis` an agent changes nothing about itself: it has 2 tools, `cordis_inspect_list` and `cordis_inspect_query`, the latter "cannot invoke business Service methods or modify the runtime" (tool-cordis/src/index.ts:23-49). Define/run/stop/undefine are `ctx.dynamicCordisRunner` service methods reachable programmatically or from the browser panel; "no model tool creates dynamic definitions" (cordis-host-runner/README.md:12). A dynamic plugin is JS source run under `node:vm` with a 5 s timeout and mounted as a child fiber under a `cordis-dynamic` group (sandbox.ts:226-232; lifecycle.ts:27-28); client-bearing packages wait on `cordis/request-run` approval (index.ts:295-318); the guard facade "is not a security boundary" (README.md:62). Definitions live in memory and "disappear on restart" (README.md:12, 58); the only session trace is user messages with `source { kind: 'cordis-host-runner' }`.

**What the kernel knows about the product.** `SessionHeader` carries `origin: 'subagent'`, `delegationDepth`, `agentPreset` (session/src/types.ts:122-135); `AgentCancelCause` enumerates `hook` (194-198); the tool registry reserves `run_code` (tools/src/index.ts:145-147); `SessionStore` and `AgentRegistry` register RPC lookups in their constructors (session/src/index.ts:1093-1103; agent/src/index.ts:266-281); llm/llm carries `x-deepseek-harness-*` transport metadata (`GenerateOptions.sessionId/purpose`, llm/src/types.ts:595-605), `in-history` prompt capability (434-451), `LlmFailure.offloadImages` naming one plugin (59-65), `ReasoningBlock` (74-78) and settings vocabulary (`settingsNs`, badges, 252-293, 354-366); the generic `FileSystem` and `ShellExecutor` each expose a `sandboxMode` getter for a sibling capability (fs/src/index.ts:135; shell/src/index.ts:74).

## 8. Ideas worth evaluating for a durable Effect harness

Each entry: the idea, the dsh files, an illustrative shape, what it would replace in a harness that already has a row log, one program per run and Effect layers, where Effect already supplies what Cordis supplies, and the risk dsh's own history shows.

**8.1 The exact model stream is part of the assistant row; failed attempts keep theirs.** dsh commits one `assistant/message { message, stream, usage }` per successful call and one `assistant/attempt { stream }` per failed, retried or cancelled call; the live `agent/assistant-stream` end frame carries the committed seq, so UI incrementality and the durable record are the same bytes, and replay, fork, telemetry and the transcript all read the settlement (agent-loop/src/agent.ts:505-583; assistant-stream.ts:18-140; session/src/types.ts:349-363; docs/architecture.md:124). Shape (illustrative): `AssistantRow = { kind: 'assistant', message, stream: TimedChunk[], usage?, interrupted?: true } | { kind: 'attempt', stream }`. In a row log this replaces any separate stream buffer, partial-text row or usage row and makes "which attempt produced this message" a non-question. Effect: the stream is already a `Stream<Chunk>`; `Stream.scan` or a `Sink` accumulates the compact record the final row embeds. Risk: the format moved to this in v2 and needed a migration package per step (§4); rows carry whole streams; "a hard process loss before settlement leaves no durable attempt stream" (architecture.md:124).

**8.2 Pending input as durable splices folded by a pure projection.** The inbox is two lists whose every change is one `agent/inbox/spliced { target, start, removedCount?, inserted, outcome? }` event, folded by a 30-line pure `apply` that rejects malformed history by seq; claim at a step boundary is a non-discarding splice plus live `claimed` emits; the same fold serves cold readers with no live agent (agent-loop/src/inbox.ts:26-64, 108-113, 186-231; docs/subsystems/core.md:343). Shape: `InboxRow = { target: 'next-turn' | 'next-step', start, removed, inserted: Msg[], outcome?: 'canceled' }`, `inbox = rows.reduce(apply, empty)`. With run input already as rows this replaces any in-memory queue and gives resume the pending prompts for free. Effect: the fold is `Array.reduce`; the live reader is a `SubscriptionRef` fed by the row stream. Risk: dsh keeps two in-memory latches beside it (`wakeRequested`, agent.ts:230-240) because waking is not durable, and had to specify "wake after abort" in prose (agent.ts:171-176, 222-229).

**8.3 Crash repair as a pure function over the log that writes model-facing error results with retry guidance.** `interruptedTurnClosers(events)` scans for an open tail turn, emits an error `tool/result` for every `tool-call` with no recorded result, distinguishing `TOOL_NOT_STARTED` from `TOOL_OUTCOME_UNKNOWN`, with model-visible text telling the model to retry only idempotent operations, then `step/end` and `turn/end { kind: 'interrupted' }`; fork cuts reuse it with `forked` wording (session/src/repair.ts:14-98, 157-197; agent-loop/src/index.ts:795-803). Shape: `closers(rows): Row[]` appended through the normal writer before the resumed program starts; the same function is the live failed-step path (agent.ts:376-381). This replaces a resume path that re-sends or silently drops dangling calls. Effect: a total function over `ReadonlyArray<Row>` run once in the resume program; no new service. Risk: dsh had to separate semantic repair (agent layer) from physical repair (persistence) and document who owns the torn tail (architecture.md:126; persistence.md:110); synthetic rows reuse the last real timestamp and must keep seq continuity (repair.ts:85-97).

**8.4 Step-scoped tool admission resolved once and disposed with the batch.** `ctx.tools.resolve({ agent, modelSelection, signal })` evaluates each registration's `when` condition once per step and returns a frozen `ResolvedToolSet` whose `view()` re-checks that the registration is still the same object; the same set decides the schemas sent and every call executed, including nested PTC sub-calls, and the loop disposes it after the batch (tools/src/index.ts:264-297; agent.ts:292, 392, 590-593; docs/subsystems/tools.md:180-224). Shape: `admit(step): Effect<ToolSet, never, Scope>` producing `{ schemas, execute(call) }` owned by the step's `Scope`. In a one-program-per-run harness this replaces per-call registry lookups and makes "the tool the model saw is the tool that runs" a property of a value, not of timing. Effect: `Scope.addFinalizer` disposes the set; a `Layer` provides the registry. Risk: dsh still looks the definition up per call inside the set (`executable`, tools/src/index.ts:251-255; pipeline.ts:70-74) and keeps a parallel per-scope executor selection (`setExecutor`, 325-350), so two mechanisms decide what runs.

**8.5 Request envelope rows with a series discipline.** Each model request is reconstructable because the loop logs `request/header { header: { config, adapterDefaults?, tools? }, reason: initial|resume|change|series, startsSeries? }` only when the envelope changes, `request/context` only when route capacity changes, and a `developer/message` naming tool additions and removals between headers; the system prompt is a `system/message` surface node reconciled per step (agent.ts:656-723; session/src/types.ts:240-279, 394-410; runtime-context.ts:68-117; request-header.ts:63-69). Shape: `HeaderRow = { config, tools?, reason, startsSeries? }` + `fold(rows): Header`. This replaces storing the full request per call or recomputing the envelope from configuration at read time; a transcript viewer and a replay harness read the same fold. Effect: the fold is pure; "log only on change" is a `Ref` of the last header compared with `Equal`. Risk: dsh needed an in-memory `requestHeaderLogged` flag and a surface-generation mirror to pick the reason (agent.ts:126-128, 675-691), three placements for the system prompt depending on route capability (architecture.md:112), and the deprecated `agent/request` hook still mutates controls (agent.ts:630-640).

**8.6 Projection units with a state version and a checkpoint row.** A projection is `{ key, init(header), apply(state, event), wire?: { view, viewSchema }, stateVersion }`; the registry folds every committed event through every unit, serves a consistent `snapshot(session)` cut with one `asOfSeq`, persists `(sessionId, key, ver, seq, val)` checkpoint rows and restores from the highest usable row plus a forward tail replay; a bumped `stateVersion` discards old rows (session-projection/src/index.ts:51-131, 171-196, 550-600, 649-750; docs/subsystems/session-projection.md:40-140). Shape: `Projection<S> = { key, version, init, apply }`, `Checkpoint = { key, version, seq, value }`. In a SQLite row log this replaces ad hoc "derive run state from rows" readers with one registered fold per fact owner and gives a cheap cold start for long sessions. Effect: a `Layer` of projections, `Stream.runFold` per session, checkpoints as rows written by the same writer; `Scope` replaces the registry's `refs`/release accounting (index.ts:233-239). Risk: dsh's handles outlive registration ("retains its reader after unregistration", session-projection.md:9) and carry deprecated compatibility paths (session-projection.md:30); the cache is "a fold shortcut, never an authority" that discards on `ver` mismatch (session-projection-cache/src/index.ts:10-14); both `zod` and schemastery validate the same state (index.ts:85, 103).

## 9. What dsh deliberately does not do or declares pre-stable

- **Whole product.** "DeepSeek Harness is experimental developer-preview software. It has not undergone a security audit" (SAFETY.md:7). "Product groups have maintained product roles, while their public APIs remain pre-stable" (packages/README.md:89). 69 packages live under `packages/experimental` without a product-support commitment (experimental/README.md:26). Every package is 0.2.2-alpha.2; `timeout-policy` carries a FIXME to rename "before the first tagged release" (timeout-policy/src/index.ts:6-9).
- **Framework.** Cordis core at 4.0.0-rc.11, Loader pinned at rc.5 with a partial rc.8 slice (vendor/README.md:19-27); 21 live local modifications, "the next new entry is V26" (35); the rc.11 upgrade plan is "Status: proposed" and needs 8 ordered PRs with temporary compatibility code (vendor/cordis-rc11-upgrade-plan.md:3, 36-91). Config validation is synchronous only (fiber.ts:52). `Context.root` is `@experimental` (context.ts:21). The Promise return of profile loading is "the pre-stable API" (app-boot/src/profile.ts:402); `--dump-config` has no byte-stability promise (app-boot/README.md:220). Loader mutations are non-transactional (vendor/README.md:88). HMR is off for headless, SDK and ACP (architecture.md:27).
- **Loop and LLM.** `agent/request` is deprecated and retained for existing listeners (agent/src/runtime-types.ts:362-365). `TODO(call-config-shape)` is open (llm/src/call-config.ts:23-24). The LLM service does no retry, caching or rate limiting; sampling is temperature/maxTokens/stop only; the cross-adapter effort vocabulary is undecided (llm/llm/README.md:171-199). Synchronous session-event reads (`eventAt`, `snapshotEvents`, `ownEvents`) are deprecated but still used (session/src/index.ts:709-743; agent-loop/src/index.ts:705).
- **Persistence.** No SQLite session log; `storage-sqlite` exists but session-backend reuse is deferred (storage/README.md:38, 49). No lease expiry, heartbeat or ownership-loss signal (lease.ts:10-13; errors.ts:56-57). Experimental `plugin:*` records sit outside schema fingerprints and compatibility history (docs/experimental-persistence-catalog.md:8). Flat-file layout, compression conversion, mixed roots and dual write are refused (jsonl README.md:111, 165). The v0→v1 migration is an "alpha" refusal policy (v0-to-v1 README.md:45, 102). Any alpha/beta/rc publication "establishes released Session-format obligations" (docs/session-format-status.md:24).
- **Capabilities.** MCP: no prompt templates, elicitation, tasks or resource subscriptions (docs/subsystems/mcp.md:101); client version string '0.0.1' (connection.ts:259). Sandbox: no network or process-visibility confinement; containers, microVMs and remote execution "replace the surrounding seam instead" (sandbox/src/index.ts:2-4, 27-28); Windows ACL and old Landlock are `partial` (docs/subsystems/sandbox.md:30). Jobs: in-memory only; a settlement may never reach the log (docs/subsystems/jobs.md:29-31). Schedule: Host must be running, no retry loop, at-least-once, no task-level authorization, whole-unit JSON load (schedule/README.md:275-287); no remote-host tasks. Subagents: no durable parent mailbox, process-local residency, lifecycle events observe-only, external runs reject follow-ups (subagent/README.md:199-214; docs/subsystems/subagent.md:176). Compaction: "no model-facing compact tool" (docs/capability-seams.md:742). Extensions: the define/run surface is "historical", "not a security boundary", with no model tool (extensions/README.md:2, 30; cordis-host-runner/README.md:12, 62). SDK: no client-side tool registration; custom composition is a profile plus patch files, never an inline tree (architecture.md:43-47).
