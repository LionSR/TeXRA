## 2. Core abstractions

1. **The row log** (`shared/schemas/sessionEvent.ts`, 38 kinds in `ROW_KINDS`, rowVersions.ts:69-183; 13 retired, 36-50). Invariant: every row is one aggregate's `(seq, commit)`, versioned per kind, written at the current version, gated whole (rowCodec.ts:388-397). Leaks: `config/ratchets/row-readers-baseline.json` lists 15 row types read outside their reducers in 43 file entries (`run.start` 8 files, `plugin.fact` 7, `run.removed` 6, `tool.result` 4), 6 of them outside the harness (`packages/texra/.../documents.ts`, `documentState.ts`, `ChatExportController.ts`, `ExternalInquiryTool.ts`, `trace-viewer/traceFrames.ts` twice). The run reducer names every display kind it ignores (`IGNORED_ROW_TYPES`, runState.ts:175-203: 24 entries), so a new display row touches the run reducer.
2. **`RunState`** (runState.ts:94-151: `RunPosition & RunFacts &` 24 own fields). Invariant: a pure function of the rows, commits strictly increasing, typed `RunHistoryInconsistent` with 5 reasons (74-87), the same function live and on resume (runHistory.ts:5-10). Leaks: the type is imported in 17 files outside `shared/session`; `.phase` is read at 21 sites in 5 files, `.messages` 20 in 7, `.pendingResponse` 10 in 4, `.input` 7 in 4, `.invocation` 6 in 4.
3. **`RunCell`** (runHistory.ts:172-221). Invariant: one writer per run, read-apply-write under a `SynchronizedRef` lock, uninterruptible (RunHistory.ts:376-392), four written preconditions (195-202), the batch applied before it is published and again after (RunHistory.ts:256-311). Leaks: `cell.opened` is a second state the dispatch branches on (`replan`, toolUseDispatch.ts:322-324; `callRequests` takes `Pick<RunCell,'opened'>`, toolGuard.ts:283); `toolUse.ts` calls `cell.append` at 12 sites; `registration` is a one-shot closure variable cleared by a `tap` (RunHistory.ts:377, 395).
4. **The invocation** (inFlight.ts:56-59, 209-246; invocation.ts:353-394). Invariant: `model.message attempt` commits before the request is billed; each failure commits a `failed` row naming the next move; `spentRetries` counts from rows, an unrecorded end spends a retry (199-200); an allowed attempt is re-asked, never resent (221-225). Leaks: three in-memory facts the rows do not hold: `again`, `failedOn` (invocation.ts:363-364) and the once-per-invocation renewal flag `spent` (153), which a resume resets.
5. **`PendingResponse` and dispatch** (inFlight.ts:379-388; toolUseDispatch.ts). Invariant: contiguous parallel calls run under a window of 4 (121), every other call is a barrier, a duplicate derives its primary, a durable write failure halts dispatch (1-10), delivery enters history once with the whole group (1101-1105). Leaks: one scheduler built from three `Deferred` maps, a `Ref` and a `Semaphore` (225-299); the script guest reuses the per-call program through `scriptDoor` (719-946) built inside the same function.
6. **`SessionLog` / the publisher** (SessionHandle.ts:90-161; SessionEvents.ts:219-361). Invariant: one inbox, one consumer fiber, commit order is enqueue order (241-246), `transact` returns after the view applied the batch (SessionHandle.ts:91-94). Leaks: 15 members on `SessionLog`; `session.log` is used 71 times in 30 files; there are five write doors (`transact(rows)`, `transact(job)`, `publish`, `detach`, `removeRun`) plus a cell's `within` (runHistory.ts:246); the job vocabulary `Append`, `Alongside`, `UnfoldedDraft`, `PublisherJob`, `committing`, `afterCommit` (shared/session/sessionEvents.ts:35-130) is reached from RunHistory.ts, plugins.ts:331-376, childTurnResult.ts:106, runLifecycle.ts.
7. **Claims and liveness** (Database.ts:117-124 `NEXT_SEQ` claims on first append, 843-900, 968-976; leaseOwnerLiveness.ts:37-62; ownerLiveness.ts:104-128). Invariant: `event_sequence.owner_id` is the durable claim; liveness is `kill(pid, 0)` plus the start identity, no clocks or leases; a `dead` verdict is final (ownerLiveness.ts:42-56). Leaks: four answers to "is this run live": `RunRegistry.isLive` (runRegistry.ts:251-255, "the single in-process liveness authority", 1-8), `SessionLog.owns` ("the durable claim, read from SQLite rather than from the view, which lags", SessionHandle.ts:152-154), `RunView.ownerId` with `LocalRuntimeState.dead` (sessionSources.ts:29-49), and `ProcessIdentity.owners` (sessionEvents.ts:131-144). `decideResume` consults three of them in sequence (resumeRun.ts:163, 181, 190).
8. **Requests** (`request.opened` v4, `request.decided` v2; requestPolicy.ts:1-13; SessionRequests.ts). Invariant: one writer of a decision (`decide`, SessionHandle.ts:313-317), the policy's answer lands beside the request in the same batch, ids are derived `${responseId}/${callId}:${attempt}:${ordinal}` so a resumed call rejoins its request (inFlight.ts:316-317). Leaks: eight modules decide approval (`shared/approvalPolicy.ts`, `runApprovalQueue.ts`, `requestPolicy.ts`, `loop/toolGuard.ts`, `tools/approval/bashApproval.ts`, `toolEditApproval.ts`, `SessionRequests.ts`, `sessionLayer.ts`); an edit request's content lives only in `SessionViewAccess.toolEdits` (SessionHandle.ts:204-206) because the row "deliberately omits" it.
9. **The inbox** (Inbox.ts:1-6; FollowUps.ts:1-19). Invariant: a run's input is `followup.queued` minus `followup.consumed`, read in the job that acts on it, one reader per run, consumption and the user message commit in one batch. Leaks: the registry calls `Inbox.wake` (runRegistry.ts:90, 454, 536) and the inbox names the registry's `run`/`resume` (Inbox.ts:45-59): mutual knowledge; `session.followUps` in 9 files.
10. **The step** (step.ts:1-20; `tools.offered` v4). Invariant: a run's tools change only at a step; the row pins the system-text hash, the context hash, skills, hooks and modules (runState.ts:442-452), so a resume detects drift. Leaks: the open step is also held in `AgentRun.steps` (AgentRun.ts:118), the bound model in `AgentRun.model` (122) beside `run.config` rows.
11. **Child runs** (childRunLoop.ts; childTurnResult.ts:122-181, 276-292; `child.turn`, `child.park`, `run.result`). Invariant: a child's turn result and its delivery to the parent commit in one transaction (I6); a parent open elsewhere gets the result through `child.park` and `deliverHeld` (runLaunchGuard.ts:102). Leaks: `ChildLoop` keeps `turnIndex`, `consumed`, `failure`, `end` as mutable fields (249-262) beside the rows; three strategy interfaces (107-186) form a template method.
12. **Plugins** (plugins.ts:101-145; `PluginArm` 57-94; `AgentBlock` toolTable.ts:131-160). Invariant: every tool belongs to one plugin, a plugin writes rows only of its own kinds through the one publisher, `admits` runs in the writing transaction. Leaks: `defineBuiltinPlugin` gives built-ins `ToolServices | Runs` (ToolServices.ts:126) that an app plugin cannot have; `RunCall` is a second tool contract "as only the harness's built-in tools read it" (RunCall.ts:1-12); `RecipeChange` carries `added`/`removed` line counts (toolTable.ts:162-172).

## 3. The loop

**Size.** `runToolUse` is 431 lines (toolUse.ts:138-568): `openFresh` 175-276, `runTurn` 288-393, `enter` 396-409, `loopBody` 411-515, exit 545-568. `dispatchPendingResponse` is 804 lines (toolUseDispatch.ts:304-1107): `execute` 487-685, `resumeCall` 690-711, `scriptDoor` 719-946, `responseCall` 956-1000, delivery 1011-1106. `runInvocation` is 42 lines (invocation.ts:353-394) over seven helpers (150-347). The three files are 2,072 lines; the loop directory is 3,471.

**State.** The loop continues from `RunState` as `cell.append` returns it (toolUse.ts:4-6, 291, 415). State held beside the rows: `openingSystem` and `response` (161-163; `response` is re-derived from the last assistant message on resume, 401-406, so a turn's text has two homes); `restoring` (413, 431-432); `AgentRun.model` and `AgentRun.steps` refs (AgentRun.ts:118-122); the dispatch scheduler's maps (toolUseDispatch.ts:226-240), `sharedValues` (800), `pendingUploads` (1067), `accepting`/`streamed` (506-507); `again`, `failedOn`, `spent` in the invocation; `RunRegistry.entries` with fiber, hold, controls, activation `{unbornParent, stop, attempt, deciding}`, lane, launches (runRegistry.ts:104-136); `Inbox.readers`/`sendLanes`/`observers` (Inbox.ts:104-107); `ChildLoop` fields; `ModelRetryGate.routes`; `SessionEvents` `openWorkTracker` (80); `LocalRuntimeState` (self, dead, unreadable, resumeBlocked; sessionViewInput.ts:82-95), `TextChunkSource`, `TranscriptSubscriptions`, `toolEdits` (SessionView.ts:296).

**Resume.** `openRun(runId, resume)` (runProgram.ts:72) opens the cell with an `activation` (runHistory.ts:237-239): the claim is taken (`session.log.hold`, resumeRun.ts:181-188), every undecided request no resume can answer is cancelled (`unboundRequests`, runState.ts:243-264), `run.activate`, ended grants and a changed configuration commit in that batch (runLifecycle.ts:63). Re-read: the whole run aggregate (runHistory.ts:258-259). Recomputed: `RunState`; the step re-resolves tools from the catalog and records a row only when the pinned set differs (toolUse.ts:348-349); `providerMessages(state.messages, session.log.blobs)` rebuilds the `TurnRequest` (ModelInvoker.ts:408-423), the continuation sent only while the binding's origin matches (`chainedContinuation`). Re-sent: nothing by itself; `nextAttempt` decides `send`, `observe` (an accepted background operation, never resubmitted), `reask` (a person allowed one, or the budget is spent), `await`, `fail`, `cancel` (inFlight.ts:209-246). Dispatch on resume: a settled call keeps its result; a duplicate derives; an untouched call of a recovered response is skipped as not started (toolUseDispatch.ts:322-324, 702-704); a started call re-runs only when the saved and current `replay` both say `safe` and the attempt is within `REPLAY_ATTEMPTS` (run/tools.ts:139-141), else "outcome unknown"; a started call with a standing request re-enters it (inFlight.ts:356-376). A script guest is handed its settled calls in commit order before any call runs and a differing call at a recorded `seq` fails `ScriptDiverged` (730-737, 839-849).

**Bounds.** Automatic resends: `bound.automaticRetries` counted from rows (ModelInvoker.ts:753; inFlight.ts:278); the process-wide `ModelRetryGate` cools a route for every run (invocation.ts:211-219); `RETRY_BACKOFF_MS` 1000 (48); tool replays `REPLAY_ATTEMPTS`; held-result delivery 20 × 500 ms (runLaunchGuard.ts:217); upload deadline 5 s (toolUseDispatch.ts:165); session close 5 s (SessionHandle.ts:400).

**Interruption.** Fiber interruption only; `cell.append` and the opening batch are uninterruptible (RunHistory.ts:392; toolUse.ts:196, 273); `acquireUseRelease(enter, loopBody, release)` settles a finished compaction and the cell on any exit (545-563); a call that does not finish interrupts every call placed after it (toolUseDispatch.ts:288-296); interrupts are kept distinct from finalizer failures (592-602); a stop is `RunRegistry.stop` → `terminate` → `Fiber.interrupt`, cascading to children (runRegistry.ts:608-720); `stoppedBy` turns the cause into a cancelled report (runProgram.ts:147; toolUse.ts:566); uploads run in an explicit `Effect.interruptible` island inside "the loop's uninterruptible handoff" (1087-1089).

**Child runs.** A native child runs `executeAgent` through `programs.executeAgent` on a fiber `RunRegistry.start` forks (nativeSubagentStrategy.ts:88; runRegistry.ts:343-399); its rows are `run.start` with `parent.call`, `child.turn accepted/settled`, `run.result`, and its delivery is a `followup.queued` row on the parent, committed in the same transaction as the turn (childTurnResult.ts:276-292); the parent is woken (375). A parent open in another process gets a `child.park` and `deliverHeld` on its next admission. A script run is a child whose single response is the handed-down call (scriptRun.ts:1-9; `RunState.handedDown`). A background shell delivers through `bashDelivery.ts`. A process child (agent-CLI tools, app code) uses `ProcessChildStrategy`. Concurrency: one `Semaphore` per session (runRegistry.ts:551-560), released while a child waits for input (childRunBudget.ts:1-12).

**Temporal decomposition.** One run's birth and death are cut across ten modules by phase: `rootLaunch.ts` (184; `admittedRun` 133-184), `AgentLaunchContext.ts` (336; `prepareAgentDefinition` 124, `buildAgentLaunchContext` 250, `enterRun` 203), `executeAgent.ts` (205; layers 124-138, the description fiber 150-162, the editor notice 180-188), `runProgram.ts` (180; `openRun`, `settleRun`, `stoppedBy`), `AgentRunLifecycle.ts` (417; `runWithLifecycle` 207, `endActivation` 97, `finalizeFailedRun` 238), `agent/storage/runLifecycle.ts` (400; `registrationRows` 132, `activationRows` 63, `finalizeRun` 326, `endIn` 229, `beforeEnd` 298), `terminalResultToast.ts` (107), `sessionDescription.ts` (208; `settleDescriptionOnExit`), `runLaunchGuard.ts` (264; "the ends a run's driver does not write"), and `resumeRun.ts` (367; `decideResume` 157-210, the resume-time twin of `admittedRun`): 2,668 lines. `childRunLoop.ts` repeats the pattern with `beginTurn`, `buildTurnResult`, `recordLastTurn`, `endTurns`, `finishInterimTurn`, `writeEnd`, `endChildLoop`, `runChildLoop` (397-846). `sessionLayer.ts` has `sessionHandleLayer`, `sessionGraphLayer`, `openSession`, `heldSession`, `closeSession`, `sessionOwnerLayer` (159-643).

**One tool call, model response to `tool.result`.** About 24 named functions in 14 files: `finishAttempt` commits the `response` row (ModelInvoker.ts:311) → `runTurn` sees `pendingResponse` (toolUse.ts:307) → `stepFor` (step.ts:421) → `dispatchPendingResponse` (toolUseDispatch.ts:304) → `makeScheduler.run` (269) → `responseCall` (956) → `parseCallArguments` (run/tools.ts) → `resumeCall` (690) → `resumedAttempt` (inFlight.ts:356) → `replayable` (run/tools.ts:136) → `execute` (487) → `callRequests` (toolGuard.ts:281) → `preToolUse` (hooks.ts:392) → `guardedToolCall` (toolGuard.ts:251) → `answerOf`, `rejection`, `sessionPermission` (119, 153, 84) → `bodyStarts` commits `tool.intent` (547-557) → the `defineTool` `call` wrapper validates and runs `execute` (tools/core/definition.ts:97-131) → `extractToolAttachments` + `checkOwnFacts` (620-634) → `captureAttachments` (646) → `pre.after` (hooks.ts:431) → `factRows` (plugins.ts:331) → `retireStanding` (663) → `commitResult` → `commit` → `resultCards` (367-440) → `cell.append` → `RunCell.commit` (RunHistory.ts:235: `contractViolation`, `rowOrigins`, `applyRunRows`, `unprepared`) → `sessionLog.transact` → the inbox job (SessionEvents.ts:294) → `Database.job` → `appendRows` → `prepareEventDraft`/`encodeDraft` (rowCodec) → `projectionUpkeep` (projections.ts:279) → `applyStored` (RunHistory.ts:305).

## 4. Durability and ownership

- **Rows.** 38 kinds; 12 tables and 6 indexes (storeSchema.ts:54-144); `SCHEMA_VERSION = BASELINE_1_0 = 101` (30-33), application id `TeXR` (38); a store below the baseline is moved aside whole (`texra.db.pre1`). ## 8. The biggest design problems

Each entry was checked against `config/ratchets/refuted-candidates.json`; none re-proposes a refused candidate (`withPerKeyLane`, `ModelRetryGate`, the MCP client, `timeouts.ts`, the jitter helper, `ConfigProvider`, `executeCommand`, `ExternalRoots` are left as ruled).

1. **The per-call path is one 804-line function with ~20 closures (shallow internals under a deep door).** Evidence: toolUseDispatch.ts:304-1107; `execute` 487-685, `scriptDoor` 719-946 nested in it; 3 max-lines-per-function and 2 complexity baseline rows; ~24 functions in 14 files per call (section 3). Better shape (illustrative): a `settleCall(cell, call: PendingCall, place)` module whose only input is the row-derived `PendingCall` and whose only output is the `tool.result` batch, called by both the response and the script guest; the scheduler becomes a pure partition `[barrier | parallel[]]` run with `Effect.forEach({ concurrency: 4 })`, the script guest's `seq` order kept by the journal rows it already holds. Deletes: the closure nest (commit/commitResult/cardStart/resultCards/intentRow/skipCall, ~130 lines), `makeScheduler` (75), the `replan` read of `cell.opened`. Risks: the interleaving of guest calls with response calls under one `seq`, and the "nothing runs until the guest holds all that settled" handoff (285-286).
2. **A run's birth and death are decomposed by time across ten modules.** Evidence: 2,668 lines in `rootLaunch`, `AgentLaunchContext`, `executeAgent`, `runProgram`, `AgentRunLifecycle`, `storage/runLifecycle`, `terminalResultToast`, `sessionDescription`, `runLaunchGuard`, `resumeRun`; `run.end` reached through `endIn` from four paths (`finalizeRun`, `childRunLoop.writeEnd` 697, `runLaunchGuard.deliverOne` 126-148, `runRegistry.stopEnd` 672); `rowVersions.ts` and `runLifecycle.ts` edited 34 and 30 times in 30 days. Better shape (illustrative): `run.ts` with `launch`, `resume` and `end` grouped by what they know, the registration, activation and end rows beside their readers in `shared/session/runFacts.ts`, and the editor notice and toast moved to a host that reads `run.end` from the view. Deletes: `executeAgent.ts` (205) and `AgentRunLifecycle.ts` (417) collapse to about 150 lines; `terminalResultToast.ts` (107) and `buildFallbackNotification` (18) leave the kernel. Risk: the crash-point suite's commit points move; `onAdmitted` ordering (executeAgent.ts:80-89).
3. **Four answers to "who runs this run".** Evidence: section 2.7; `decideResume` asks the registry, the claim and the rows in turn (resumeRun.ts:163-191); `RunRegistry.isLive` reads `fiber ?? hold` or `launches > 0` (251-255); `LiveRun` has 8 fields (runs.ts:38-66). Better shape (illustrative): the claim row is the only owner; the registry is a `FiberMap<RunId>` plus the lanes the refuted ruling requires; "live here" means "has a fiber"; the view carries `ownerId` and the process's verdict map only as a projection. Deletes: `RunEntry.hold/launches/activation.deciding` bookkeeping and `prune`/`drains`/`waiting` (about 200 of runRegistry.ts's 825 lines), `LiveRun.live/launched`. Risk: the admission race `withPerKeyLane` was kept for (refuted entry's 2-of-2101 measurement); keep the lane, delete the counters.
4. **The row vocabulary and `SessionHandle` leak into the whole runtime.** Evidence: 43 reader entries over 15 row types, 6 outside the harness; `session.log` 71 uses in 30 files; `SessionLog` 15 members; `RunState` fields read in 17 files; 15 `getUnsafe(view)` sites. Better shape (illustrative): `SessionLog` narrows to `transact`, `publish` and fact reads (`facts(runId)` already exists, SessionHandle.ts:127); each baseline reader becomes a reducer output (`RunRows.start`, `RunRows.removed`), and `rows(id, types)` goes. Deletes: the 43 baseline rows (the ratchet's own goal), `rows()`/`display()` filters, `IGNORED_ROW_TYPES` once display rows stop reaching the run reducer. Risk: cold listing reads that today filter by type in SQL (`READ_LISTING`, rowReader.ts:75).
5. **The public surface is still a host door with app vocabulary.** Evidence: `host.ts` 87 statements, api 194 lines; `SessionHost extends Omit<HostInteractions, 'dispose'>` with five editor-named events; `AgentConfig` 17 top-level fields (25 nested) of which 11 are the app's (`inputFiles`, `outputFiles`, `mediaFiles`, `cli.{outputFile, outputDirectory, expectedOutputFiles, teamId}`, `displayInstruction`, `rootUserInstruction`, `delegationAgentScope`, `outputSchema`); `tools` repeated on `resume`; `WorkspaceAgentsController` and `TeamPlan` in the package. Better shape (illustrative, the design doc's lanes 1 and 3): `SessionHost = { approve?, notice?(n: Notice) }` with a neutral `Notice` union; `AgentConfig` splits into the kernel's `{ agent | persona, instruction, model, tools, workingDirectory, script }` and app launch data carried as a plugin block; custom tools stored by name in `run.config` so `resume` needs no `tools`.
