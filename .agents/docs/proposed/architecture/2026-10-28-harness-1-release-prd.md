# Harness 1.0 发布 PRD

Harness 1.0 提供一个可以独立使用、允许模型编写策略、能够可靠保存和恢复调用的 agent runtime。用户可以从一个 agent 文件或 inline 定义开始，通过脚本组合工具、子 agent、自己的后续调用和 context 操作。TeXRA 是使用这些能力的应用。

本次发布要兑现三个承诺：**模型有编程自由，运行有明确所有者，正式发布的数据可以持续使用。** 内核维护调用、权限、资源和持久化契约；goal、研究流程和领域策略由脚本及插件表达。

状态：产品需求提案。下文“必须”是建议纳入 1.0 的验收要求，不表示实现已经完成。代码基线为 `main` 的 `8fcd0a33911397fab03e51fd640f00928c8ca70a`。存储修复 [#14350](https://github.com/LionSR/TeXRA/pull/14350) 位于 `0bd092d991`，截至 2026-10-28 为 draft，尚未合入。

## 目标用户和使用场景

| 用户                   | 要完成的事情                    | 1.0 应提供的体验                                                         |
| ---------------------- | ------------------------------- | ------------------------------------------------------------------------ |
| 嵌入 harness 的开发者  | 给自己的应用添加 agent          | 使用公开入口配置模型和工具，启动、读取结果、停止、重新打开并恢复         |
| 编写 agent 的用户      | 复用 persona、prompt 和工具配置 | agent 文件与 inline 定义使用同一种语义；文件可以作为模板并组合明确的依赖 |
| 编写策略的模型或开发者 | 动态选择工具，编排多步任务      | 通过 codemode 使用条件、循环、并发、模块和子调用；策略不需要进入内核     |
| 插件作者               | 提供新的工具、模块或领域能力    | 使用公开插件接口完成接入，并获得相同的授权、取消、记录和恢复行为         |
| 使用长期任务的用户     | 中断、关闭或升级后继续工作      | 历史和输出仍可访问；可以恢复的任务继续，不能恢复的任务说明具体原因       |

主要成功路径是：安装包，运行一个 agent；让 agent 写脚本组合能力；关闭进程后重新打开同一项目；读取原有结果并安全继续未完成的调用。

### 后续版本可以完成

任意网络 URL 或 npm 包的动态 import、第三方插件商店、运行中热替换整个插件、多个数据库后端、跨机器执行环境，以及完整替换所有历史目录布局，都不作为本次发布的必要条件。

1.0 的 imports 覆盖工作区和已启用插件提供的明确模块。命名暂用现有 harness 和 TeXRA；包名调整单独处理，不能顺带更改已发布的持久化身份。

## 调用和持久化契约

### 从调用产生事实

跨恢复边界的操作必须有稳定身份，并能关联调用者、被调用能力、实际输入、尝试及结果。优先由现有 run、response、call 和 attempt 身份表达；只有证明现有身份无法表达必要语义时，才增加持久字段。

这里的“调用”包括模型请求、工具执行、子 agent，以及需要持久保存结果的 context 操作。普通函数、局部变量和临时计算不要求逐条保存。外部输入、用户决定和资源所有权中无法从调用结果推导的事实，继续保留自己的明确记录。

| 持久事实                     | 恢复行为                                           |
| ---------------------------- | -------------------------------------------------- |
| 尚未提交执行意图             | 按正常授权和调用路径决定是否启动                   |
| 已有可复用的结果             | 返回原结果，不重复执行原调用                       |
| 已提交意图，结果缺失         | 按该操作的恢复契约处理；不能推断为未执行或失败     |
| 子调用仍由父调用持有         | 重新关联原有子调用和结果，不因恢复另造一棵子运行树 |
| 实际代码或依赖与原执行不兼容 | 保留历史，阻止直接续跑，并说明不匹配的依赖         |

结果缺失的调用，只有工具与具体调用均允许安全重放时才自动重放。其余沿用结果未知的语义，交还模型处理；后续新调用仍经过正常授权。不得为此新增默认的“重跑或跳过”人工确认流程。

### 自由脚本的恢复边界

脚本恢复必须能识别同一调用，并校验能力、输入和执行契约。不能仅按“这是第几个调用”复用另一个调用的结果。

运行应保留或可定位实际执行的脚本与模块内容，并保存足以检查兼容性的身份或摘要。影响恢复的时间、随机值、外部读取等输入，要么经过可记录的能力入口，要么明确使该段执行不可自动重放。具体存储方式在实现切片中选择，不预先规定新的表或运行引擎。

数据库保存需要跨进程保留的事实。fiber、scope、订阅、锁和临时执行栈属于运行时资源；重构这些资源通常不应触发数据库格式变化。

## 运行所有权和 Effect

每项资源必须能回答：谁创建、谁持有、谁可以停止、谁等待回收。代码要从资源的实际所有者得到答案，避免调用方维护第二份生命周期判断。

| 边界         | 必须成立的规则                                                                                           |
| ------------ | -------------------------------------------------------------------------------------------------------- |
| 启动和交接   | 对外返回 handle 前发生失败或取消，不留下无人持有的执行与订阅；已被其他调用者合法接手的共享执行继续受管理 |
| 加入已有运行 | 结束自己的等待不等于停止共享执行；两种操作在公开 API 中可以区分                                          |
| 运行停止     | 由持有执行的层发出停止；正在等待的授权、队列和外部进程按各自资源契约退出                                 |
| 业务结束     | 结果和必要的持久事实完成提交后，对外报告业务结果                                                         |
| 资源回收     | 独立确认 fiber、数据库 claim、订阅和子进程已释放；业务结束不直接等同于回收完成                           |
| 关闭 session | 持有的工作停止或完成交接；回收超时必须报告未释放的对象                                                   |

首个清理范围是 `runHandle.ts`、`resumeRun.ts` 和 `Resumes`。目标是把取消与共享执行的归属判断收回执行所有者，再删除 SDK 对应的状态和回调。不能先删除保护逻辑，再补一个更大的状态管理器。

`RunRegistry` 中的数据库 claim、FIFO 等待和子运行结果投递有真实职责。保留这些职责，逐项证明哪些字段重复表达同一事实。把 `Map` 改成 `Ref`、字段换名或拆文件，都不单独算完成。

异步资源使用 Effect 的 scope、fiber、队列和 finalizer。不可中断区需要对应明确的提交或资源交接步骤。当前两个 `AbortController` 常驻点有既有裁决；删除它们必须在同一切片证明外部进程取消、结果投递与收尾仍正确，并同步修订裁决，不能机械清零。

## Agent 文件和 imports

Agent 文件是可复用的 persona 和能力配置。inline 定义与文件定义进入同一解析和执行路径。文件形式本身不需要被替换。

1.0 必须区分两类组合：prompt 或模板内容的组合，以及脚本代码模块的 import。模板解析不执行任意代码；代码模块在同一个受控执行环境内运行，通过已授予能力产生副作用。

模块解析需要确定的来源、相对路径规则和错误定位。缺失模块、越界路径、模板循环引用或不支持的模块循环必须给出明确错误。一次运行固定实际使用的依赖，文件修改影响后续运行，不能悄悄改变已经开始的运行。

插件提供模块时，模块身份绑定插件及其版本。导入模块不会扩大调用者的工具或文件权限。远程依赖安装和运行时任意包解析留到后续版本。

## Codemode 和 goal

模型在 codemode 中可以发现工具、检查输入结构、发起调用、处理返回值、组合并发，并调用子 agent 或 `self`。工具和模块的接口要足够清楚，使模型能够在一次失败后根据结构化错误修正代码。

`self` 的语义必须公开：使用哪个 agent、继承哪些工具和权限、context 从何处截取、是否复制待处理输入、结果如何返回。默认行为可以简洁，但调用者必须能明确选择需要的 context。

默认 goal 是一段可查看、可修改、可替换的脚本。循环次数、分工、context 选择、总结和完成判断属于脚本策略；内核提供可取消的调用、预算执行、输入和结果。自定义策略不能绕开这些约束。

默认 goal 至少返回可区分的完成、需要用户输入、预算或运行条件导致暂停等结果。完成判断需要引用实际产物或检查结果；一次模型自报完成不能替代验收。暂停后的继续策略和 context 必须明确，不依靠内核暗中新增一轮。

业务上的暂停与运行时挂起分别表达。脚本返回 `paused` 不自动意味着还有一个可恢复的存活 fiber；继续工作通过明确的新调用或受支持的恢复入口完成。

预算必须说明度量、作用域和检查时点。整棵运行树的预算、单次脚本并发限制和每轮后的停止条件分别表达。当前 goal 在轮次之间检查花费，这属于停止启动下一轮的阈值；1.0 不能把它描述成正在执行的调用绝不会超出的费用硬上限。

## 插件和 SQL

“Everything as a plugin”的验收对象是扩展能力。内核的授权、调用身份、持久化、资源回收和恢复约束是所有插件共同遵守的边界。

公开接口必须覆盖一个完整外部插件需要的贡献：工具、脚本模块、agent 模板、必要的版本化数据，以及这些能力的发现和使用。插件贡献哪些项目，由清晰的能力矩阵说明；不同安装格式没有实现的能力直接声明不支持。

以同一示例同时验证内置和仓库外插件。外部插件不得依赖 harness 内部 import、修改核心 union 或加入专属启动分支才能完成该示例。若仍需要这些改动，视为公开接口缺口，按示例所需的最小范围修复。

SQL 面向查询允许公开的历史数据。保持 `HistoryQuery` 的隔离边界，公开可查询字段、读取截至哪个 commit、返回限制和超时。禁止 SQL 修改权威运行库、读取未暴露的记录或附加其他数据库。持久化内部表布局不因此变成供模型长期依赖的 API。

## 数据库发布后的演进

采用现有存储设计的契约：从首次正式冻结开始，保留已发布事件版本的读取链，直到经过明确的大版本转换。转换集中在 codec，业务层只读当前语义。升级后的历史、输出和用户设置仍然可访问。

| 数据层                | 演进方式                                                                                       |
| --------------------- | ---------------------------------------------------------------------------------------------- |
| 物理 schema           | 真正需要更改时，将升级步骤、事务失败处理和旧库验收一起交付；支持的正式库不走开发期移开重建路径 |
| 核心事件与调用结果    | 按类型独立版本化，在读取边界转换；不就地改变已发布版本的含义                                   |
| 插件事实              | 插件身份和事件类型稳定，独立版本化；插件不可用时保留原始记录并标明当前能力限制                 |
| 投影和索引            | 从权威事实重建；不要求保留旧投影实现                                                           |
| 设置等 current values | 按所属数据契约演进；必须纳入旧版本样本和升级检查，不能只测试 run 事件                          |

历史可读与任务可续跑分别验收。代码、模型或插件依赖不满足恢复契约时，阻止不安全续跑，但保留可访问的历史、输出和具体原因。旧程序遇到不能理解的新库，应拒绝使用且不修改数据。

发布检查同时保留最早需要支持的版本和最新发布版本。新增冻结文件不能掩盖早期兼容链被删除。格式指纹检查之外，还要使用旧版本生成的真实样本，核对历史、输出和恢复效果。

[#14350](https://github.com/LionSR/TeXRA/pull/14350) 已实现这个范围中的两个修复：转换步骤相对可读版本下限索引；冻结检查保留首个正式版本的要求。该 PR 不代表物理库升级、插件接入和执行恢复已全部完成。

每个切片只解决一个所有权或契约问题。PR 必须列出保留的所有者、被删除的状态或路径、消费者变化、生产代码与测试的增减，以及对应的失败场景。新增抽象必须在同一 PR 替代旧路径。

修复正确性问题可以增加必要代码；清理不能只靠新增 wrapper、移动目录或扩大 baseline 宣称完成。默认沿用现有测试；新增回归测试先复现具体失败。禁止为了接受新行为而批量刷新旧数据样本。

| 编号 | 场景                                                       | 必须得到的结果                                                  |

| R6   | Agent 文件与等价 inline 定义执行同一输入                   | 解析后的 persona、工具和权限语义一致                            |
| R7   | 工作区及外部插件模块导入；修改依赖后尝试恢复               | 合法导入成功；越界与缺失错误可定位；不静默更换运行依赖          |
| R8   | 两个不同 goal 脚本执行至少两轮 self，并选择不同 context    | 内核无需新增策略分支；结果、花费范围和暂停原因可检查            |
| R9   | 在受控外部插件中安装工具、模块和 agent，并关闭该插件后恢复 | 正常使用走公开接口；缺失能力被明确处理，历史保留                |
| R10  | SQL 查询、越权语句、超时和大结果                           | 只返回允许的数据；权威库不变；限制可见且查询资源可回收          |
| R11  | 读取旧正式库，升级失败，再由旧程序打开新库                 | 旧历史与输出保持一致；失败保留可恢复原库；不支持的新库拒绝改写  |
| R12  | 汇总 A 至 C 的代码变更                                     | 已替换的实现被删除；无新增内部 import 例外或放宽的质量 baseline |

确定性故障注入用于验证运行契约，真实模型用于验证接口是否能被正确使用，两类证据分别报告。真实模型验收至少覆盖两条受支持的模型路线，并记录模型、配置、脚本、调用历史、产物及失败原因；没有实际运行的项目不能标为通过。

发布不要求所有技术债归零。P0 场景全部通过、数据契约冻结、示例可以独立复现，且没有已知会丢失数据、重复产生未知外部效果或留下失控执行的缺陷，才进入发布审批。
