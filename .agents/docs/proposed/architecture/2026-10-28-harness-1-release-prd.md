# Harness 1.0 发布 PRD

Harness 1.0 提供一个可以独立使用、允许模型编写策略、能够可靠保存和恢复调用的 agent runtime。用户可以从一个 agent 文件或 inline 定义开始，通过脚本组合工具、子 agent、自己的后续调用和 context 操作。TeXRA 是使用这些能力的应用。

本次发布要兑现三个承诺：**模型有编程自由，运行有明确所有者，正式发布的数据可以持续使用。** 内核维护调用、权限、资源和持久化契约；goal、研究流程和领域策略由脚本及插件表达。

状态：产品需求提案。下文“必须”是建议纳入 1.0 的验收要求，不表示实现已经完成。代码基线为 `main` 的 `f4c9efd355e148b7507354713e1db7b86655b7d2`。存储修复 [#14350](https://github.com/LionSR/TeXRA/pull/14350) 位于 `0bd092d991`，截至 2026-10-28 为 draft，尚未合入。

## 目标用户和使用场景

| 用户                   | 要完成的事情                    | 1.0 应提供的体验                                                         |
| ---------------------- | ------------------------------- | ------------------------------------------------------------------------ |
| 嵌入 harness 的开发者  | 给自己的应用添加 agent          | 使用公开入口配置模型和工具，启动、读取结果、停止、重新打开并恢复         |
| 编写 agent 的用户      | 复用 persona、prompt 和工具配置 | agent 文件与 inline 定义使用同一种语义；文件可以作为模板并组合明确的依赖 |
| 编写策略的模型或开发者 | 动态选择工具，编排多步任务      | 通过 codemode 使用条件、循环、并发、模块和子调用；策略不需要进入内核     |
| 插件作者               | 提供新的工具、模块或领域能力    | 使用公开插件接口完成接入，并获得相同的授权、取消、记录和恢复行为         |
| 使用长期任务的用户     | 中断、关闭或升级后继续工作      | 历史和输出仍可访问；可以恢复的任务继续，不能恢复的任务说明具体原因       |

主要成功路径是：一个仓库外的示例包提供 agent 文件、原生插件工具和脚本模块；使用公开 SDK 启动；模型发现能力并编写至少两轮 self 脚本，根据结构化工具结果及 SQL 历史选择下一步；在子调用结果提交、父脚本尚未消费时结束进程；重新打开后沿用原调用记录和模块源码，安全继续并得到可检查的产物。

## 调用和持久化契约

### 从调用产生事实

跨恢复边界的操作必须有稳定身份，并能关联调用者、被调用能力、实际输入、尝试及结果。优先由现有 run、response、call 和 attempt 身份表达；只有证明现有身份无法表达必要语义时，才增加持久字段。

这里的“调用”包括模型请求、工具执行、子 agent，以及需要持久保存结果的 context 操作。普通函数、局部变量和临时计算不要求逐条保存。外部输入、用户决定和资源所有权中无法从调用结果推导的事实，继续保留自己的明确记录。

| 持久事实                     | 恢复行为                                           |
| ---------------------------- | -------------------------------------------------- |
| 尚未提交执行意图             | 按正常授权和调用路径决定是否启动                   |
| 已有可复用的结果             | 返回原结果，不重复执行原调用                       |
| 已提交意图，结果缺失         | 按该操作的恢复契约处理；不能推断为未执行或失败     |
| 子调用仍由父调用持有         | 重新关联原有子调用和结果，不因恢复另造一棵子运行树 |
| 实际代码或依赖与原执行不兼容 | 保留历史，阻止直接续跑，并说明不匹配的依赖         |

结果缺失的调用，只有工具与具体调用均允许安全重放时才自动重放。其余沿用结果未知的语义，交还模型处理；后续新调用仍经过正常授权。不得为此新增默认的“重跑或跳过”人工确认流程。

### 自由脚本的恢复边界

脚本恢复必须能识别同一调用，并校验能力、输入和执行契约。不能仅按“这是第几个调用”复用另一个调用的结果。

已开始的脚本必须保留或可定位实际执行的代码与模块内容，并保存足以检查兼容性的身份或摘要。当前 `tools.offered` 已按内容摘要保存模块源码，恢复使用已保存的版本；继续沿用这个边界。后续新 step 可以采用新版本，不要求整个长会话固定依赖。影响恢复的时间、随机值、外部读取等输入，要么经过可记录的能力入口，要么明确使该段执行不可自动重放。不新增第二套模块快照、调用日志或运行引擎。

数据库保存需要跨进程保留的事实。fiber、scope、订阅、锁和临时执行栈属于运行时资源；重构这些资源通常不应触发数据库格式变化。

## 运行所有权和 Effect

每项资源必须能回答：谁创建、谁持有、谁可以停止、谁等待回收。代码要从资源的实际所有者得到答案，避免调用方维护第二份生命周期判断。

| 边界         | 必须成立的规则                                                                                           |
| ------------ | -------------------------------------------------------------------------------------------------------- |
| 启动和交接   | 对外返回 handle 前发生失败或取消，不留下无人持有的执行与订阅；已被其他调用者合法接手的共享执行继续受管理 |
| 加入已有运行 | 结束自己的等待不等于停止共享执行；两种操作在公开 API 中可以区分                                          |
| 运行停止     | 由持有执行的层发出停止；正在等待的授权、队列和外部进程按各自资源契约退出                                 |
| 业务结束     | 结果和必要的持久事实完成提交后，对外报告业务结果                                                         |
| 资源回收     | 独立确认 fiber、数据库 claim、订阅和子进程已释放；业务结束不直接等同于回收完成                           |
| 关闭 session | 持有的工作停止或完成交接；回收超时必须报告未释放的对象                                                   |

### Resume 的职责和删除顺序

当前 `ResumeRunResult` 同时返回 `started`、`delivered`、`outcome` 和另一个 `completion`；SDK 又通过 `joined`、`cancelled`、启动的 fibers 和回调参与执行归属判断。问题是跨层协议，不是这些字段天然重复。首次启动与恢复已经共用运行循环，继续保留这一点。

| 职责               | 唯一负责的边界                      | 对外含义                                      |
| ------------------ | ----------------------------------- | --------------------------------------------- |
| 确定恢复哪个运行   | 在数据库 claim 内判定归属与恢复条件 | 正常返回启动、加入、跟随父运行或拒绝的决定    |
| 建立执行归属       | 现有执行所有者                      | activation 提交并完成交接；明确谁能停止该执行 |
| 交付指定输入       | 既有输入队列和已提交的轮次事实      | 本次捕获的输入批次已经到达约定的消费边界      |
| 等待业务结果与回收 | 运行所有者及其 scope                | 业务结果、观察者退出和资源回收分别完成        |

SDK 只持有自己的观察资源，不再通过回调和跨层 joiner 查询解释共享执行该不该继续。调用者退出等待与 session 关闭仍有不同语义。现有两个 joined 值分别表达“我是观察者”和“已有其他观察者”，不能不经替代直接删去其中一个。

按以下顺序清理，每片删除它替代的旧路径：

1. 利用 `resumeHere` 已有的外层 scope 持有 claim，删除没有独立关闭时点的手建嵌套 scope；保留 claim 的完整持有期。
2. 将 `ownedBy` 作为正常恢复决定，删除 `OwnedByParent → RunFailure → catch → follow` 的异常往返。归属判定仍在 claim 内，重定向前的监听必须回收。
3. 将共享 attempt 的取消与观察者规则收回现有执行所有者，同片删除 SDK 对应的取消回调、身份回调和 joiner 查询。
4. 由既有已提交事实提供输入批次回执，等价替代后删除贯穿 resume、执行入口和循环的 `onIdle` 通知链。不增加持久化 resume-status 表。

输入回执有一个必须保留的边界：它针对本次捕获的非 model-switch 输入，运行未结束时，等待 idle/turn boundary 且该批次已离队；若运行先结束，则根据该批次是否仍排队判断送达；不是“整个队列为空”，也不是单独一条 consumed 记录或“当前 phase 为 waiting”。同一提交可能结束上一轮、消费下一批并进入 `turn.ready`。后来追加的输入不能改写原批次回执；运行提前结束时仍要区分未送达的输入。输入回执不再借用业务结果字段表达。

`RunRegistry` 中的数据库 claim、FIFO 等待和子运行结果投递有真实职责。保留这些职责，逐项证明哪些字段重复表达同一事实。把 `Map` 改成 `Ref`、字段换名或拆文件，都不单独算完成。

异步资源使用 Effect 的 scope、fiber、队列和 finalizer。不可中断区需要对应明确的提交或资源交接步骤。当前两个 `AbortController` 常驻点有既有裁决；删除它们必须在同一切片证明外部进程取消、结果投递与收尾仍正确，并同步修订裁决，不能机械清零。

## Agent 文件和 imports

Agent 文件是可复用的 persona 和能力配置。inline 定义与文件定义进入同一解析和执行路径。文件形式本身不需要被替换。

Prompt 模板与脚本代码是两种组合方式。1.0 保留参数化 prompt 和已注册脚本模块；模板解析不执行任意代码，代码模块在同一个受控环境内运行，通过已授予能力产生副作用。当前模板 loader 不支持 include，脚本 resolver 拒绝相对路径；不能把新增这两套解析能力写成已有能力的整理。

已注册模块必须有确定的来源和缺失时的明确错误。恢复已经开始的脚本使用原模块源码；后续新 step 可以读取更新后的模块。将来增加工作区 import 时，再同时交付相对路径、越界和循环处理规则，不提前建立无人消费的 resolver。

模块来源关联贡献插件；执行内容通过已保存源码及其摘要固定，恢复所需能力另行检查兼容性。导入模块不会扩大调用者的工具或文件权限。远程依赖安装和运行时任意包解析留到后续版本。

## Codemode 和 goal

模型在 codemode 中可以发现工具、检查输入结构、发起调用、处理返回值、组合并发，并调用子 agent 或 `self`。工具和模块的接口要足够清楚，使模型能够在一次失败后根据结构化错误修正代码。

`self` 的语义必须公开：使用哪个 agent、继承哪些工具和权限、context 从何处截取、是否复制待处理输入、结果如何返回。默认行为可以简洁，但调用者必须能明确选择需要的 context。

默认 goal 是一段可查看、可修改、可替换的脚本。循环次数、分工、context 选择、总结和完成判断属于脚本策略；内核提供可取消的调用、预算执行、输入和结果。自定义策略不能绕开这些约束。

默认 goal 至少返回可程序判断的完成、需要用户输入、调用失败、缺少有效 verdict、费用阈值停止等原因。当前这些暂停原因被折叠成 `paused` 和 report 文本；修复应增加明确的结果语义，而不是新增 goal scheduler。完成判断需要引用实际产物或检查结果；一次模型自报完成不能替代验收。暂停后的继续策略和 context 必须明确，不依靠内核暗中新增一轮。

现有 `self` 默认 fork 脚本开始时的 context，goal 通过上一轮 report 传递进展；它不会自动继承每一轮全部新对话。P0 用 fork 与 fresh 等已有选择验证两种脚本策略，允许模型修改循环、分工和报告内容，不硬编码任务流程。

业务上的暂停与运行时挂起分别表达。脚本返回 `paused` 不自动意味着还有一个可恢复的存活 fiber；继续工作通过明确的新调用或受支持的恢复入口完成。

预算必须说明度量、作用域和检查时点。整棵运行树的预算、单次脚本并发限制和每轮后的停止条件分别表达。当前 goal 在轮次之间检查花费，这属于停止启动下一轮的阈值；1.0 不能把它描述成正在执行的调用绝不会超出的费用硬上限。

## 插件和 SQL

“Everything as a plugin”的验收对象是扩展能力。内核的授权、调用身份、持久化、资源回收和恢复约束是所有插件共同遵守的边界。

公开接口必须覆盖示例所需的工具、脚本模块、版本化事实及其发现和使用。Agent 文件可以随包提供，通过公开 `nodePlatform({ agentsDir })` 加载；`agentBlock` 是任务配置块，不应被写成 agent 模板发布接口。

| 接入形式             | 当前能力与 1.0 范围                                                                    |
| -------------------- | -------------------------------------------------------------------------------------- |
| 原生 `Plugin` 贡献包 | 工具、process/session layer、持久化 arms、脚本模块与任务配置块；本次完整路径采用此形式 |
| 安装式 manifest      | skills、commands、agents、MCP 和 hooks；不承诺原生脚本模块与持久化 arms                |
| 内核与受信内置能力   | 授权、执行归属和持久化约束继续由内核负责；不为追求形式一致而给任意插件开放 `Runs`      |

以同一示例同时验证内置和仓库外插件。外部插件不得依赖 harness 内部 import、修改核心 union 或加入专属启动分支才能完成该示例。若仍需要这些改动，视为公开接口缺口，按示例所需的最小范围修复。

### SQL 的能力范围尚待决定

已确认的问题是现有 SQL 只提供展示历史，能力范围过窄。不能直接把当前限制冻结成 1.0 的最终边界。当前实现是只读的内存副本，尚无业务表写入口；具体读写范围仍需确定。

目前确定的改进是结构化返回：脚本直接获得列、行及限制信息，不必解析展示文本。进一步开放完整调用事实、允许模型维护自己的业务表，分别作为待评估的范围选择；后者尚未得到确认，不列为已经决定的 P0 要求。

范围收敛前，不预建业务数据库、每表 schema 注册或 SQL 迁移框架。SQL 最终方案应说明数据来源、读写权限、持久化、事务与结果未知的行为，并复用既有调用和资源管理边界。

## 最小存储契约

**旧调用是什么，就一直保存成什么；新代码能否继续它，另行判断。** 数据库设计首先减少需要兼容的变化，而不是要求所有能力都有版本号、迁移链和旧接口适配器。

1. **沿用已经记录的事实。** 现有调用身份、父子关系、attempt、原始输入输出、附件和内容摘要是存储基础。完成的调用复用原结果；脚本使用已经保存的模块源码。不再建一套 call journal，也不保存整个执行对象图。
2. **执行变化通常不改变存储格式。** 更换 provider、工具实现、agent 策略或插件，本身不触发数据迁移。历史 `{ path: "a.txt" }` 不必转换成新工具的 `{ uri: ... }` 才能读取；需要再产生效果的调用，才检查当前权限、输入和重放条件。不承诺永久运行所有旧环境。
3. **只处理真实的存储变化。** 保留现有格式标识、schema 校验和旧程序拒绝误写新库的保护。只有持久表示的结构或含义确实不兼容时，才对受影响的一处提供必要转换；兼容新增字段、可重建投影和可独立保存的应用数据变化不自动产生核心格式版本。

这仍要求调用身份、结果边界、费用和附件完整性正确，不能把无验证 JSON 直接交给授权或恢复决策。历史读取得到支持期内的原事实；无法执行时给出原因。缺失插件时，历史入口提供原事实的身份、未解释原因和原始 payload，不静默丢内容，也不将未知内容当作已解释的执行状态。

当前需要优先解除的耦合是：`rowVersions.ts` 因移除 provider 升级多个历史类型；缺插件的事实只留在库里而被普通读取略过。`current_value` 共用版本号也不意味着现在必须引入 family 版本框架；由值的 owner 保持已存值可解释，真实变更发生时选最小局部处理。应用设置不用全部改成事件。

1.0 保存少量覆盖实际契约的真实调用样本，并沿用现有冻结检查。发生存储变化时补充受影响的样本；验收历史可读，并分别验证可继续的调用和应明确拒绝的调用。取消逐应用版本的完整恢复矩阵，以及预先为每个 family、工具或插件建立版本机制的要求。任何实际数据转换都必须验证失败不覆盖原值，不影响无关数据；没有转换就不创建迁移工程。

物理库格式真正变化时，才交付对应升级步骤。现有 writer gate、claim 和投影事务继续保护核心库；不通过跳过校验实现宽松读取。不要求旧程序理解任意未来格式。已有 [Storage v1](../../implemented/architecture/2026-09-28-storage-v1-design.md) 的历史保留与校验约束继续有效；本提案收窄的是本 PRD 额外施加的版本机制和普遍续跑承诺。

[#14350](https://github.com/LionSR/TeXRA/pull/14350) 修复已有转换链的索引与首发版本检查，应按现有机制的正确性修复审查；它不构成继续增加迁移框架的理由，也不代表上述存储边界和 SQL 能力已经实现。
