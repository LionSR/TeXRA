# Harness 1.0 发布 PRD

Harness 1.0 提供一个可以独立使用、允许模型编写策略、能够可靠保存和恢复调用的 agent runtime。用户可以从一个 agent 文件或 inline 定义开始，通过脚本组合工具、子 agent、自己的后续调用和 context 操作。TeXRA 是使用这些能力的应用。

本次发布要兑现三个承诺：**模型有编程自由，运行有明确所有者，正式发布的数据可以持续使用。** 内核维护调用、权限、资源和持久化契约；goal、研究流程和领域策略由脚本及插件表达。实现应让普通功能只表达自身的行为，少量既有边界负责记录、恢复和资源释放；新增功能不应重复编写这些协议。

状态：产品需求提案，首批实现已开始。下文“必须”是建议纳入 1.0 的验收要求，不表示实现已经完成。已合入代码基线为 `main` 的 `fa6fb1e04f0a9812fa5cdfd17684c31c13d8a790`。以下计划把相关 open PR 按预期会合入处理，但区分现有实现、待整合改动与剩余工作；预期合入不等于已经通过组合验证。

## 目标用户和使用场景

| 用户                   | 要完成的事情                    | 1.0 应提供的体验                                                         |
| ---------------------- | ------------------------------- | ------------------------------------------------------------------------ |
| 嵌入 harness 的开发者  | 给自己的应用添加 agent          | 使用公开入口配置模型和工具，启动、读取结果、停止、重新打开并恢复         |
| 编写 agent 的用户      | 复用 persona、prompt 和工具配置 | agent 文件与 inline 定义使用同一种语义；文件可以作为模板并组合明确的依赖 |
| 编写策略的模型或开发者 | 动态选择工具，编排多步任务      | 通过 codemode 使用条件、循环、并发、模块和子调用；策略不需要进入内核     |
| 插件作者               | 提供新的工具、模块或领域能力    | 使用公开插件接口完成接入，并获得相同的授权、取消、记录和恢复行为         |
| 使用长期任务的用户     | 中断、关闭或升级后继续工作      | 历史和输出仍可访问；可以恢复的任务继续，不能恢复的任务说明具体原因       |

主要成功路径是：一个仓库外的示例包提供 agent 文件、原生插件工具和脚本模块；使用公开 SDK 启动；模型发现能力并编写至少两轮 self 脚本，根据结构化工具结果及 SQL 历史选择下一步；在子调用结果提交、父脚本尚未消费时结束进程；重新打开后沿用原调用记录和模块源码，安全继续并得到可检查的产物。

## 让复杂状态少出现

干净代码的目标是减少每次变更必须同时理解和维护的状态。新增一个管理器来容纳旧分支，只改变代码位置，不能算实现这个目标。

| 当前需要手工协调的事情                   | 目标写法                                                               | 应消失的工作                           |
| ---------------------------------------- | ---------------------------------------------------------------------- | -------------------------------------- |
| 每个调用方猜测执行是否被接手、该不该取消 | 执行留在实际所有者的 scope；调用方只持有观察资源，明确停止走执行所有者 | SDK 的第二套归属判断与相互通知回调     |
| 在已有 scope 内再手建同寿命的 scope      | 在现有 `Effect.scoped` 内获取资源，由已有 finalizer 释放               | 重复的 make、close、provide 和退出分支 |
| 正常的父运行重定向经过 throw/catch       | 在持有 claim 的原决策处返回互斥结果；调用方直接处理结果                | 专用异常类型、包装和拆包链             |
| 为工具或脚本变化维护旧执行接口           | 保留原调用输入、结果和源码；恢复入口只判断即将产生效果的调用           | 对所有历史逐个适配当前工具接口的工作   |
| 为新 goal 流程增加引擎分支               | 用普通脚本组合已有能力并返回结构化结果                                 | 核心中的任务策略状态与专属调度分支     |

互斥的决定用明确的结果分支表达，阶段不同的数据由各自阶段产生；不要让任意组合的布尔值成为一个跨层协议。可从已提交事实推导的状态，消费者读取现有结果，不再维护镜像。一次授权、一次执行归属判定和一次结果提交，各自只保留已有的一个权威边界；这不要求新增统一 facade。

副作用已发生但结果未保存时的不确定性仍然存在，由既有调用恢复边界明确处理。普通工具作者只声明该操作的权限和重放语义，不需要自己实现一套恢复过程。相同原则用于数据：存储表示保持稳定，执行代码的变化不自动变成数据迁移。

用三种日常变更检查这个设计，而不只看文件数或代码行数：

- 新增一个使用现有能力的普通插件工具，只改工具、贡献声明和相应使用场景；无需修改 resume、SDK 交接或核心存储版本，也不必为普通调用额外注册 `plugin.fact`。
- 改写 goal 的循环、分工和 context 策略，只改脚本与结果消费；无需给内核增加策略状态。
- 更换或移除执行 backend，只改当前执行适配；已有原调用仍可读，不为此更新多个历史事件版本。

如果这些变更仍需同时修改上述核心路径，当前边界就尚未收敛。只有引入真实的新资源或新的持久事实时，才论证新增状态，并在同一实现中删除被替代的路径。

## 调用和持久化契约

### 从调用产生事实

跨恢复边界的操作必须有稳定身份，并能关联调用者、被调用能力、实际输入、尝试及结果。优先由现有 run、response、call 和 attempt 身份表达；只有证明现有身份无法表达必要语义时，才增加持久字段。

这里的“调用”包括模型请求、工具执行、子 agent，以及需要持久保存结果的 context 操作。普通函数、局部变量和临时计算不要求逐条保存。外部输入、用户决定和资源所有权中无法从调用结果推导的事实，继续保留自己的明确记录。

| 持久事实                     | 恢复行为                                           |
| ---------------------------- | -------------------------------------------------- |
| 尚未提交执行意图             | 按正常授权和调用路径决定是否启动                   |
| 已有可复用的结果             | 返回原结果，不重复执行原调用                       |
| 已提交意图，结果缺失         | 按该操作的恢复契约处理；不能推断为未执行或失败     |
| 子调用仍由父调用持有         | 重新关联原有子调用和结果，不因恢复另造一棵子运行树 |
| 实际代码或依赖与原执行不兼容 | 保留历史，阻止直接续跑，并说明不匹配的依赖         |

结果缺失的调用，只有工具与具体调用均允许安全重放时才自动重放。其余沿用结果未知的语义，交还模型处理；后续新调用仍经过正常授权。不得为此新增默认的“重跑或跳过”人工确认流程。

### 自由脚本的恢复边界

脚本恢复必须能识别同一调用，并校验能力、输入和执行契约。不能仅按“这是第几个调用”复用另一个调用的结果。

已开始的脚本必须保留或可定位实际执行的代码与模块内容，并保存足以检查兼容性的身份或摘要。当前 `tools.offered` 已按内容摘要保存模块源码，恢复使用已保存的版本；继续沿用这个边界。后续新 step 可以采用新版本，不要求整个长会话固定依赖。影响恢复的时间、随机值、外部读取等输入，要么经过可记录的能力入口，要么明确使该段执行不可自动重放。不新增第二套模块快照、调用日志或运行引擎。

数据库保存需要跨进程保留的事实。fiber、scope、订阅、锁和临时执行栈属于运行时资源；重构这些资源通常不应触发数据库格式变化。

## 运行所有权和 Effect

每项资源必须能回答：谁创建、谁持有、谁可以停止、谁等待回收。代码要从资源的实际所有者得到答案，避免调用方维护第二份生命周期判断。

| 边界         | 必须成立的规则                                                                                           |
| ------------ | -------------------------------------------------------------------------------------------------------- |
| 启动和交接   | 对外返回 handle 前发生失败或取消，不留下无人持有的执行与订阅；已被其他调用者合法接手的共享执行继续受管理 |
| 加入已有运行 | 结束自己的等待不等于停止共享执行；两种操作在公开 API 中可以区分                                          |
| 运行停止     | 由持有执行的层发出停止；正在等待的授权、队列和外部进程按各自资源契约退出                                 |
| 业务结束     | 结果和必要的持久事实完成提交后，对外报告业务结果                                                         |
| 资源回收     | 独立确认 fiber、数据库 claim、订阅和子进程已释放；业务结束不直接等同于回收完成                           |
| 关闭 session | 持有的工作停止或完成交接；回收超时必须报告未释放的对象                                                   |

### Resume 的职责和删除顺序

当前 `ResumeRunResult` 同时返回 `started`、`delivered`、`outcome` 和另一个 `completion`；SDK 又通过 `joined`、`cancelled`、启动的 fibers 和回调参与执行归属判断。问题是跨层协议，不是这些字段天然重复。首次启动与恢复已经共用运行循环，成功启动的 root/child 也都已有必需的 completion，继续保留这两点；#14342 已关闭，不重复实现 completion，未移入的回归证据仍需单独验收。

| 职责               | 唯一负责的边界                      | 对外含义                                      |
| ------------------ | ----------------------------------- | --------------------------------------------- |
| 确定恢复哪个运行   | 在数据库 claim 内判定归属与恢复条件 | 正常返回启动、加入、跟随父运行或拒绝的决定    |
| 建立执行归属       | 现有执行所有者                      | activation 提交并完成交接；明确谁能停止该执行 |
| 交付指定输入       | 既有输入队列和已提交的轮次事实      | 本次捕获的输入批次已经到达约定的消费边界      |
| 等待业务结果与回收 | 运行所有者及其 scope                | 业务结果、观察者退出和资源回收分别完成        |

这些是职责边界，不是四个新服务或状态管理器。优先由现有执行、队列及 scope 直接承担；结果类型表达阶段差异，不再增加一层对它们的同步。

SDK 只持有自己的观察资源，不再通过回调和跨层 joiner 查询解释共享执行该不该继续。调用者退出等待与 session 关闭仍有不同语义。现有两个 joined 值分别表达“我是观察者”和“已有其他观察者”，不能不经替代直接删去其中一个。

按以下顺序清理，每片删除它替代的旧路径：

1. 利用 `resumeHere` 已有的外层 scope 持有 claim，删除没有独立关闭时点的手建嵌套 scope；保留 claim 的完整持有期。
2. 将 `ownedBy` 作为正常恢复决定，删除 `OwnedByParent → RunFailure → catch → follow` 的异常往返。归属判定仍在 claim 内，重定向前的监听必须回收。
3. 将共享 attempt 的取消与观察者规则收回现有执行所有者，同片删除 SDK 对应的取消回调、身份回调和 joiner 查询。
4. 由既有已提交事实提供输入批次回执，等价替代后删除贯穿 resume、执行入口和循环的 `onIdle` 通知链。不增加持久化 resume-status 表。

输入回执有一个必须保留的边界：它针对本次捕获的非 model-switch 输入，运行未结束时，等待 idle/turn boundary 且该批次已离队；若运行先结束，则根据该批次是否仍排队判断送达；不是“整个队列为空”，也不是单独一条 consumed 记录或“当前 phase 为 waiting”。同一提交可能结束上一轮、消费下一批并进入 `turn.ready`。后来追加的输入不能改写原批次回执；运行提前结束时仍要区分未送达的输入。输入回执不再借用业务结果字段表达。

`RunRegistry` 中的数据库 claim、FIFO 等待和子运行结果投递有真实职责。保留这些职责，逐项证明哪些字段重复表达同一事实。把 `Map` 改成 `Ref`、字段换名或拆文件，都不单独算完成。

异步资源使用 Effect 的 scope、fiber、队列和 finalizer。不可中断区需要对应明确的提交或资源交接步骤。当前两个 `AbortController` 常驻点有既有裁决；删除它们必须在同一切片证明外部进程取消、结果投递与收尾仍正确，并同步修订裁决，不能机械清零。

### 2026-10-28 设计评审：激活即尝试，`Run` 即视图

对上述四片做过一次对抗性评审（只读，基于 `ea6e1e2` 及 #14355、#14356、#14363 的 diff）。方向不变：进程内由 `RunRegistry` 的运行记录作唯一所有者。但四片按原样实施会留下两处结构问题，并漏掉一个现存缺陷：

- **另起一条“恢复尝试”记录，会和已有的 activation 记录描述同一件事。** 恢复时两者都从准入覆盖到 generation 退出。更简单的做法是：`launch` 与 `resume` 一被调用就打开 activation，它本身就是这次尝试，携带准入结果（启动、跟随父运行或拒绝）、等待者计数、是否已交出句柄以及输入回执。第二次启动或恢复同一运行时加入它，而不是回答 `RunLive`。
- **SDK 的 `Run` 仍然自己持有运行纤程、drain、spawned、trace 缓冲和 `sdk/${runId}` 订阅端口，是第二个所有者。** #14356 的 `replayTrace` 与 #14363 的已存结束已经把事件和结果移到会话事实上。终态是 `Run` 只作为（session、runId、activation 提交号）上的视图：`result` 读该 activation 之后的第一个结束行，`events` 重放，`interrupt` 即 `run.stop`（原因 user），与 `serviceSession.ts` 的形状一致。
- **现存缺陷，已核实：** 恢复处于决策阶段（`resumeQueuedToolUse` 调用 `start` 之前）时，注册表里还没有该运行的记录，`run.stop` 走 `RunRegistry.stop` 的无主分支并写下 cancelled 结束；认领按计数共享，恢复随后照常激活这个已被取消的运行，用户的停止丢失。
- **另外三处 R3/R4 缺陷：** 第一个调用方在准入前被中断时，第二个 SDK 恢复者会被连带中断；有加入者时离开的启动方会留下无人持有的纤程；`Inbox.wake` 只观察而不加入恢复尝试，等待者都离开后唤醒会丢失。

等待者规则：交出任何句柄之前，最后一个等待者离开即停止；交出之后，只有显式停止或关闭 session 能结束运行。这正是“对外返回 handle 前发生失败或取消，不留下无人持有的执行”。

切片顺序与估计（生产代码净行数）：

1. 进程内存活只留一个答案，删除 `RunHandle`：已由 #14373 合入（−151），并修复刚启动的子运行被 kill/wait 视为不存在。
2. 输入回执读 activation 之后已提交的行，删除 `onIdle` 链、手建 `Latch` 和未使用的 `outcome`：已由 #14377 合入（−24），新增 R13 回归用例。实施时纠正了两点：行的 `commit` 是逐行插入序号而非事务号，按提交号比较会在 R13 场景挂起；回执通过既有 `applyRunRow` 归约读取，不新增行读取方。
3. 落地 #14363、#14356。#14355 由第 4 片整体取代（`ownedBy` 成为准入结果的一个分支，不再需要 `handOver` 的泛型）。
4. 激活即尝试：删除 `Resumes`、joiner 重取 claim、`onJoined` 回调（改为返回 `joined` 值）、SDK 的 `resuming` 与 `starting` 表、`Inbox` 与 `SessionRequests` 里的 `resumes.*` 和双重 fork（约 −150），同时修复上述四个缺陷。
5. `Run` 即视图，并入 `Run.interrupt` 改走 `run.stop`（约 −160 至 −200；若保留 #14356 的首读缓冲约少 90 行）。

## Agent 文件和 imports

Agent 文件是可复用的 persona 和能力配置。inline 定义与文件定义进入同一解析和执行路径。文件形式本身不需要被替换。

Prompt 模板与脚本代码是两种组合方式。1.0 保留参数化 prompt 和已注册脚本模块；模板解析不执行任意代码，代码模块在同一个受控环境内运行，通过已授予能力产生副作用。当前模板 loader 不支持 include，脚本 resolver 拒绝相对路径；不能把新增这两套解析能力写成已有能力的整理。

已注册模块必须有确定的来源和缺失时的明确错误。恢复已经开始的脚本使用原模块源码；后续新 step 可以读取更新后的模块。将来增加工作区 import 时，再同时交付相对路径、越界和循环处理规则，不提前建立无人消费的 resolver。

模块来源关联贡献插件；执行内容通过已保存源码及其摘要固定，恢复所需能力另行检查兼容性。导入模块不会扩大调用者的工具或文件权限。远程依赖安装和运行时任意包解析留到后续版本。

## Codemode 和 goal

模型在 codemode 中可以发现工具、检查输入结构、发起调用、处理返回值、组合并发，并调用子 agent 或 `self`。工具和模块的接口要足够清楚，使模型能够在一次失败后根据结构化错误修正代码。

`self` 的语义必须公开：使用哪个 agent、继承哪些工具和权限、context 从何处截取、是否复制待处理输入、结果如何返回。默认行为可以简洁，但调用者必须能明确选择需要的 context。

默认 goal 是一段可查看、可修改、可替换的脚本。循环次数、分工、context 选择、总结和完成判断属于脚本策略；内核提供可取消的调用、预算执行、输入和结果。自定义策略不能绕开这些约束。

默认 goal 至少返回可程序判断的完成、需要用户输入、调用失败、缺少有效 verdict、费用阈值停止等原因。当前这些暂停原因被折叠成 `paused` 和 report 文本；修复应增加明确的结果语义，而不是新增 goal scheduler。完成判断需要引用实际产物或检查结果；一次模型自报完成不能替代验收。暂停后的继续策略和 context 必须明确，不依靠内核暗中新增一轮。

现有 `self` 默认 fork 脚本开始时的 context，goal 通过上一轮 report 传递进展；它不会自动继承每一轮全部新对话。P0 用 fork 与 fresh 等已有选择验证两种脚本策略，允许模型修改循环、分工和报告内容，不硬编码任务流程。

业务上的暂停与运行时挂起分别表达。脚本返回 `paused` 不自动意味着还有一个可恢复的存活 fiber；继续工作通过明确的新调用或受支持的恢复入口完成。

预算必须说明度量、作用域和检查时点。整棵运行树的预算、单次脚本并发限制和每轮后的停止条件分别表达。当前 goal 在轮次之间检查花费，这属于停止启动下一轮的阈值；1.0 不能把它描述成正在执行的调用绝不会超出的费用硬上限。

“Everything as a plugin”的验收对象是扩展能力。内核的授权、调用身份、持久化、资源回收和恢复约束是所有插件共同遵守的边界。

公开接口必须覆盖示例所需的工具、脚本模块、版本化事实及其发现和使用。Agent 文件可以随包提供，通过公开 `nodePlatform({ agentsDir })` 加载；`agentBlock` 是任务配置块，不应被写成 agent 模板发布接口。

| 接入形式             | 当前能力与 1.0 范围                                                                    |
| -------------------- | -------------------------------------------------------------------------------------- |
| 原生 `Plugin` 贡献包 | 工具、process/session layer、持久化 arms、脚本模块与任务配置块；本次完整路径采用此形式 |
| 安装式 manifest      | skills、commands、agents、MCP 和 hooks；不承诺原生脚本模块与持久化 arms                |

### SQL 的能力范围尚待决定

已确认的问题是现有 SQL 只提供展示历史，能力范围过窄。不能直接把当前限制冻结成 1.0 的最终边界。当前实现是只读的内存副本，尚无业务表写入口；具体读写范围仍需确定。

目前确定的改进是结构化返回：脚本直接获得列、行及限制信息，不必解析展示文本。进一步开放完整调用事实、允许模型维护自己的业务表，分别作为待评估的范围选择；后者尚未得到确认，不列为已经决定的 P0 要求。

范围收敛前，不预建业务数据库、每表 schema 注册或 SQL 迁移框架。SQL 最终方案应说明数据来源、读写权限、持久化、事务与结果未知的行为，并复用既有调用和资源管理边界。

## 最小存储契约

**旧调用是什么，就一直保存成什么；新代码能否继续它，另行判断。** 数据库设计首先减少需要兼容的变化，而不是要求所有能力都有版本号、迁移链和旧接口适配器。

1. **沿用已经记录的事实。** 现有调用身份、父子关系、attempt、原始输入输出、附件和内容摘要是存储基础。完成的调用复用原结果；脚本使用已经保存的模块源码。不再建一套 call journal，也不保存整个执行对象图。
2. **执行变化通常不改变存储格式。** 更换 provider、工具实现、agent 策略或插件，本身不触发数据迁移。历史 `{ path: "a.txt" }` 不必转换成新工具的 `{ uri: ... }` 才能读取；需要再产生效果的调用，才检查当前权限、输入和重放条件。不承诺永久运行所有旧环境。
3. **只处理真实的存储变化。** 保留现有格式标识、schema 校验和旧程序拒绝误写新库的保护。只有持久表示的结构或含义确实不兼容时，才对受影响的一处提供必要转换；兼容新增字段、可重建投影和可独立保存的应用数据变化不自动产生核心格式版本。

这仍要求调用身份、结果边界、费用和附件完整性正确，不能把无验证 JSON 直接交给授权或恢复决策。历史读取得到支持期内的原事实；无法执行时给出原因。缺失插件时，历史入口提供原事实的身份、未解释原因和原始 payload，不静默丢内容，也不将未知内容当作已解释的执行状态。

当前需要优先解除的耦合是：`rowVersions.ts` 因移除 provider 升级多个历史类型；缺插件的事实只留在库里而被普通读取略过。`current_value` 共用版本号也不意味着现在必须引入 family 版本框架；由值的 owner 保持已存值可解释，真实变更发生时选最小局部处理。应用设置不用全部改成事件。

1.0 保存少量覆盖实际契约的真实调用样本，并沿用现有冻结检查。发生存储变化时补充受影响的样本；验收历史可读，并分别验证可继续的调用和应明确拒绝的调用。取消逐应用版本的完整恢复矩阵，以及预先为每个 family、工具或插件建立版本机制的要求。任何实际数据转换都必须验证失败不覆盖原值，不影响无关数据；没有转换就不创建迁移工程。

物理库格式真正变化时，才交付对应升级步骤。现有 writer gate、claim 和投影事务继续保护核心库；不通过跳过校验实现宽松读取。不要求旧程序理解任意未来格式。已有 [Storage v1](../../implemented/architecture/2026-09-28-storage-v1-design.md) 的历史保留与校验约束继续有效；本提案收窄的是本 PRD 额外施加的版本机制和普遍续跑承诺。

### 运行结束只有一个公开结构

`origin/main` 478ab1b 上，“运行如何结束”有五个结构：存储行 `RunEndRow`、trace 事件 `ResultEvent`、`RunEnd`、`RunEndResult`、`RunResult`。`Run.result` 返回 `RunEndResult`，只从 `./schemas` 导出，错误是未分类的 `RetryErrorInfo`；而失败的根运行实际以只含 message 的 `RunFailure` 失败，分类后的错误到不了接入方。README 所说“唯一结果结构、失败时带结构化错误”两处都不成立。恢复时 `resumeRun.ts` 又把已分类的结束转回未分类结构，丢掉错误种类。

决定：

- **唯一公开结构是 `RunEnd`**（outcome、已分类 error、usage、output），它已从根导出并交给插件。`Run.result: Effect<RunEnd, RunFailure>`。
- **已存的结束一律是值。** 失败与 #14363 的取消一样作为值返回，携带 `error.kind`。`RunFailure` 只表示“这次 activation 没有可读的结束”：结束未存下、读不出，或运行从未开始。
- **分类只在 lifecycle 一处。** 循环交给 lifecycle 的是内部未分类报告（`RunReport`），不是第二个结束结构。
- `RunEndRow` 作为存储格式不变，golden 样本不动。

切片（生产代码净行数为估计）：

1. S1：`Run.result` 返回 `RunEnd`；service 的 `task.ended` 发整个 `RunEnd`（协议升版）；删 CLI 的 `readCliRunOutcomeState`；`RunEndResult` 退出 `./schemas`；改正 README（约 −60/+15）。与 #14356 同改 `runHandle.ts`，在其后变基。
2. S2：内部报告更名 `RunReport`，删 `buildTerminalRunEndResult`、`memoryMisses` 副本（已存于开场事实）和重复的子运行花费累加（约 −35/+8）。排在 S1 之后，宿主不会看到更名。
3. S3：删 `resumeRun.ts` 中已分类到未分类的反向转换（约 −10）。
4. Stage B 第 5 片只改 `result` 读哪一行结束，不再改类型。先改类型可避免第 5 片从行重建未分类结构再删一次。

风险：所有 `run.result` 调用方须逐个核对，依赖“失败即失败通道”的地方编译器不报；CLI 结果 JSON 在失败时新增 `error`，`memoryMisses` 在 S2 后消失。texra-action（`src/lib/cliResult.ts`）用宽松对象只读 outcome、response、files、cost 等字段，两者都不影响它。`RunEndErrorSchema` 的 `message` 改为必填需升 `run.end` 行版本，单独成 PR。`RunResult` 是否退出公开 `RunRecords` 取决于 `history show --json` 是否是冻结契约，暂不做。

**实测修正（2026-10-29，`peer-mechanisms-2026-10-29.md`，基于 66d165b）。** 机制 3 的线协议是主要缺口（但“不改存储格式”须按契约 4 证明后才成立）：`followup.queued` 与 `followup.consumed` 已存 `followUpId`，收件箱已按投递 id 去重，缺的只是线协议（`followUp.send` 不收 id、答复不回 id），它是 API 冻结项。真正的大头是机制 2：“该写结束了”在 8 个调用点判断，`RunEntry` 用 6 个可选字段表示所有权；按一个所有者联合类型收口约 −340。机制 1 约净删 60，价值在消灭一类缺陷（5 处读策略、shell 钩子只能拒绝）；`Plugin.decision` 与设置 `onWrite` 不是调用前闸门，不进链。机制 4 只涉及计划用的 `run.fact`（7 类 `current_value` 是进程或全局状态，不随分叉），约 −20 至 −40，退役 `run.fact` 进格式批。机制 5 的边检查已存在（`subsystemEdgeRatchet`）但按裸目录名计、只拦新的有向边，12 处反向依赖藏在已允许的 `agent→tools` 边里；改为按包与目录记并数每条边的名字。实测后否决：pi 的单一 `commit(tx)` 写入口（已只有一个发布者）、pi 的存储一致性套件（只有一种实现）、DeepSeek 的工具管线分段（`execute` 已按段执行）。

**四个契约（2026-10-29 评审修正，先定契约再实现）。** 架构以“更少的独立决定”为目标，而不是更多更窄的模块；行数不能证明设计正确。

| 关注点             | 唯一权威                                                    | 其他地方消失的                                            |
| ------------------ | ----------------------------------------------------------- | --------------------------------------------------------- |
| 已记录的历史与结果 | 现有会话日志与归约器                                        | 重建的结局、复制的完成状态                                |
| 执行与资源释放     | 现有会话运行时；每个正在执行的运行一个有作用域的 activation | SDK 自有的执行纤程、重复的 claim 管理、彼此竞争的结束决定 |
| 输入与回答的对应   | 从已记录的输入与回合事实推导的精确关系                      | 队列为空的猜测、数模型调用、私有的等待协议                |
| 执行某个操作的许可 | 对实际要执行的输入或拟议改动做的一个决定                    | 各工具里重复的策略解读                                    |

由此确定：

1. **所有权不是联合类型。** `Root | Child | Resume | Hold` 不互斥（子运行可被恢复；hold 是持有 claim，不是谁拥有执行）。持久的父子关系（`run.start.parent`）与临时的执行生命周期（activation 作用域）分开；“恢复”描述执行如何开始，不是另一种所有者。
2. **怎么结束只有一处决定**，比“一个写 `run.end` 的函数”更强（该函数已存在）。根运行、子运行、启动失败、显式停止、会话关闭都得到同一个关于持久结局的决定；不把现有分支搬进一个大注册表。四种操作含义不同，不能合并：取消等待只释放这个观察者，执行不动；显式停止请执行所有者停下，写取消结局；关闭会话或进程只释放本地执行，未完成的工作保持可恢复；中断后的恢复按已记录事实和重放策略重建。子运行结果与父运行投递在同一事务提交、释放子运行 claim 之后才唤醒父运行（`runLifecycle.ts` 收尾事务、`childRunLoop.ts`），这一顺序保留；DeepSeek 把两者分成两步（先刷盘、再通知内存里的父对象），崩溃在中间时没有恢复保证，不学。在纤程启动前被拒或被停的启动也要完成清理。连续 activation 之间的互斥保留；只有重构去掉这层互斥时，才需要显式的 activation 校验。**验收标准：改变运行怎么停止，只改一处，所有调用方继承正确行为。**
3. **`Run` 只观察，不拥有执行。** 读事件或等结果获取观察资源，取消等待只释放这些资源；显式停止走会话的 stop；本地与远程含义相同（#14395 即此）。
4. **输入回执不是回答回执。** `followup.consumed` 实测有 8 个写入点、9 种含义（2026-10-30 按 `consumedRow(` / `consumedRows(` 调用点逐一核对）：文本并入新回合或运行中的回合（此时还没有回答）；过期的子运行通知不投递就消费；子运行的提示或投递被 `run.report` / `executions wait` 的结果回答；`/model` 已应用或同模型空操作；`/compact` 已应用或无可压缩；运行收尾只消费剩余的**控制**请求，不消费未读文本（`consumedRows` 无 kind 时按 `control` 过滤，`rows.ts`）；关闭输入清掉剩余控制与过期通知。消息回执须区分“已接收”“已并入回合”“终态：回答的引用，或未回答及其原因”；控制回执区分“已应用”与“已取消或被拒”。关闭本地进程本身不让可恢复的输入变成未回答。多个输入可共享同一个回答（pi 的多对一），不假装一问一答。等待读已提交事实，并覆盖“读完到订阅之间”的间隙；`restsWith` 现在等批次离队后的等待位置，换成“一消费就算”会削弱它。先定语义，再抽公共等待函数。

   加调用方 id 之前要定两个重试规则：(a) 确认丢失后重试仍能找回原回执，即使输入已关闭：`Inbox.admission` 现在先查关闭、后查重复，公开重试须先找回已接收的操作（保留访问检查）；(b) 同一 id 换了内容：返回同一规范化请求的原回执，内容冲突则明确拒绝（pi 是一律返回首次提交）；id 的作用域是运行加请求种类，比较存储的语义请求而非序列化顺序。承诺“不改行格式”之前，须证明在批处理、失败、恢复下“输入→回合→回答”的关系无歧义；已有 id 只证明输入身份。

5. **许可针对实际执行的操作。** 顺序：原始操作 → 记录钩子结果与改写 → 校验最终操作 → 对它许可 → 持久执行意图 → 执行同一个操作。保存两个值：原始发出的输入（重放身份）与实际被许可、执行的输入。脚本恢复按原始输入比对（`toolUseDispatch.ts` 的 `ScriptDiverged`），若用改写后的参数覆盖记录，忠实的重放会被误判为分叉。恢复从已提交的钩子结果重建有效输入，不重跑钩子；路径检查、命令渲染、许可展示与执行用同一个输入。钩子的 allow 不推翻策略的 deny，许可之后的防护仍可拒绝。文件编辑的审阅在拟议改动存在之后、应用之前，由同一个策略所有者决定；为了取得用户输入的提问不是许可检查。人的答复走现有的持久请求与决定机制（DeepSeek 的内存里的审批续延恢复保证更弱）。
6. **依赖跟随实际生命周期。** 运行从 Effect 取它需要的少数会话服务；不把 `SessionHandle` 换成一打转发服务。保留承载实质行为的服务，只删通往同一所有者的重复路径（修订 C1–C5）。

**推进顺序。** 规则：(1) 不可逆的先做：存储格式在 1.0 冻结前一次做完；(2) 先做能解锁别人的；(3) 先建通用机制再删特例，同一处代码不改两次；(4) 消灭一类缺陷优先于删行数；(5) 便宜的防回退检查先上；(6) 改同一组文件的串行，不相交的并行。

多个视角得出的同一结论（经负责人侧源码复核后修正，并入排期）：

1. **请求入口的两个对应关系**（错误、分层、深模块三份）：`PermissionPayload.kind` 决定允许的 `RequestDecision`；`RuntimeRequest.kind` 决定返回的 `Outcome`。现在 7 种请求与 9 种决定互不约束，两个读取方对同一不可能组合分别读成拒绝与取消；5 种 `Outcome` 让 11 处调用方各自收窄或编造兜底。用现有 schema 与一个入口表达，不加七套方法或类；宿主的答复按已记录的待决请求种类校验后才接受其决定与附带效果（只改 TypeScript 类型不够）；同一改动删掉调用方的不可能分支。排在第 7 步之前，作为回执的前提。
2. **停止只决定一次，含子运行去留**（信息隐藏、改动放大）：“停止优先于运行报告”写在 5 个文件；子运行去留仍在 `terminate`、`endOwnedChildren`、进程内委派的 join（`inBandSubagentRun.ts`，不读停止策略，推断）与两个设置读取方；`finalizeRun` 只回 `{recorded}`，`endActivation` 重算一次。由 `RunRegistry.stop` 决定一次、记在 activation 上，其余读取；`finalizeRun` 返回实际记录的结束，并能表达“尚无结束”：子结果等待投递（`lastTurn.held`）时 `endIn` 有意不写结束；已有结束时带回记录的错误与输出，不回请求的结局。第 4 步下一片。
3. **claim 协议只收重复的那部分**（信息隐藏）：`log.hold(` 有 13 处、7 个文件（不是 3 处），已复核。6 处 `{ends:true}` 不是同一个操作：`letGoOfClaim` 只释放出生时的 claim，registry 的 `claimed` 拥有一代执行的整个生命周期，后者保持不动。只把“无主结束”时的取得移入现有的结束所有者，宿主对“被别处持有”收到有类型的拒绝（CLI 两处解析原始错误）。`deliverHeld` 给 `deliverOne` 一个事务，其中 `endIn` 让子运行的结束与父运行的投递一起提交；可以移动所有权，但不能换成另开事务的调用，否则失去这条被称赞的性质。调用点减少只在同时减少调用方责任时才有用。第 4 步。
4. **授权类别由工具声明，不比名字**（错误、改动放大）：只有名为 `bash` 且声明 `guard.bash` 的工具得到 `bash` 操作（shell 授权）；MCP、Codex、Claude、SendToTerminal 等声明 `guard.bash` 的工具得到 `call` 操作，只共用命令样式的确认界面，不得 shell 授权。问题是授权类别靠名字决定，第二个真正的 shell 工具得不到会话授权。改为工具声明类别，并保留这个区分，不让每个命令样式的工具都获得 shell 权限。公开插件接口，冻结前、#14413 之后。已决定（2026-10-30，取推荐项，三个设计比较）：A，工具自己声明类别，循环读 `guard?.command?.grant ?? 'call'`，删 `toolGuard.ts` 的 `SHELL_TOOL` 与名字比较；B（按守卫能否说出目录推导）否，`claudeAgent` 没声明 `cwd` 会默默获得 shell 授权；C（名字检查搬进插件或 `Plugin.shellTools` 列表）否，仍是名字比较、两处说同一事实。拼法：`ToolGuard.command` 收拢 `{ text（原 `bash` 函数）, grant?: 'bash', cwd?: 'unknown' }`，因为 `cwd` 本就只在有命令时被读，嵌套把隐含依赖变成结构，`ToolTypes.ts` 接口成员 37 到 36（平铺加字段会到 38，棘轮不许）。只有 `bash` 声明 `grant`，`send_to_terminal` 自己的说明写着不得用来绕过 bash 审批，所以不拿。#14457 已合入（e44882877b），行与线上格式不变，行为不变，源码净 +22（多数是嵌套成员的 TSDoc）；bot 留一条 minor：`OPERATIONS` 注释里的 `guard.grant` 应为 `guard.command.grant`，随下一个动 `toolGuard.ts` 的 PR 改。

| R23  | 旧 activation 收尾时新 activation 启动；观察者取消等待                              | 旧的迟到写入与清理不影响新执行；取消等待不停止执行                                                        |
| R24  | 持久提交成功、发布失败                                                              | 已提交事实为准；调用方看到失败，不假装回滚                                                                |

若交付内容实际包含数据转换，额外验证失败不覆盖原值、不影响无关数据；无实际转换时不创建迁移任务或预设 family 版本机制。

确定性故障注入用于验证运行契约，真实模型用于验证接口是否能被正确使用，两类证据分别报告。真实模型验收至少覆盖两条受支持的模型路线，并记录模型、配置、脚本、调用历史、产物及失败原因；没有实际运行的项目不能标为通过。

发布不要求所有技术债归零。P0 场景全部通过、数据契约冻结、示例可以独立复现，且没有已知会丢失数据、重复产生未知外部效果或留下失控执行的缺陷，才进入发布审批。
