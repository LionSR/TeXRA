Our package, our provider contracts

Proposed @texra-ai/llm

Build from our existing provider code. A configured model executes one provider turn; a portable request carries data. Neither owns the agent’s conversation or tool handlers.

Scroll the diagram horizontally to see every component →

One parser and normalizer serve both collected and streaming generation. Provider-required signatures and operation IDs remain explicit.

A new API, not a facade

generateTurn and streamTurn replace the class-shaped handler contract. The provider implementation is Effect-native up to its actual foreign I/O edge.

The package owns

  • Canonical requests, messages, results and errors
  • Typed provider options and capability checks
  • Request lowering, streams and scoped transports
  • Opaque continuation and remote operation evidence

The application owns

  • History, retries, approvals and tool execution
  • Credential selection, quotas and billing settlement
  • Document files, output markers and compilation

Two real consumers: a helper completion without a SessionHandle, and a durable agent turn preserving Responses or Interactions continuation. Both use the same providers and canonical values.
