# Runs as peers: one provenance edge, three permission scopes, nothing else inherited

Baseline: `main` at `a20cc39310`, with #14251 (the tool-call context fix)
assumed merged where it is named. Line references point into that tree.

## Summary

The owner asked (2026-10-24) whether agents can be "more equal", with one
condition: some permissions are global, and some must be passed down to a
run its launcher starts. This note answers both. Today a child run is one
stored fact (the `parent` on its `run.start` row) plus five consequences that
travel as separate launch options through about twenty files. Two of the four
defects fixed in #14251 were those options disagreeing with the row. Of the
five consequences, one is structural (a call that waits for a result), one
already has a single owner that walks the parent edge (approvals), and three
are choices that can go: tool narrowing, the child-only input rule, and the
`budgeted` flag. What remains is the edge, the approval ancestry, and the
awaited call. Permissions keep the three scopes they already have: the
session's, the launch's, the run's own.

## What exists

### The one stored fact

A child's `run.start` row carries `parent: { id, uid, callId }` and
`parentCard` (`packages/harness/src/shared/schemas/sessionEvent.ts:256,262`).
Nothing else about being a child is durable: everything below is recomputed
or re-passed at launch.

### Five consequences, carried separately

| Consequence | What it does | Carried by | Sites |
|---|---|---|---|
| Lifetime coupling | in-band: the launching call blocks on the child; detached: the result arrives as a follow-up; a stop cascades into children (`runRegistry.ts:723-803`) | `awaited`, the stop cascade | `awaited` in 20 files |
| Concurrency | a native detached child takes one slot of the session's semaphore (`childRunBudget.ts`); in-band, root and process children take none | `budgeted` | 9 lines, 6 files |
| Tool narrowing | a child persona keeps only tools its parent's step offered (`agentToolResolution.ts:195-208`, rule 3); a child naming an MCP server the parent lacks is refused (`childToolRefusal`) | `parentOffered` | 36 lines, 10 files |
| Input | a child launched by `agent` in band, a background script and a shell child declare `userFollowUpSupport: 'unsupported'`; `executions send` refuses them (`send.ts:70`) | `userFollowUpSupport` | set at 8 launch sites |
| Approvals | a child's bypass for a kind is the nearest run in its ancestry that decides it (`resolveBypass`, `approvalBypassKind.ts:143`); a launch may narrow the policy (`APPROVAL_POLICY_LIMITS`); a detach keeps what the edge gave (`grantsKept`) | the parent edge itself | one owner |
| Prompt and loop | a child's memory instructions differ (`memoryPromptSection.ts:34`); a child that errors with nothing queued ends FAILED, and a child's park opens no step (`toolUse.ts:444,452,510`) | `isChild` = `runs.parentOf(runId) !== null` | derived from the edge |

Two of these were the defects. `parentOffered` was re-passed and lost on a
host resume (`resumeRun.ts:304-327`), so a resumed child was treated as a
root; and it was applied to script runs, so a recipe lost the tools its
plugin declared. #14251 patched both inside the existing shape.

### What the approval model already is

Approvals are the one facet that never had the problem, and the reason is
instructive: they have one owner and read the edge. `resolveBypass` walks
`runId → parentId → …` over the view's `runs` and `policy` maps and stops at
the nearest run that decides the kind; `policyLimit` takes the strictest
launch limit on the ancestry; `delegatedChildGrants`
(`tools/delegation/subagentRun.ts:69`) writes a child's own grant when the
launching call was approved for it; `grantsKept` seeds a detached child with
what the edge gave it. Nothing is re-passed, and a resumed child reads the
same rows as a live one.

## Design

### The rule

A run's standing is its own. The only fact a run inherits is the one the
row states, and only along that row's edge: who launched it, and therefore
whose approvals it falls under. Everything else a run has — its tools, its
input, its lifetime — it has because its own definition and launch say so,
not because its launcher had it.

### Permissions: three scopes, as today

The owner's condition is already how the code works; the proposal names it
and promises not to change it.

1. **Session-global**: the project's approval policy (`runPolicy`), launch
   limits below Auto-approve, credentials (`Secrets`), disabled plugins, host
   capabilities. Read live per step by every run. No change.
2. **Passed at launch, along the edge**: the approval a person gave the
   launching call covers the child's work. `delegatedChildGrants` writes it
   on the child; `resolveBypass` finds a human's or a goal's grant on any
   ancestor; a `parent` value defers to the ancestry; `grantsKept` carries it
   across a detach. No change.
3. **The run's own**: `own[kind]` a human set on this run, and its goal's
   grant. No change.

Tools are not a permission. A tool's *use* is gated by approval kinds
(`bash`, `toolEdit`, `superYolo`) that scope 2 already inherits; the tool's
*presence* is a declaration of the run's definition. Narrowing presence to
the parent's set added no protection the approval ancestry does not give,
and it is what broke recipes.

### What changes

**Tools.** A run is offered what its definition and launch declare, under
the session's gates (plugin switch, dependency probe, host, capability,
approval prompts). Rule 3 of `agentToolResolution.ts` and `childToolRefusal`
go, with `parentOffered` and every site that threads it. An MCP server a run
declares is held by the run (`session.tools.hold(declared, root)` already
does this per run). The `inherits` rule for a plugin agent that declares no
tools ("a child every tool its parent's step offered") becomes "the tools a
top-level run of that agent would get": the same list, read from the
catalog instead of the parent.

*Reversal, stated:* the lead ruling of 2026-10-13 (G11), "a child can only
narrow its parent", is withdrawn for persona children. #14251 withdrew it
for script runs; this withdraws the rest.

**Input.** A run takes a message when its input is open, whoever sends it.
`userFollowUpSupport` collapses to the fact it stands for: a one-shot run
(`stopAfterCycle`) has no later turn to read a message in, a conversation
does. The `'unsupported'` value a child launch writes today becomes that
flag, and the admission rule in the run-input proposal
(`2026-10-23-run-input-one-owner.md`, "One admission") drops its
"non-parent sender" refusal: any run may message any run whose input is
open, and a child's delivery to its launcher is one such message, not a
special path. This is the communication facet of "equal"; it lands with
that proposal, which coauthor-cf owns.

**Concurrency.** The semaphore is already per session. `budgeted` says
which launch kinds acquire; the answer is a function of the launch kind
(native and not awaited), so the flag goes and the child-run loop derives
it. No behaviour change.

**Lifetime.** Two things stay, both as operations on the edge rather than
properties of a child: an awaited call blocks until the run it launched
ends (structured concurrency, the one hierarchical case), and a stop on a
run cascades to the runs it launched, because a person who stops a
conversation expects its work to stop. A detached run otherwise owns its
lifetime: it is not ended when its launcher ends, and it may be resumed on
its own, which today's `resumeRun` child branch already does.

**Prompt and loop.** `isChild` stays where it reads the edge for a reason of
its own (a child's memory instructions; a child that errors with nothing
queued ends rather than parks). It is a derived fact, not a passed one, and
is not what this note is about.

### What is deleted

| Element | Lines | Files | Replaced by |
|---|---|---|---|
| `parentOffered` threading and `StepToolInputs.parentOffered` | 36 | 10 | nothing: a run's declared tools under the session's gates |
| rule 3 (`narrowed`, `sameIdentity` use) and `childToolRefusal` | ~70 | 1 + 2 callers | nothing |
| `budgeted` | 9 | 6 | derived from launch kind in `childRunLoop` |
| `userFollowUpSupport` values at launch sites | 8 sites | 8 | the run's own one-shot flag |
| "non-parent sender" refusal in the inbox admission | — | 1 (with cf's proposal) | input-open check |
| `AgentRun`'s `inherits` reading the parent's offered list | 6 | 1 | the catalog |

Kept: the `parent` row fields, `awaited`, the stop cascade, the approval
ancestry, the session semaphore, `isChild` where the edge is the reason.

## Why this is the right size

The owner's rules: fewest elements, one owner per fact, nothing speculative.
The proposal adds no stored shape, no service and no setting. It deletes one
rule, one flag and one re-passed list, and relabels one enum as the boolean
it encodes. The one place "equal" costs anything is the inbox admission, and
that change is a deletion too. Nothing here needs a new fairness or
scheduling mechanism: peers are what remains when the subordination that
had no owner is removed.

## Risks

- A persona child that declares a tool the parent was *deliberately* not
  offered (a switch, a host gate) now gets it if the session's gates allow.
  This is the intended reading: the switch and the gate are session facts
  and still apply; only the parent's accidental set stops mattering.
- A plugin agent with no declared tools (`inherits`) read the parent's
  offered list, which at top level included the parent's run-scoped tools;
  reading the catalog instead drops those. No bundled agent depends on it;
  the change is stated in the CHANGELOG.
- The inbox change widens who may message a run. The approval ancestry does
  not cover messages, so a run could be steered by a sibling. Today a parent
  can already do this through `executions send`; the proposal extends it to
  any run in the session. If the owner wants a limit, it is a session-global
  one (scope 1), not a parent relation.

## Plan

1. `AgentRun`: drop `parentOffered` from `toolInputs`; `inherits` reads the
   catalog; `root` stays for `injectInstalled`.
2. `agentToolResolution`: delete rule 3, `narrowed`, `childToolRefusal` and
   their two callers; update the header.
3. Launch sites: delete `parentOffered` and `budgeted`; `childRunLoop`
   derives acquisition from `awaited`/native.
4. `userFollowUpSupport` → one-shot flag on `run.start` (row version bump,
   pre-1.0: no upcaster), `executions send` and the admission read it.
5. CHANGELOG, DIRECTIONS ledger line, and the ratchet probes that name the
   deleted elements.
6. One E2E: a persona child declaring a tool its parent lacks is offered
   it; a detached child resumed on its own keeps its declared set.
