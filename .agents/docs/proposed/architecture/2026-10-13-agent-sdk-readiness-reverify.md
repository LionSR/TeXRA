## Verdict (unchanged)

The codebase is still well-aligned, and this audit remains a standing program,
not a gap. No autonomous refactor of substance is warranted from this charter.
Three read-only audits this pass — over the *re-consolidated* agent core/run
loop, the model handler, and the logger + SDK surface — found **no wrapper
layer that only forwards, no second run-history writer, no services bag, and no
re-export shim** introduced by the lane-D/lane-G work. A sibling scheduled
scan reached the same conclusion independently: the
`2026-10-11-refactoring-debt-audit.md` (verified 2026-10-12, corroborated by a
second automated reviewer) refuted every structural finding — "this is an
unusually well-refactored codebase."

- **Single live append path confirmed, under the new name.** The one writer is
  now `RunCell.append` (`RunHistory.ts:447`): `SynchronizedRef.updateAndGetEffect`
  that pre-folds candidate rows before publishing and re-folds the published
  rows to return the new `RunState`. Live loop writes all route through
  `cell.append` (`toolUse.ts:311`, `toolUseDispatch.ts:1197`,
  `ModelInvoker.ts`, `FollowUps.ts:359`); the one-time birth of a forked run is
  `forkRun.ts:175`; the service-internal `tx.append` writes only decisions and
  activation rows inside the service. No second writer. `AgentEngine`,
  `SessionBackend` and `runAgent` were removed cleanly — a grep for each as a
  live symbol in `packages/harness/src` is empty, no re-export shim left behind.
- **Model handler has one chokepoint.** The `packages/llm` `Model` is still the
  sole provider-API path. There is exactly one dynamic-dispatch point —
  `construct` in `node.ts:108`, which switches on `configuration.protocol` and
  dynamic-imports exactly one of the five protocol arms — and **no shadow
  per-provider class hierarchy**: ~a dozen providers collapse onto five wire
  protocols via the data-driven `BACKEND_PROTOCOLS` map
  (`providers/providerPlugins.ts`), compile-checked. `bindModel` has exactly one
  caller (`modelAccess/binding.ts:212`). One retry loop (`runInvocation`) with
  two drivers (`ModelInvoker.invoke`, `callModel`); `ModelRetryGate` is an
  orthogonal process-wide credential-cooling coordinator, not a second retry.
- **No services bag.** `AgentRun` is a per-run `Context.Service` carrying real
  captured state; `ToolServices.ts` is type unions plus `ChildRuns` with real
  `launch` logic. Services are provided once at the `executeAgent` boundary and
  read from context — "No services bag, no node fields" holds in code.
- **Logger is one clean pipeline.** Still one path: producers call `Effect.log*`
  + `withLogChannel(channel)`; `effectDiagnosticsLayer`'s `Logger.make` is the
  only adapter and reshapes nothing (`Logger.formatStructured` already carries
  the structured record); one owner renders → redacts → bounds
  (`logSink.writeLogEntry`) before the single host sink. `writeLogLine` is the
  deliberate synchronous seam for the few fiber-less publication points, not a
  parallel logger. Telemetry is app-owned (`packages/texra/src/telemetry/`,
  `@telemetry/*`), not in the harness.

## Strategic note: what "SDK readiness" means here (carried, re-stated)

The model-handler audit this pass restated the architectural framing worth
keeping explicit so a future routine does not re-mine it as a gap: TeXRA's
`Model` interface (`prepareTurn` / `streamTurn` / optional `background`) is a
**turn-executor port the harness drives** — the *inverse* of adopting the
Anthropic Claude Agent SDK, where the agent loop, tool dispatch, compaction and
model calls live below the API boundary and the host supplies only a model
selection and tools. TeXRA deliberately owns its own `runToolUse` loop,
`ModelInvoker`, `runInvocation`/`ModelRetryGate`, compaction, background
submit/observe, and a multi-provider wire layer, because it is a multi-provider
desktop/CLI app, not an Anthropic-only one. "Agent SDK readiness" for this
codebase therefore means **embeddability as `@texra-ai/harness`** (the durable
harness and its extend surface), not swapping TeXRA's loop for the Anthropic
SDK's. That is the direction the whole harness-package-split and durable-harness
program already pursues; this charter should keep measuring against it, and
should **not** propose replacing the run loop with the Agent SDK — the
provider-manifest + five-protocol normalization (`providerPlugins.ts`,
`configuration.ts`) is exactly the part with no SDK equivalent and the part
worth keeping regardless.
