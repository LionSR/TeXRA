# Ownership audits #12424 and #12425: source refresh against main

Baseline: `main` at `6eb322f83e` (2026-09-21). This note refreshes §4
packages B and C of the
[effect-native completion protocol](./2026-09-15-effect-native-completion-protocol.md),
whose citations were last re-measured on 2026-09-18 and have since gone stale.
It does not re-derive §3's definition of completion, or §4 packages A and D,
which still govern. It is an audit, not an implementation order: no production
code is changed by it.

## 2. #12424 — remaining direct Effect host and settings contracts

### 2.1 Remaining Promise-typed internal contracts reached by the native loops: none

`toolUse.ts` and `reflection.ts` contain zero `Effect.tryPromise`, and the
collaborators the protocol §4C named are all Effect-typed now:

- `resolveRuntimeModelConfig` is `Effect.fn`
  (`src/model/runtimeModelRegistry.ts:237`), `buildInitialToolUsePrompts` is
  `Effect.fn` (`src/agent/prompt/PromptBuilder.ts:202`),
  `maybeBuildGoalContinuation` is `Effect.fn`
  (`src/agent/goal/maybeBuildGoalContinuation.ts:27`), and `recordUsage` is
  synchronous (`src/agent/runtime/UsageMonitor.ts:110`); every one is reached
  through `yield*` in `src/agent/runtime/loop/toolUse.ts`
  (`:274`, `:338`, `:673`, `:767`).
- `reflection.ts`'s named collaborators (`buildInitialPrompts`,
  `buildUserRequest`, `runCompileCheck`, `summarizeRound`,
  `resolveBaseFilesForDiff`) are all `yield*`ed Effects; the raw-output writer
  is an Effect over the context filesystem (`:602-641`).
- `childRunLoop.ts`, `executeAgent.ts`, `runAgent.ts`, and `resumeRun.ts`
  contain no Promise machinery, only prose that says "await".

Across `src/agent/runtime` there are zero `Effect.tryPromise` sites. The
`Effect.tryPromise`/`Effect.promise` sites that remain in the tree are
dominated by tool executors, `packages/llm` HTTP transports, and host-frontend
boundaries, with auth adapters (`callPort`, `src/auth/authProgram.ts:24-27`)
and Node/host API wrappers besides (`src/housekeeping/`,
`src/platform/defaults/`, `src/utils/`, `src/skills/`, `src/agent/index/`,
`src/agent/remote/`, `src/latex/arxivProcessor.ts`,
`src/controllers/session/deletionCleanup.ts`) — all adapting genuine foreign
APIs, not internal contracts. This is the acceptance the tracker's "no
internal Promise method merely executes an Effect through an injected
runner" test is about: it now holds.

### 2.2 The one open item: `runAgent`'s launch failure is still a bare `Error`

`runAgentRequest` is typed
(`Effect.Effect<void, RequestRefusal | RunLaunchFailed>`,
`src/controllers/session/hostRunActions.ts:147-156`), and its admission is
session-owned: `runAgent` admits through `runSession.runs.launchRun`
(`src/agent/runtime/runAgent.ts:212`). What remains is the settlement half of
the tracker's "session-owned runAgentRequest admission and settlement":

- `runAgent` still returns `Effect.fn.Return<AgentFlowResult, Error,
ProcessServices>` (`src/agent/runtime/runAgent.ts:109-112`), i.e. a bare
  `Error` channel.
- Each host re-tags that channel into `RunLaunchFailed` at its own edge:
  `packages/extension/src/progressView/extensionHostRequests.ts:255-262` and
  `packages/desktop/src/main/desktopAgentRun.ts:244-253`. The desktop's
  `runValidated` states the same gap in prose (`:90-96`).

There is no remaining Promise shape here; the leftover is a failure channel
typed as `Error` that two hosts independently re-tag. Typechecking alone
accepts it (an `Error` is not an unexecuted Effect), which is exactly why the
tracker's acceptance is a caller audit, not a count.

Those two edges are not the whole caller set: `runAgentRequest` is the
admission wrapper the extension and desktop hosts use, but eight further
direct `runAgent` production callers exist (section 5 enumerates them with
their error sinks), and a channel change must be audited against each one.

**Acceptance check:** the launched run's failure travels one typed tag from
`runAgent` through the host port, no host re-tags a bare `Error`, and the run's
result is presented exactly once — the run's own result event (the SDK's
`Run.result`, `packages/agent/src/effect/sessionPrograms.ts:383-385`) or the
workflow host's `openWorkflowOutput` (`src/agent/runtime/executeAgent.ts:385`),
never once by the port and once by the run.

## 3. #12425 — Requests/Runs session ownership and SDK composition

### 3.1 What is genuinely done

- `Runs` is a session service (`src/agent/runtime/runRegistry.ts:485`), built
  once per session by the session layer
  (`src/controllers/session/sessionLayer.ts:481`) over that session's doors.
- `Requests` is a per-session value, not a tag: `SessionRequests`
  (`src/agent/runtime/runApprovalQueue.ts:371-387`) is built by
  `sessionRequests` (`src/controllers/session/SessionRequests.ts:77-135`),
  whose decision lanes are a local `Map` per session (`:94`), and is reached
  through `session.requests` (`src/agent/runtime/SessionHandle.ts:347`).
- No module-global registry remains: `liveSessions`, `runLanes`, and
  `waitingTermination` have no production references, and `sweepLeftoverRuns`
  takes `session: SessionHandle` and reads `session.runs` / `session.requests`
  directly (`src/controllers/session/sweepLeftoverRuns.ts:25-46`).
- The SDK consumes the same owners. The root entry is Effect-first
  (`packages/agent/src/index.ts:1-21`, #12960) and `Session.start` /
  `Session.request` reach the session's owners, not a parallel path
  (`packages/agent/src/effect/sessionPrograms.ts:295` launches through
  `runAgent` with `session`; `:423` is `handle.requests.request`; `:287` reads
  `session.runs.getHandle`).

### 3.2 Consumers that still bypass Requests/Runs

None in the run/request paths. The one remaining tag-shaped consumer is
legitimate provision, not a bypass:

- `Runs` remains a `Context` tag only so tool bodies that have no session
  parameter can read it (`src/agent/runtime/ToolServices.ts:15`); `executeAgent`
  provides the session's runs into the run context
  (`src/agent/runtime/executeAgent.ts:602`, `:771`).

The only surviving "default session" mechanism is a host-composition fact,
not routing for callbacks or approvals: `defaultSessionRoot` /
`tryDefaultSession` / `initializeDefaultSession` / `teardownDefaultSession`
(`src/agent/runtime/sessionGraph.ts:283-335`) is reached only from the
single-session hosts — the extension
(`packages/extension/src/extension.ts:706`, `:331`) and the CLI
(`packages/cli/src/runtime/initPlatform.ts:350`, `:395`, `:426`, `:447`) —
and never by a request callback or an approval. Two of the CLI's four sites
are lazy rather than init- or teardown-time: the setting slots fall back to
`tryDefaultSession()?.roots` when another root installed the platform before
this init ran (`:426`), and `CliPlatformServices.session` opens via
`tryDefaultSession()` when a command first evaluates it (`:447`). Both are
ambient runtime lookups, and both remain on `main` after #12975 — that change
retired the ambient `platform()` readers (#12421), not the session fallback. The desktop opens one session per
project and has no reference to it. The protocol §4B citation
`SessionHandle.ts:1500` (`currentSession()` / `defaultSession()`) is stale:
those functions no longer exist in production, and `SessionHandle.ts` is 1438
lines.

So the tracker's last open box — "remove ambient/default-session routing in
request callbacks and approvals" — is satisfied by source: approvals and
request handlers all take the session explicitly
(`src/tools/approval/index.ts:21`, `:69`; `src/controllers/session/SessionRequests.ts:95`),
and the GitHub subscription binding takes its owning `SessionHandle` as a
parameter (`src/tools/github/RunSubscriptionRegistry.ts:93-96`). What is left
of the old `defaultSession` vocabulary is the host-lifecycle fact above, which
belongs to #12421's host-composition cleanup, not to a Requests/Runs bypass.

**Acceptance check:** a grep of
`tryDefaultSession|defaultSessionRoot|initializeDefaultSession` shows the three
spellings only in `src/agent/runtime/sessionGraph.ts`, the extension and CLI
composition roots, and `src/test-kernel/support/defaultSessionTestSetup.ts` —
never in a request callback or approval. That satisfies the protocol's
routing box ("remove ambient/default-session routing in request callbacks and
approvals"). It does not satisfy the protocol's removal criterion, which
requires the ambient session fallback itself to be removed in the same change
(`2026-09-15-effect-native-completion-protocol.md:236-240`): the CLI's two
lazy sites above keep the fallback alive, so #12425 stays open for their
retirement — host-composition work tracked under #12421.

### 3.3 What the SDK must reach directly

The SDK's public surface is the `Sessions` service

owner port and the session's own fields directly:

- `openSessionEffect` (`src/agent/runtime/sessionGraph.ts:235`),

- `session.runs.getHandle` (`:287`) for the live handle during the launch

## 5. Verification for the two remaining items

For #12424's settlement item, the caller audit is wider than the two host
adapters. `runAgentRequest` (extension
`packages/extension/src/progressView/extensionHostRequests.ts:255-262`,
desktop `packages/desktop/src/main/desktopAgentRun.ts:244-253`) is the
admission wrapper those hosts use; the direct `runAgent` production callers a
channel change must be audited against, with their result/error sinks, are:

- extension `packages/extension/src/commands/agent/executeCommand.ts:87` —
  post-start failures travel the failure channel without a second log entry
  (`:83-86`); the result is presented via `openWorkflowOutput`;
- extension `packages/extension/src/commands/setup/setupAssistantCommand.ts:320` —
  `onRunResolved` presents the launched run;
- extension `packages/extension/src/frontend/review/AgentReviewService.ts:357` —
  `runtime.runPromise(runAgent(...))` with `openWorkflowOutput` opening the
  final output;
- CLI `packages/cli/src/runtime/executeCli.ts:522` — the invoke wrapper
  returns the run's Effect to the command runner;
- CLI `packages/cli/src/chat/chatSessionController.ts:643` — inside the chat
  command's Effect pipeline, with `onApprovalPolicyDenial` classification;
- desktop `packages/desktop/src/main/desktopAgentLaunch.ts:52` — `yield*`ed
  inside `runValidated`'s program with `catch: ensureError` (`:48-51`); this
  is the body the `desktopAgentRun.ts:244-253` adapter wraps;
- workflow script `src/agent/workflowScript/runWorkflowScript.ts:727` —
  forked via `Effect.forkChild(Effect.suspend(runAgent(...)))` under the
  attempt's `signal`;
- SDK `packages/agent/src/effect/sessionPrograms.ts:295` (`runValidatedAgent`)
  — the launch behind `Session.start`.

The launch's `onRun`/`onRunResolved` callbacks (`src/agent/runtime/executeAgent.ts:369`,
`:414`) and the result path named in §2.2's acceptance check complete the
audit. Several of these sinks classify or present failures themselves, so the
subtype change must not be judged by typechecking alone.

For #12425's routing item, the check is the §3.2 grep plus a search for
`currentSession|defaultSession` in production, which returns only the
host-composition spellings named above.
