# Verbosity has one owner and one scope: the transcript fold. Settings stay synchronous by ruling; the log surface owns its own level.

Winners per judge: Deletion first (module-level globals and pass-through wrappers; one Context.Reference for the Logger) - 18/20, Deletion first (P1), 18 - but it does not ship without P3's transcriptDebug graft, which is the single most valuable item across all three proposals.

## Decision

Take P1's classification (every "synchronous reader" on this seam is already inside an Effect program holding the provider as data, so converting them deletes nothing) and P3's crash-boundary finding (a process-local module slot is frozen into a durable column and replayed as truth), and resolve both judges' fatal flaws by removing the reason an ambient debug-mode carrier exists at all rather than by re-homing it. Effect `Config`/`ConfigProvider` is refused for the settings catalog and recorded as a refuted candidate: `Config<T> extends Effect.Effect<T, ConfigError>` (node_modules/effect/src/Config.ts:108) decodes with Effect `Schema` (Config.ts:1192), its provider is a `Context.Reference` defaulting to `fromEnv()` (ConfigProvider.ts:342) so a missed provision silently answers from process env, and three live readers pass a key the catalog does not own — `readConfig<string>(stores.config, selected.configKey, '')` (src/latex/formatter/texFormatter.ts:74), `ReplacementConfigRead = <T>(path: string) => T` (src/replacement/engine.ts:64), and `call.roots.config.get(input.key)` for a key the model named (src/tools/setup/ConfigTools.ts:81) — so `ConfigProvider.get` stays synchronous on the port and `readConfig` (src/utils/config/configUtils.ts:28-34, a one-line pass-through with 22 call sites) is the whole config deletion. `texra.logger.debugMode` then has exactly one meaning: transcript verbosity plus payload detail. The producer-side level gate (src/logger/effectDiagnostics.ts:20-21 and :53) is deleted because the host surface already owns the live filter — `createVsCodeLogSink`'s own header records that its `LogOutputChannel` supplies "a user-selectable level, and the Output view's level filter" (packages/extension/src/frontend/vscode/vscodeLogSink.ts:4-6) — and `References.MinimumLogLevel` is set per host at runtime build from facts that genuinely cannot change mid-process (surface kind, a new CLI `--verbose`/`--quiet` flag), which is the one place a layer-build capture is correct. With the gate gone, `isDebugModeEnabled` has no reader outside the fold, so `DebugModeConfig`, `setDebugModeConfig`, the module slot and (after the conversion waves) `logUtils.ts` all delete with **zero** new constructs: no `Context.Reference` (P1's `DiagnosticConfig` becomes unnecessary), no `Context.Service` (P2's `WorkspaceSettings`, which additionally captures the level at layer build and cannot be provided at process-runtime build time in any host — every host opens its `JsonConfigProvider` after `installProcessRuntime`, e.g. packages/extension/src/extension.ts:242 vs :281), and no snapshot-republish plumbing (P3's addition for a refresh behaviour that does not exist today). `transcriptDebug` leaves the durable schema, bumping `SESSION_EVENT_FORMAT` 8→9 in the one PR that needs it.

## Design

## 0. The three classes of reader, and which is actually debt

**R1 — a pure function of `(ConfigProvider, input)` whose caller already holds the provider.** Verified: `isGoalEnabled(ports.call.roots.config)` at src/tools/plan/PlanTool.ts:128 and :233, both inside `Effect.fn` declared at :122 and :226; src/agent/goal/maybeBuildGoalContinuation.ts:35 inside `Effect.fn('goal.continuation')` at :27; `postProcessResponse(text, config)` (src/latex/texraResponseTextProcessing.ts:40-41) from src/agent/runtime/loop/reflection.ts:672; `selectAutoOpenFinalOutput(config, result)` from the extension's finalOutputOpener and the desktop's desktopAgentLaunch, both inside Effect bodies; `isTelemetryEnabledBySetting(config)` (src/telemetry/UsageLogService.ts:115), which reads `config.inspect()` across both scopes (:120) — a thing Effect `Config` has no concept of. Making any of these an Effect re-derives from the fiber a value the caller already holds, adds a fiber requirement to a pure predicate, and breaks the injection table's field type for one row (src/agent/runtime/toolInjection.ts:52). **They are the end state, not a facade.** This is the shape src/platform/workspaceRoots.ts:7-13 already rules ("Resolution is by hand, not by ambient scope").

**R2 — a host callback that logs.** Already at an R1 boundary kind (scripts/check-effect-migration-ratchet.mjs:141-146). Its log moves inside the program the callback already runs.

**R3 — the Logger itself.** A `Logger` is invoked by the runtime and has no parameter list to thread into. One fact is read there today: `texra.logger.debugMode`, at src/logger/effectDiagnostics.ts:21 and :53 and src/logger/logUtils.ts:142. **Section 2 removes that read entirely, which is why no ambient carrier is added.**

## 1. Config: one deletion, one ruling, one home for the refused facility

`readConfig` (src/utils/config/configUtils.ts:28-34) is `return config.get<T>(path, defaultValue as T)` under 27 lines of doc. Delete the file; its 22 call sites across 21 production files call `config.get(...)` directly, and the path-convention paragraph moves onto the `ConfigProvider.get` docblock (src/platform/interfaces.ts:55-63), which is where a reader looks for it.

`ConfigProvider.get` **stays**, synchronous, and its docblock says why: one production implementation (`JsonConfigProvider.get`, src/platform/defaults/jsonConfigProvider.ts:48-56, three map lookups plus `getCoreSettingDefault`), a per-workspace value, roots threaded as data, and three dynamic-key readers named in the decision above that `requireEntry(key)` would throw on.

Record `EFF-ADOPT-config-provider` in config/ratchets/refuted-candidates.json (which today holds 13 ids, four `EFF-ADOPT-*`, none on this seam) with the four reasons and the two pinned signatures. Rewrite step 1 and the `grep -r "Config."` acceptance line of .agents/docs/proposed/simplification/2026-09-20-effect-facility-adoption.md; its enumeration of "deliberately synchronous readers" is correct about the code and wrong about the conclusion.

Where `Config`/`ConfigProvider.fromEnv` does belong, so the pressure to adopt it is resolved rather than merely refused: the ~126 `process.env` reads in production. That is a string source, which is what `ConfigProvider`'s `Node` model (string leaves; `fromUnknown` stringifies primitives, ConfigProvider.ts:1038-1041) was built for. Out of scope here; named so a later lane has a target.

Keep one finding from the effect-config lane: a `"false"` hand-edited into a boolean row reads back truthy through `get`'s cast. That is a gap in the **catalog** reader, not a reason for a second decoder — `validateStored` (src/shared/config/settingsAccess.ts:106-118) already warns loudly and falls back to the row's Zod default, so the answer is to route the affected keys through `readSettingFrom` or the config-only `readConfigSettingFrom`, which is what `readConfig`'s own docblock (:19-21) already says.

## 2. Verbosity: the producer stops filtering, the surface keeps filtering

`effectDiagnosticsLayer` (src/logger/effectDiagnostics.ts:71-78) provides three things: the redacting `Logger`, `Layer.succeed(References.MinimumLogLevel)('Trace')`, and the bounded `Tracer`. Two of the three stay as they are. What is deleted is the hand-rolled gate inside the logger:

```ts
const diagnosticLogger = Logger.make<unknown, void>((options) => {
  if (options.logLevel === 'None') return;
  writeLogEntry(Logger.formatStructured.log(options));
});
```

and, with it, `DiagnosticSpan.end`'s `isDebugModeEnabled()` read and its `log.debug` (:50-63) — `Tracer.span`'s options carry no `fiber` (node_modules/effect/src/Tracer.ts:29-43), there are three `withSpan` sites tree-wide, and the attribute clamp and event/link suppression stay because they are a privacy bound, not a log.

**Who filters instead, per host, and why each is correct:**

- **Extension.** `createVsCodeLogSink()` writes to a `LogOutputChannel` created `{ log: true }`, whose own header documents "a user-selectable level, and the Output view's level filter" (vscodeLogSink.ts:1-8). `MinimumLogLevel` stays `'Trace'` so the channel sees everything and the user's own filter decides. This is strictly better than the setting: it is live, per-surface, and already exists.
- **Desktop.** A rotated log file (packages/desktop/src/main/desktopAppLog.ts:42-50). `MinimumLogLevel` `'Debug'`; the file is the artefact you attach to a bug report and rotation already bounds it.
- **Webview.** `installWebviewRuntime` keeps its own `Logger.make` behaviour, including the deliberate ERROR/FATAL→WARN mapping and its stated reason (webviewSessionLayer.ts:85-104).
- **CLI.** The only surface with no live filter. `MinimumLogLevel` is chosen from argv at `defineCliCommand`, before the runtime builds: `'None'` under `--quiet`, `'Debug'` under a new `--verbose`, `'Info'` otherwise. **A flag is exactly the kind of fact a layer-build capture is right for** — it cannot change mid-process — which is the precise distinction P2 missed when it fed a live user setting into the same reference. Adding the flag is a one-line change by the file's own docblock (packages/cli/src/commands/_helpers/globalArgs.ts:10-17).

**The `data` payload stops being a second knob.** `withLogData` (src/logger/effectLog.ts:40-48) exists only to skip `formatLogData` when debug mode is off; its `Effect.suspend` around `isDebugModeEnabled()` is the whole body. Delete it at its 10 call sites in favour of `Effect.annotateLogs(self, { data })` carrying the **raw** value, and move `formatLogData` + `serializeError` (src/logger/logUtils.ts:89-127) into src/logger/logSink.ts, applied inside the write path **before** `redactEntry` — the order is load-bearing, because `redactDisplayValue` walks objects recursively (src/logger/redaction.ts:83-94) while `formatLogData`'s `WeakMap` renders a cycle as `"[Circular]"` (logUtils.ts:110-113). `safe-stable-stringify` then runs only for entries the threshold already admitted, which is strictly cheaper than today. `withLogChannel` (effectLog.ts:28-31) **stays**: 54 call sites, a one-liner whose docblock is this seam's documentation, and inlining it deletes nothing.

Bound the rendered payload at the sink. `detail()` (vscodeLogSink.ts:23-32) already renders every non-`channel` annotation, so an always-attached `data` would flood the Output view; a length cap in the shared renderer, once, is the fix and it belongs with the one owner of payload rendering.

**Result: `isDebugModeEnabled` has no reader left in the logging subsystem.** `DebugModeConfig` (logUtils.ts:37-39), the `let debugModeConfig` slot (:48), `setDebugModeConfig` (:53-55) and its two production installs (src/controllers/hostBootstrap.ts:86, packages/agent/src/effect/runtime.ts:206) all delete with no replacement mechanism — no `Context.Reference`, no `Context.Service`, no second module global. That is the element count P1 and P2 were each paying one new construct for.

## 3. Transcript verbosity: read at fold time, never frozen into a row

This is the defect on the seam, and it is fully verified. src/agent/runtime/SessionHandle.ts:651 stamps `transcriptDebug: isDebugModeEnabled()` onto a durable column (src/shared/schemas/sessionEvent.ts:428-430, "Stamped at publication"). `isDebugModeEnabled` reads a module slot installed by whichever composition root came up first, over _that_ root's config, and returns `false` before any root installs one (logUtils.ts:64-66). Both folds replay the frozen stamp into `TraceStamp.debug` — src/shared/session/sessionFold.ts:1822 and src/transcript/StreamLogStore.ts:60 — where src/shared/session/traceFold.ts:99 **drops** every `debug`-level entry when it is false. A process-local fact, captured at a point where it may be absent or belong to a different workspace, is written into the ledger and read back as truth on every resume and every reload.

The fix removes the column rather than fixing its source:

- **Delete** `transcriptDebug` from sessionEvent.ts:428-430 and the stamp at SessionHandle.ts:651. `SessionHandle.publish` appends the draft unchanged, which also restores the property that a publication adds nothing the draft did not carry.
- **`SessionView` gains `debug: boolean`**, set by `emptySessionView(key, cursor, debug)` (src/shared/session/sessionView.ts:264-276). `fold` (sessionFold.ts:167) reads `view.debug` at :1822 instead of `event.transcriptDebug`. `TraceStamp.debug` (traceFold.ts:49) is unchanged — it is the fold's input and was always correct.
- **One replay policy, carried with the replay.** `sessionInputsLayer` reads `DEBUG_MODE_KEY` through the existing catalog validator over the session's `ConfigProvider`. Its transient `debug` input precedes listing and transcript rows. `SessionFramer` carries that value in `EventsFrame.debug`; `SessionFrames` prepends it to the completed replay batch. The browser never reads configuration or derives the policy from a host snapshot. `HostSnapshot.debugMode` and the callback that formerly supplied it are deleted.
- **Rebuild only when the policy changes.** A subscribe carries the published view's `debug` value beside its cursor and aggregate sequences. The reader compares that value with the sampled setting. An unchanged setting retains incremental reads; a changed setting reads history from the beginning. The decoder also resets aggregate subscription sequences for that replay. The first debug input creates a fresh view when the policy differs, and the complete batch replaces the published view atomically. No second event store, reset flag, or configuration observer is added.
- **Other transcript readers use the same policy.** `SessionHandle.readView` folds the policy carried by the process input reader. The separate `StreamLogStore` projection receives a catalog-validated value from its owner. `readConfigSettingFrom` delegates to the catalog's existing `readConfigSetting`; it does not duplicate a schema or wrap a raw getter without validation.

**Semantics after the change.** A setting change takes effect on the next replay: reload, resume, or a new transcript subscription generation. An ongoing tail retains the policy chosen for its replay. A cold desktop replay does not wait for catalog or host-snapshot publication, and later host frames cannot change its policy. On a policy change, historical rows are rebuilt so both enabling and disabling debug produce a consistent transcript. Settings-change observers remain outside this change.

`SESSION_EVENT_FORMAT` (src/shared/schemas/sessionEvent.ts:588, previously 8) bumps to 9. src/test-kernel/schemas/sessionEventFormat.vitest.ts pins the stored shape and fails a change that leaves the version alone; regenerate its snapshot in the same PR. Every existing `texra.db` is cleared on its next open, which is the documented contract (Database.ts:1352-1384) and the repo's stated position on legacy-format readers — **no tolerant read, no `.catch()`**.

## 4. `createLog` retires, fiberless first

Measured on main: **161 production files call `createLog`; 137 already import `effect`; 24 do not.** The 24 are: src/replacement/{engine,advanced}.ts, src/utils/text/{unifiedDiff,xmlExtraction}.ts, src/utils/system/{execCore,platformPaths}.ts, src/tools/support/externalBinaryUtils.ts, src/agent/trace/{TraceEmitter,channelTrace}.ts, src/agent/review/reviewDiff.ts, src/agent/runtime/agentSettingTools.ts, src/agent/workflowScript/sandbox.ts, src/logger/logUtils.ts itself, four CLI TUI files, and six extension frontend files.

Order matters, and the 2026-09-20 note's order ("convert the easy ones, keep the facade for the rest") guarantees the facade never dies. Do the 24 **first**:

- **Pure functions that log** (unifiedDiff, xmlExtraction, reviewDiff, replacement/*) put the fact in the return type. src/utils/text/unifiedDiff.ts:49 warns that the diff timed out and returns a whole-file replacement — that degradation belongs in the returned value; src/utils/text/xmlExtraction.ts:105 logs the reason it returns `null` while its own comment at :131-132 says the caller owns the recovery and narrates it, so return the reason. This is the repo's own "silent degradation is a defect" answer, not a new convention.
- **Modules that do I/O** (execCore, platformPaths, externalBinaryUtils, sandbox, agentSettingTools) become `Effect.fn`. `src/utils/system/execCore.ts:47` literally declares `export type Log = ReturnType<typeof createLog>` and takes an injected logger as a parameter — the shape `Logger` replaces wholesale.
- **Host callbacks and renderers** (the CLI TUI four, the extension frontend six) sit at R1 boundary kinds; the log moves into the program the arm already runs. Do packages/cli/src/chat/tui/** last: its writes interleave with the Ink frame.
- **`TraceEmitter.emit`** (src/agent/trace/TraceEmitter.ts:71) is the trace plane's one synchronous publication point and must not recurse into itself; it writes the subscriber-threw warning through the sink directly.

**The real last blocker is not `createLog`.** It is `createChannelTrace` (src/agent/trace/channelTrace.ts:31-45), the log-only `AgentTrace` adapter, with six production callers: packages/extension/src/progressView/ProgressViewProvider.ts:173, packages/desktop/src/main/desktopAgentRun.ts:108, packages/desktop/src/main/desktopAgentResume.ts:33, src/tools/github/PollingSourceBase.ts:230, src/agent/runtime/childRunLoop.ts:910, src/agent/runtime/AgentRunLifecycle.ts:48. Each takes `noopTrace` (already exported, src/agent/trace/index.ts:18) plus `withLogChannel(name)` on the surrounding program. Once those six land, `logUtils.ts` has no caller and deletes itself, which is what its own header has promised since it was written (:9-10).

The 137 effect-importing files are mechanical and order-independent: `const log = createLog('X')` → `const CHANNEL = 'X'`, `log.warn(m)` → `yield* Effect.logWarning(m)`, `{ data }` → `Effect.annotateLogs({ data })` with the raw value, and the module's entry `.pipe(withLogChannel(CHANNEL))` — the pattern src/housekeeping/runDirOps.ts:52 and clean.ts:21 already use. The effect-logger lane has ~92 of them done; let it finish.

## 5. The sink becomes a Layer, last

`src/logger/logSink.ts` holds `let sink` / `let sinkTrusted` (:110-111), `setLogSink` (:118-125) and `writeLogEntry` (:128-130). Delete them, with `LogSink` (:34-37), `consoleLogSink` (:78-98) and `silentLogSink` (:106-108). What survives is stateless and is what hosts already use: `LogEntry`, `LOG_CHANNEL`, `entryChannel`, `entryMessage`, `redactEntry`, plus `formatLogData` moved in.

`installProcessRuntime` (src/controllers/session/sessionLayer.ts:1055) gains a required `diagnostics: Layer.Layer<never>` field — **the same shape as the `lean`, `usageLog` and `globalDatabase` layer parameters it already takes** (:1017-1050) — and the hardcoded `effectDiagnosticsLayer` at :1141 becomes it. Each root builds `diagnosticsLayer({ write, trusted, minimumLogLevel })` in place of its `setLogSink` call. Layer ordering is what expresses "the logger exists while the other layers build", and webviewSessionLayer.ts:116-118 already demonstrates exactly that form with `Layer.provideMerge`; put that rationale in the parameter's docblock so a later lane does not reintroduce the global that #12940 reached for four days ago. Note `Logger.layer` replaces the current logger set (mergeWithExisting defaults false, node_modules/effect/src/Logger.ts:1162-1180), so one per runtime.

Ordering per host is already right: packages/extension/src/extension.ts:651 runs inside `activateExtension` (:546) _before_ `initVscodePlatform` (:174) installs the runtime at :242, so the writer exists when the layer is built; packages/cli/src/commands/_helpers/defineCliCommand.ts:123 chooses its sink before `installCliProcessRuntime` at :128 and its :112-124 rationale about covering the layer build is satisfied by construction. packages/cli/src/bin/texra.ts:26 keeps a plain stderr writer function for the pre-runtime window (cite `RT-write-raw-and-wait` and `RT-install-cli-process-runtime`), not a sink.

**This step is last** because it is the expensive one: `setLogSink` is the log-capture seam for roughly a dozen kernel suites through src/test-kernel/support/logSinkCapture.ts:8,:32 — Texcount, ArxivProcessor, LatexdiffShadowStorage, OutputDiscovery, RunLatexdiff, ChannelTrace, DesktopAppLog, processRuntime, ToolsCommand and LogUtils. `logSinkCapture` becomes a helper that returns a `diagnosticsLayer` over a capturing `write`, which is one rewrite for all of them.

## 6. What is deliberately not done

No `Context.Reference` or `Context.Service` for config, roots or verbosity: the 2026-09-19 ruling "The process-roots holder is retired" (rulings ledger :511-539) forbids a second ambient carrier reintroduced to avoid threading a parameter, and after §2 there is nothing left to carry. No `SubscriptionRef` holding a setting value (a second copy of the config store). No `Effect.run*` below a boundary kind — config/ratchets/effect-migration-baseline.json has three rows over seven files and **no `Effect.run*` row at all**, so any below-boundary run fails as a new file. No new ESLint rule, no new baseline, no new kernel architecture test: CLAUDE.md states the open work is shrinking frozen lists, and the PR default is zero new tests. No snapshot-republish plumbing for a refresh behaviour that does not exist today. `processSettingHost` (src/utils/config/platformSettings.ts:25) stays: already ruled, one process is one host, and it is not a shadow of a durable per-workspace fact.

## Primitives

- Logger.make<unknown, void>((options) => write(Logger.formatStructured.log(options))) — the redacting logger with its hand-rolled debug branch removed; Logger.Options carries `fiber` (node_modules/effect/src/Logger.ts:101-107) but this design needs nothing off it, which is the point.
- Logger.layer([logger]) — the sink as a layer, replacing the `sink`/`sinkTrusted` module globals. Replaces the current logger set (mergeWithExisting defaults false, Logger.ts:1162-1180), so one per runtime.
- Layer.succeed(References.MinimumLogLevel)(level) — the emission threshold, now an argument each host passes instead of a hardcoded 'Trace'. A layer-build capture is CORRECT here and only here: the inputs are surface kind and argv, neither of which changes mid-process. It is fiberCached (node_modules/effect/src/internal/references.ts:56-58) and read from fiber.cache before any logger runs, which is exactly why a live user setting must not be routed through it.
- Layer.succeed(Tracer.Tracer)(Tracer.make({ span })) with the bounded span — unchanged from effectDiagnostics.ts:74-78 minus its debug log, because Tracer.span's options carry no fiber (node_modules/effect/src/Tracer.ts:29-43).
- Layer.mergeAll of the three above, exported as `diagnosticsLayer({ write, trusted, minimumLogLevel })`, passed by each composition root into installProcessRuntime / installWebviewRuntime beside the existing `lean` / `usageLog` / `globalDatabase` layer parameters (sessionLayer.ts:1017-1050).
- Layer.provideMerge for the ordering contract 'the logger exists while the layers below build' — the form webviewSessionLayer.ts:116-118 already uses.
- Effect.annotateLogs(self, { data }) with the RAW value, rendered at the sink. Replaces withLogData's Effect.suspend + isDebugModeEnabled (effectLog.ts:40-48).
- withLogChannel (effectLog.ts:28-31) — KEPT. 54 call sites, one line, load-bearing docblock; inlining it deletes nothing.
- Effect.logDebug / logInfo / logWarning / logError — the single logging mechanism after the conversion waves.
- Effect.fn for the src/** modules that hold the last synchronous log calls (execCore, platformPaths, externalBinaryUtils, sandbox, agentSettingTools, replacement/_). No Effect.run_ is introduced anywhere under src/**, so the baseline's absent Effect.run* row stays absent.
- ConfigProvider.get — KEPT, synchronous by contract (src/platform/interfaces.ts:63). Three live readers pass an uncataloged or model-named key.
- NOT USED, deliberately: Config, Config.schema, Effect's ConfigProvider / fromEnv / fromUnknown / layer, Context.Reference, Context.Service, SubscriptionRef over a setting, and any new Effect.run*. See design §1 and §6.
