# Current-value SQLite rows for non-run state

Date: 2026-09-22

Status: accepted 2026-09-22; implementation pending

Audit baseline: `origin/main` `c7df1f69a0ad385df0846c98102380b089aac45e`; #13008 and #13009 merged.

Tracking: [#11867](https://github.com/LionSR/TeXRA/issues/11867), [#12880](https://github.com/LionSR/TeXRA/issues/12880).

## Accepted decision

Use one `current_value` SQLite table for the four latest-value families below, with their writes removed from `event` and `event_sequence` in the same change. This is a bounded-state replacement, not a second authority. Keep the run/session event journal and the already bounded `input_history` table. Do not build a migration, dual writer, legacy reader, or adapter. This decision document makes no schema change.

The benefit is structural: a repeatedly changed application key or inquiry thread currently retains every prior value. The replacement retains one row per live key. The cost is a small direct SQL surface and one write-order column for inquiry listing. No production caller identified below needs the discarded value history. This recommendation is based on source paths and a synthetic storage experiment, not a measurement of real user databases or update rates.

## Contract and consumers at the audit baseline

`SessionEventDraftSchema` admits one `state.value.set` arm. Its `StoredValueSchema` binds four families to their aggregate kind, and `Database.appendPrepared` temporarily claims each aggregate, increments `event_sequence.seq`, appends an `event` row with a global `commit`, then releases the claim. The connection's `BEGIN IMMEDIATE` transaction serializes writes. A successful write advances the local `level` even when no event is appended; the 250 ms `PRAGMA data_version` poll wakes another connection after a foreign commit. `SESSION_EVENT_FORMAT` is 9; a mismatched store is cleared at open under the present 1.0 format policy.

The global service contract deliberately exposes only application records, with no event cursor or reactive reader. Project `Database.readAll`, `readAggregate`, `readInputBatch`, and `readListing` are run/session consumers; they have no identified semantic use for `state.value.set`. `readAll` can presently return the rows because it is a generic journal scan. Removing the arm must be accompanied by checking direct and test-only event readers, rather than inferring from a missing dedicated history API that the arm is unused. `runStateFold` lists it among event types, but produces no value projection. `input_history` is a separate bounded table and is outside this change.

Ownership must stay distinct: global records use the process-scoped `GlobalDatabase` on the shared global root; profile application state uses its own scoped storage path; project application state borrows its project database from `ProjectDatabases`; ephemeral session databases must not become persistent state. A table is created within each existing database identity, not in a new file or connection. The #11867 project-connection lifetime work is independent and may land before this schema change.

## Proposed direct design

Add a strict table owned by `Database.ts` with `family`, `key`, `data`, and `revision`. Constrain `(family, key)` to one row. Assign `revision` as `COALESCE(MAX(revision), 0) + 1` while `BEGIN IMMEDIATE` holds the write lock, including the first write to an empty table; index it for latest-write order. This ordinal is local to current values and is **not** an event `commit` or a session cursor. Deleting the highest-revision app-state row may let a later write reuse its ordinal, so revision is strictly greater than every currently live row's revision, not globally monotonic across deleted rows. Inquiry rows are never deleted, preserving their latest-write order. Deleting an app-state key deletes its row. The remaining three families retain a row while their current record exists. Read and validate `data` against the family's existing Zod schema at the database boundary; a malformed present row fails with `DatabaseReadFailed`, never a default. Keep the public `StateStore`, `UpdateCheckRecords`, `InquiryRecords`, and `DesktopProjectRecords` behavior and their typed error boundaries.

Use the existing transaction helper for direct writes. For application state, retain the per-key FIFO lane and validation before entry. For update checks and inquiries, read and write on the same reserved connection inside one write transaction. Move desktop's read/change/no-op/write into that transaction too; its local lane still admits same-process operations in order. SQLite's `BEGIN IMMEDIATE` serializes competing connections. Preserve the existing successful-transaction wake and `data_version` poll. A current-row write may leave `observedCommit` unchanged, which is correct: event consumers wake, find no new event, and retain their event cursor. Do not fabricate an event to advance it.

Retire the `state.value.set` union arm and `StoredValue` event envelope, `borrowsClaim`, its temporary claim/release branch, the latest-event read helpers for these families, `readDesktopProjects`' event-shaped return, and their `event_sequence` rows. Simplify the application-state writer to a direct database method. Keep run and project inquiry _display_ events; they represent different facts. Update the CLI's refusing global-service shape and architecture tests for the changed interface. Remove compatibility-specific tests for the retired event arm; preserve behavior tests at the durable store boundary.

The event format current at implementation must be bumped with the schema switch. At open, the existing mismatch transaction must drop/recreate the new table along with the event tables and must account for it in the cleared-store report. There is no earlier-format reader or copy. This follows the accepted fresh 1.0 format policy, but clearing the prior format's state is a material consequence to state plainly in the implementation PR. Pre-1.0 legacy files remain untouched.

## Storage experiment and limits

A disposable Python `sqlite3` experiment inserted 10,000 updates to **one** application key into a copy of the current `event`/`event_sequence` table and three event indexes, then into a strict `(family,key)` upsert table. Both used the same compact JSON value and WAL, then checkpointed before `page_count`/file-size inspection. It read or changed no user database. Results on this machine: event model **10,000 event rows, 748 pages, 3,063,808 bytes**; current model **1 row, 3 pages, 12,288 bytes**. This models row growth and index/storage cost for a hot key; it is not a product benchmark. Actual savings depend on key count, value size, update frequency, free-page reuse, and VACUUM/checkpoint behavior. Direct current writes still incur a transaction and WAL write, so this experiment does not establish latency improvement.

Reproduction: in a temporary SQLite database, create the `event_sequence`, `event`, and three event indexes exactly as in `Database.ts`; insert one aggregate; repeat 10,000 `UPDATE event_sequence SET seq = ?` and `INSERT event` operations with `{"state":{"key":"app-state","value":{"kind":"json","value":N}}}`. In another temporary database, create `current_value(family TEXT NOT NULL,key TEXT NOT NULL,data TEXT NOT NULL,PRIMARY KEY(family,key)) STRICT`, repeat 10,000 `INSERT ... ON CONFLICT(family,key) DO UPDATE SET data=excluded.data` operations with the same JSON, run `PRAGMA wal_checkpoint(TRUNCATE)`, then inspect `count(*)`, `PRAGMA page_count`, and file size. The proposed revision/index adds a few pages relative to that deliberately minimal comparison; it does not change the one-row bound.

## Acceptance for an implementation PR

- One current row per live `(family,key)` after repeated writes; app-state deletion removes it; no `state.value.set` or its aggregate/sequence rows are newly written. Run/session events and bounded CLI input history still work.
- Reopen, two same-root connections, distinct project roots, global/profile isolation, and ephemeral sessions return the right value. Invalid present JSON fails, rather than masquerading as missing state.
- Concurrent update-check changes preserve both fields; concurrent inquiry transitions cannot both accept an already-open turn; desktop project operations remain ordered, no-op writes do not change the row, and cross-process read/modify/write cannot lose a root.
- Inquiry listing preserves latest-write order with a deterministic tie-free revision. Event readers and cursors receive only real event commits; local and foreign current-row commits still wake subscribers through the existing level/data-version mechanism.
- Current-format mismatch clears the entire new schema atomically and reports the actual cleared state; no migration or dual writer is added. Applicable format, typecheck, lint, pure and full tests pass at the final head.

The owner accepted this bounded table and the current-format reset consequence on 2026-09-22. Implementation remains a separate change with the acceptance gates above. The source audit does not justify claiming a measured runtime win.
