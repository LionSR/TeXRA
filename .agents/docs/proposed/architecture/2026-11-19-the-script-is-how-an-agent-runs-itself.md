# 脚本是 agent 操作自己的那一层

基线：`main` 的 `7fa63aa`（2026-11-19）。路径相对仓库根。本文接着
[programs, not agents](./2026-11-06-programs-not-agents.md) 往下写：那份提案
回答"用户和模型能创造的单位是什么"（程序），这一份回答"一个在跑的 agent
能对自己做什么，由谁管住"。"今天"一栏逐条对过基线的源码；没对过的地方
写明了。

## 摘要

harness 分两层。下面一层只管模型自己管不了的事：能碰什么，花了多少，做
到哪了，谁判对错，什么时候被叫醒。上面一层是流程、指令和工具的用法，交
给模型写。**两层之间的接口就是脚本**：内核管着的每一样东西，在脚本里是
一个能调的函数；每一条限制由内核执行并落在 run history 里，不靠提示词。

负责人 2026-11-19 给了三条方向，本文把它们当成每一项新能力的检查：

- **通用。** 名字、说明和例子不假设 TeXRA、LaTeX、论文或代码；对任何嵌
  入 `@texra-ai/harness` 的应用读得通。
- **code mode 原生。** 能力是一个导出的函数或模块，脚本能拿去按别的方
  式拼；不埋进某个内置循环里。
- **给 agent 更多自由。** 说明只写结果和不变量，不写步骤；用什么工具、
  做几份、查多深由它定。
- **不替工作写死数据结构。** 断言的表、尝试的档案、程序库的格式、计划
  的形状，都是 agent 自己写的文件，它想怎么组织就怎么组织；随包的只能
  是一段它可以改写或不用的脚本模块。存储里的行只为内核自己的担保存在：
  做过什么改不了，上限越不过，断了能接着跑。判断一样东西该不该进系统，
  问的是"agent 能不能替自己担保这件事"，不是"它做不做得好"。

自由越多，三样东西越不能交出去：授权（凭据、花钱的上限、不可逆的外部动
作），验收条件（什么叫做完），审计记录（它对自己做的每个操作都是一行，
自己删不掉）。

## 今天脚本能对自己做什么

| 自己的什么 | 今天                                                                                                                                                                                                                                                                                                           | 缺的                                                                              |
| ---------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| 子运行     | `agent()`、`program()`、`self()` 三个函数。前两个共用一份调用字段（`CALL_FIELDS`，`packages/harness/src/agent/runtime/delegation/inputFields.ts`）并各自收 `model`（可带 `@effort`）；`self()` 有自己的一份输入，只有 `prompt`、`fork`、`schema`、`label`（`packages/harness/src/tools/codemode/SelfTool.ts`） | `self()` 不能换模型、不能限时、不能指定工作目录                                   |
| 花费       | 每个子运行的结果带 `cost` 和 `spent`（`childResult`，`packages/harness/src/agent/runtime/delegation/AgentTool.ts`）。上限只有 goal 的 `maxCostUsd`，由策略脚本在两轮之间自己查（`packages/harness/src/tools/plan/goalScript.ts`）                                                                              | 给一个子运行分一份预算、由内核停下它                                              |
| 上下文     | 三种压缩都由 harness 发起；`self({ fork: false })` 能不带对话重开                                                                                                                                                                                                                                              | agent 自己看当前视图、自己替换一段                                                |
| 做完没有   | goal 的每一轮自己报 `done`（`goalScript.ts`）                                                                                                                                                                                                                                                                  | 干活的一方之外的判定                                                              |
| 流程       | `program` 只按登记的名字启动（`packages/harness/src/agent/runtime/delegation/ProgramTool.ts`）。模型现写的代码有两条路：当场的 `script`，和送后台的 `script`（`packages/harness/src/tools/codemode/backgroundScript.ts`：父的工具，结果作为一条后续消息回来）                                                  | 现写的代码作为一个自己的 run 被 `await`、只带它声明的工具；做对过的流程留下来     |
| 时间       | 沙箱没有定时器、`Date.now()` 和 `Math.random()`，这是重放要的（`packages/harness/src/tools/codemode/ScriptTool.ts` 的 `SURFACE`）。能等的只有自己的子运行（`executions wait`）。唯一的事件来源是 app 里的 GitHub 订阅（`packages/texra/src/tools/github/`）                                                    | 到点或遇到事件时被叫醒                                                            |
| 历史       | `executions query` 对 run history 跑只读 SQL（`packages/harness/src/tools/executions/queryAction.ts`）                                                                                                                                                                                                         | 够用；自己上下文的占用随"上下文"那一行给                                          |
| 多份尝试   | `agent()` 和 `program()` 收 `working_directory`，受 worktree 开关管（`rejectUnusableWorkingDirectory`，`inputFields.ts`）                                                                                                                                                                                      | `self()` 不收，所以"同一个我在各自的工作副本里做八份"写不出来；没有"采纳其中一份" |

11 月 19 日另一个会话里的那张"七处缺口"表有一格和代码不符：它说 agent 不
能给子运行选模型。`agent()` 和 `program()` 一直能，不能的只有 `self()`。

没对过的：三种压缩的触发条件（另一个会话读过，这里照它的说法）；
"采纳其中一份"今天有没有现成的工具。

## 设计

### 1. 一份启动限制，三个函数共用

programs 提案把三个函数写成一个 `start` 的三个糖。今天它们的限制是分开长
出来的：`timeoutMs` 在 `CALL_FIELDS` 里，`model` 在 `agent` 和 `program`
各写一遍，`self` 哪个都没有。上表前两行和最后一行的缺口是同一个原因。

- `self()` 收 `model`，解析规则就是 `agent()` 的那一条
  （`selectAvailableDelegationModel`），不另立一条。这样"同一个 persona、
  同样的工具、换一个模型来判"是 `self(prompt, { fork: false, model })`
  一行。
- 每个子运行可以带 `maxCostUsd`。它和 `timeoutMs` 是同一种东西：属于等它
  的那次调用，子运行这棵树的花费到了就停，脚本的 `await` 以
  `BudgetExceeded` 拒绝。它比限时好恢复：花了多少在库里，恢复时不用重新
  计时。
- 上限只能往下分。子运行给自己的子运行写多大的数都越不过父的，因为父的
  上限盯的是整棵树。提高上限不是脚本能调的函数。
- 之后 `self()` 也收 `working_directory`，多份尝试各在自己的工作副本里
  做。这一步等 worktree 开关的归属定了再做。

状态：`model` 和 `maxCostUsd` 已在分支
`claude/codemode-harness-roadmap-0gcb88` 上实现，未合并。实际做法：

- 三个函数的 `model`、`label`、`timeoutMs`、`maxCostUsd` 出自一处
  （`CHILD_FIELDS`，`inputFields.ts`）。
- 上限由等子运行的那次调用执行（`withinLimits`，
  `packages/harness/src/agent/runtime/delegation/agentChild.ts`）：它跟着
  session 视图里这棵树的花费走，到了就用已有的 `released` 停掉子运行和它
  下面的 run。没有加定时器、存储字段、行版本或设置。
- 没选的做法是让子运行自己知道上限、在每次计费请求前查。那样能早停一次
  请求，代价是 `run.config` 上多一个存下来的字段、沿父链找祖先的上限、
  以及改 run loop。
- 所以上限是在每次有价的回复之后读的，花费会超出当时在途的那几次回复。
  工具说明里写了这一点。
- 一处行为变了：不被等的子运行（直接调用，或 `background: true`）以前收
  下 `timeoutMs` 但从不执行，现在带 `timeoutMs` 或 `maxCostUsd` 会被拒绝
  并说明原因。
- fork 出来的 `self()` 换模型时沿用种子的绑定，和宿主切换一个对话的模型
  走同一条规则；对话格式不同的模型在绑定时被拒，要用 `fork: false`。这
  条路径只读过代码，没有跑过。

### 2. 上下文和判定

两样都在另一个会话的分支上做，这里只记它们和本文的关系。

- **上下文**：一个内置工具，`view` 把当前模型视图作为数据返回，`replace`
  把一段换成 agent 自己写的文字。存的仍是已有的 `context.edit` 行，原文留
  在库里，人看到的转录不变。
- **判定**：判定方从 goal 的模块里单独导出，默认策略是 `self()` 轮次加它
  的一个组合；别的脚本可以导入它，判一件不是 goal 的工作。它的不变量四
  条：活不是你干的；要求从目标本身推；每条断言带一个别人能重跑的检查；
  查不了的记 `unverified`。

第 1 节给判定方补上的一点：判的一方要和干活的一方不同，换上下文不够，要
换模型，这需要 `self()` 收 `model`。

### 3. 模型现写的程序：能等，能留下

programs 提案第 1 期剩下的一项，等 #15091（安装式插件带程序）合并后做，
因为两者改同一批文件。

- `program({ code, uses })`：`uses` 是它能调的工具，用 #15091 定下的同一个
  词。它是一个自己的 run，脚本默认等它结束。
- 存法不必新增。送后台的脚本今天存的就是 `{ code, title, tools }`
  （`AgentConfig.script` 的 `background` 成员）；被等的内联程序是同一份记
  录，差别只在结果是直接回给等它的调用，还是作为后续消息投递。动手前要先
  读 `backgroundScriptOf`（`packages/harness/src/shared/schemas/runRecords.ts`）
  的每个读者，确认"后台"这个词在每一处问的是"怎么投递"还是"谁写的"。
- 它不受信：代码是模型写的，它启动的 `agent()` 照模型的脚本那样问人，不
  像登记的程序那样随插件批准。
- **留下**不加内核机制。#15091 之后，一个流程留下来就是本地插件文件夹里
  的一个 `programs/<name>.js`，agent 用普通的文件工具写；摘要变了，人审
  阅一次。"检查通过才留下"的那道检查是第 5 节的评测，不是一个新开关。

### 4. 触发：登记，不是定时器

沙箱里不加定时器。给脚本一个登记动作，到点或遇到事件时由 harness 之外的
时钟来启动一个程序。两种做法：

|            | 登记是 harness 的行，宿主只给时钟和事件（选这个）                        | 触发整个放在 app 里（今天 GitHub 订阅的做法） |
| ---------- | ------------------------------------------------------------------------ | --------------------------------------------- |
| 通用       | 任何嵌入方得到同一个登记动作，自己接时钟                                 | 只有 TeXRA 有；别的嵌入方重写一遍             |
| 记录在哪   | run history：谁登记的、哪次批准的、每次触发启动了哪个 run，都能用 SQL 查 | app 自己的状态，和 run history 两处           |
| 进程重启后 | 到期的登记从行里读出来，补一次                                           | 取决于 app 的那份状态                         |
| 代价       | 新增一种行，要在存储冻结之前定下来                                       | 不动存储                                      |

- 登记的内容：什么时候（定点、间隔，或一个宿主声明过名字的事件），启动
  哪个程序，带什么 `args`，每次触发的花费上限。触发时事件放进
  `args.event`，启动走已有的那条路（`script.kind: 'program'`，
  `packages/harness/src/agent/runtime/programRun.ts`）。
- 登记要人批准一次，因为之后花钱时没人在看；每次触发的上限是必填的，用
  的是第 1 节的 `maxCostUsd`。
- 一个事件启动一次短的 run，不是一个常驻的循环。状态在文件和 run history
  里。这是 programs 提案"触发就是带着事件启动一个程序"一节已经定下的。
- 宿主侧要写的只有一块：到点或收到事件时调一次"触发到期的登记"。TeXRA
  里它的位置是后台服务（`packages/texra/src/controllers/server/`）。

没开工，等"负责人问题"1 和 2。

### 5. 循环：开放的工作没有分数，选择靠三样

上一版把这一节写成"对一组 case 打分，分数涨了就留下"。负责人 2026-11-19
指出这站不住：研究是开放的，没有一组固定的题，也不知道"评测"该是什么。
固定的题库还有第二个毛病：它会被做满、被钻空子，之后分数不再说明任何
事。

所以不设一个要去优化的分数。一段流程、一个程序或 harness 的一处改动留不
留下，由三样东西决定，各有各的主人：

- **不变量，由内核和 gate 判。** 什么绝不能坏：重放一致、限制没被越过、
  记录没丢。它只能说一处改动没有弄坏东西，说不了它更好。
- **过滤，由验证器逐条判。** 开放的目标没法判，目标里的每一条断言可以：
  有没有一个别人能重跑的检查，重跑的结果对不对得上。这是第 2 节的判定
  方。它是筛子，不是目标：把"通过的断言数"当分数去追，得到的是一堆正确
  而无用的断言。
- **选择，由使用和人来做。** 什么值得做没有正确答案可学。能记下来的是
  事后的信号：人采纳了哪些结果、退回了哪些，一个留下的程序后来有没有再
  被启动，一条标成已验证的断言后来有没有被推翻。这些信号怎么记、记成什么样由 agent 定；
  系统只保证它查得到自己做过什么（run history 已经是这样）。

对做法的后果：

- 留下的东西是一个档案，不是一个冠军。几种通过了过滤的做法并存，没人
  再用的自然退场；不做"只留分数最高的那个"。
- 带对照的比较（带某个内置程序跑、不带跑）仍然有用，但它只回答一个窄
  问题：这个程序在一件有标准答案的事上有没有增益。它是删除的依据，不
  是自我改进的方向。
- 被推翻的"已验证"是这套东西里唯一明确的负信号，要能查到：哪条断言、
  哪个检查、哪次运行。

没解决的：选择信号很稀，来自人的那部分尤其稀；怎么让人给得省事、给了
之后怎么用，这里没有设计。

## 顺序

1. 启动限制（第 1 节）。在分支上，等合并。
2. 判定和上下文（第 2 节）。另一个会话在做。
3. 模型现写的程序能被等（第 3 节）。等 #15091。
4. 触发（第 4 节）。新增一种行，所以要排在行版本归零和冻结之前。
5. 没有完成条件的工作（第 5 节）：到点自己醒，加一份按周期补的预算；别的由 agent 自己写。排在触发之后。
6. `self()` 收 `working_directory` 和"采纳一份"。

## 负责人问题

1. **触发进不进 1.0。** 进的话，登记这一种行要在冻结前落地；不进的话，冻
   结后加它是加一种新的行，按规则不算破坏性变更，但要晚到 1.0 之后。
2. **触发能启动什么。** 只能启动登记过的程序（插件带的，审阅过），还是也
   能启动模型现写的代码（要把代码存进登记里，批准时给人看）。推荐先只做
   前一种。
3. **委派能不能点名一个列表里隐藏的模型**（triage 里留着的那一问）。
   `self()` 的 `model` 现在跟 `agent()` 走同一条规则，这一问怎么答，两个一
   起变。

## 不做的事

- 沙箱里的定时器、`Date.now()` 和随机数。
- 让脚本读自己的收件箱（`receive()`）。programs 提案已经说了为什么。
- 提高自己花费上限、改验收条件或删历史的任何函数。
- 为某一个学科或某一种文件写的自我操作。
