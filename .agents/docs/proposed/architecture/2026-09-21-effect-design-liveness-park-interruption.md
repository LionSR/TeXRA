# One fiber per run: the entry's identity is the fiber, WAITING suspends in place, and a stop is fiber interruption landing on a crash boundary

Winners per judge: Crash boundaries and resume (proposal 3): one scoped RunRoster entry whose identity is the run's fiber; admission is the fork; stop is fiber.interruptUnsafe() by run id; every run — root or child — suspends in place at followUps.wait (toolUse.ts:779), and a native child's turn boundary reaches its loop on an unbounded Queue raced against Fiber.await(runFiber). Total 17/20., Crash boundaries and resume

## Decision

Take proposal 3 (crash boundaries and resume) as the design, with four grafts and four fixes. A run's in-process liveness becomes one value: the fiber running its program, held on the run's one `RunRoster` entry, registered synchronously with the fork that admits the run and erased by that fiber's own exit — so admission, stop, deletion and follow-up routing read one thing that cannot outlive the process and cannot predate it. A run that reaches WAITING suspends in place on that fiber at `followUps.wait` (`/Users/siruilu/Local/AI-Projects/coauthor/src/agent/runtime/loop/toolUse.ts:779`), which is already exactly what a root does; a native child gets there too because its turn boundary stops being a returned `{ state, waiting: true }` (`toolUse.ts:752`, `:855`) and becomes an offer on an unbounded `Queue` the child loop supplied, which the loop takes raced against `Fiber.await(runFiber)` so neither side can block on a value the other can no longer produce. A stop is then `entry.fiber.interruptUnsafe()` by run id — synchronously callable from every host surface, exactly as the roster already stops parked fibers at `runRoster.ts:481` and `runRegistry.ts:250` — and it unwinds to the last committed row batch, which is where `SIGKILL` also leaves the run, so `resumeToolUseFromResumeData` is literally the same function reading the same rows with no second path. That deletes the park (`RunRegistry.park`, `ParkedRun`, `makeParkedRuns`, and the 64-line duplicate terminal block at `AgentRunLifecycle.ts:555-625`), the `stopped` Deferred and all 16 `failIfLaunchStopped` sites, `runUntilStopped`, `RunHandle.interrupt`/`stopRequested`/`attachInterruptHandler`, `claimTerminalFinalize`, `bindAbortSignals`, the per-turn native relaunch (`resumeToolUseTurn`) and the second follow-up consumer. It keeps `ChildRunInterruptible`'s `AbortController` — ruled a permanent resident on 2026-09-18 — and gives that ruling a structural reason rather than an exception: the child loop and the child run become two fibers, so the loop's stop aborts the foreign turn's signal and interrupts the run's fiber while the loop's own fiber survives to deliver and finalize. No new durable row type, so `SESSION_EVENT_FORMAT` stays at 7 (`src/shared/schemas/sessionEvent.ts:588`) and no PR in this design bumps it.

## Design

## 0. The five tree facts the design turns on, each read

**(a) The Effect-native park already exists — for roots only.** `/Users/siruilu/Local/AI-Projects/coauthor/src/agent/runtime/loop/toolUse.ts:779` is `batch = yield* followUps.wait;`, an interruptible `Queue.take` on the run's own fiber inside its own scope. A child never reaches it: `isChild` (`toolUse.ts:140`, gated at `:742`) returns `{ state, waiting: true }` at `:752` and `:855`, commented "One child cycle per invocation: the child loop delivers this turn's facts and owns the next wait". So the whole run-level park apparatus exists for one shape: a child turn boundary carried as a return value.

**(b) The park is a second fiber and a second terminal owner for a run that already has one.** `RunRegistry.park` (`runRegistry.ts:206-223`) is `FiberMap.run(this.parked, runId)(Deferred.await(stopped).andThen(termination))` — it forks, which is why there is no deadlock today. Meanwhile `startChildRunLoop`'s fiber is still inside `runs.launchRun(runId, run)` (`childRunLoop.ts:1396`), holding the run's lane for the loop's whole life. `AgentRunLifecycle.ts:562-625` is a hand-written second copy of stage close + `finalizeRunTerminal` + `releaseRunLease` + `runOnRunEnd`, and the two are reconciled after the fact by a boolean, `RunHandle.claimTerminalFinalize()` (`RunHandle.ts:158-162`, sole caller `AgentRunLifecycle.ts:139`). A flag standing in for structure is the defect.

**(c) Fiber interruption is already the destination of every stop; the Deferred is three adapters in front of it.** `bindAbortSignals` → `handle.interrupt()` (`nativeSubagentStrategy.ts:179`) → the attached handler → `ctx.interrupt()` (`AgentRunLifecycle.ts:367-371`) → completes `ctx.stopped` (`AgentLaunchContext.ts:504-507`) → `runUntilStopped` wins its race (`executeAgent.ts:157-161`) → **Effect interrupts the losing arm.** `raceAllFirst` forks each arm with `uninterruptible = false` (`node_modules/effect/src/internal/effect.ts:1695`, `:5459-5462`), which is why the race works under `executeAgent`'s `Effect.uninterruptible`. `runUntilStopped`'s own docstring already says the loop reads `Effect.abortSignal` for the provider request (`packages/llm/src/turn.ts:1876` confirms), "so no run signal exists beside the stop."

**(d) The row-commit discipline the design needs is already implemented; eight coarse masks are what suppress interruption.** Every durable append inside a run program is individually masked: `ModelInvoker.ts:536, 596, 727, 1025, 1108, 1126, 1241`; `toolUseDispatch.ts:283`; `FollowUps.ts:186`; `reflection.ts:1125, 1316`; and `toolUse.ts`'s exit protocol hangs off `onExit` precisely because "an external interrupt unwinds straight past `Effect.exit`" (`toolUse.ts:878-887`). What blocks a stop is eight region masks — verified exactly: `executeAgent.ts:601, 715, 760`; `AgentLaunchContext.ts:631`; `childRunLoop.ts:1112, 1394, 1409`; `inBandSubagentRun.ts:362, 401`. `AgentLaunchContext.ts:629-631` states its own reason: "Let each acquisition settle before cleanup so a late Promise cannot create an unowned resource." That is `Effect.acquireRelease`'s contract, bought at region scope — and it is masking a real gap, not a hypothetical one: `acquireRunResidency` returns at `:415`, `createRunTrace` runs at `:416`, and the finalizer is only registered at `:433` with `attachRunTrace` at `:435` in between.

**(e) One `RunInput`, one lease, two consumers.** `FollowUps.ts:105` claims `manager.claimLive(runId, 'flow')`; `ToolUseFollowUpQueueManager.ts:722-724` — `private claim` returns `undefined` when `entry.owner` exists — so for a native child, whose loop already claimed `claimChildRun(runId)` at `childRunLoop.ts:986`, the flow's claim returns `undefined`. `attachInput` then takes the no-lease branch (`ToolUseFollowUpQueueManager.ts:341`: `if (lease ? owner !== lease : owner.kind === 'flow') return undefined;` — the owner's kind is `'child'`, so it proceeds) and returns the loop's existing `entry.input` at `:344`. Proposal 1's "two leases" is wrong; the defect is one queue with two alternating consumers, and it deletes when the child's flow owns its own wait.

## 1. The durable / process-local split, stated once

Durable: `run.start` with the parent edge, `run.activate`, `run.detach`, `flow.snapshot`, the `flow.step` rows including `waiting` (`sessionFold.ts:1811` moves the phase on it), `child.park` (`sessionFold.ts:1815`, written only for agent-CLI children — `childRunLoop.ts:1273` is guarded by `if (childRun)`), `followUp` / `followup.consumed`, `child.turn`, `run.end`, and the aggregate claim row.

Process-local: the roster entry, `ctx.stopped`, `ChildRunInterruptible`'s controller, follow-up leases, the trace residency.

The invariant: **no process-local value decides whether a run is resumable.** It decides only "is a fiber of mine running it right now", and a value that _is_ a fiber answers that by construction.

## 2. Target shape

### 2.1 The entry's identity is the fiber

`RunEntry` (`runRoster.ts:38-50`, as #12942 left it, plus the concurrent lane's `launches` counter) gains one field and loses two:

```ts
interface RunEntry {
  fiber?: Fiber.Fiber<unknown, unknown>; // the generation running this run here
  handle?: RunHandle;
  activation?: ChildRunActivation;
  lane?: PerKeyLane;
  launches: number;
}
```

`parked` and the `generations` Deferred set both go: `Fiber.await(entry.fiber)` is the generation's completion, and the hold's completion is its own fiber (2.2). `isLive(runId)` collapses from the four-way union the concurrent lane just consolidated (`runRoster.ts` on `int/liveness-interruption-residue-0921d`) to `entry.fiber !== undefined || entry.launches > 0 || entry.handle?.getToolUseFlow() !== undefined` — and after S4 the flow arm goes too, because a flow that is live is a fiber that is live.

**Why the roster and not a bare `FiberMap`.** `FiberMap` carries no payload, so the handle, activation, lane and stop gate would live in a second map keyed identically — the exact "two in-process authorities answer the same question" failure #12942 just ended. The roster reproduces `FiberMap`'s contract in the ten lines it already has (`fiber.addObserver` removal, the pattern already at `runRoster.ts:230-236`), and reproduces it _with_ the payload. What the roster must copy exactly, from `node_modules/effect/src/FiberMap.ts`: registration synchronous with the fork and before any finalizer can re-enter (`:464-467`); stop as interrupt-and-await in one call (`remove` is `Fiber.interruptAs`, `:1192`); drain as a loop over the map's head (`awaitEmpty`, `:1638`).

### 2.2 Admission is the fork, inside the lane claim

`RunRoster.launch` (`runRoster.ts:291-327`) keeps `withPerKeyLane` and its synchronous `refuseClaim` — the lane has a genuine remaining consumer, `withInactiveRunStep` / `holdInactiveRun`, where a launch must _queue_ behind a deletion rather than fail — and gains one step: inside the lane, fork the operation and write the fiber onto the entry in the same synchronous turn, then `Fiber.join` it.

```ts
const step = Effect.gen({ self: this }, function* () {
  this.waiting.delete(refusal);
  const fiber = yield* Effect.forkChild(operation); // no yield between
  this.setFiber(runId, fiber); // fork and register, one tick
  return yield* Fiber.join(fiber);
});
```

`holdInactiveRun` becomes the same construct with `Latch.await(latch)` as the body and the latch opened in the caller's scope finalizer (`node_modules/effect/src/Latch.ts`), and — grafted from proposal 1 — it acquires the run's DB claim with `Effect.acquireRelease` inside that fiber's scope. A deletion hold is then _a fiber that owns the run and does nothing_, which is why admission, stop and deletion answer from one place, and the second half of `fenceSupersededRun` (`workflowScriptAgentRunner.ts:358-379`) deletes with it.

**The pre-fiber window closes by construction, but only if the reads move.** Proposal 3 deletes the six `failIfLaunchStopped` sites at `runAgent.ts:179, 187, 190, 199, 226, 234` on the argument that the fork registers the run before its first await — while leaving `readRunEnd` / `exists` / `persistedParentRunId` (`runAgent.ts:181-207`) _outside_ `launchRun` at `:212`. A `kill` arriving during those reads would then reach nothing at all, strictly worse than today's latch. Graft proposal 1's fix and make it mandatory: move those three lineage reads inside the operation `launchRun` forks, so the fiber exists from the first instant the run is admitted. This is the design change that resolves the flaw; it is not a guard, and it must land in the same PR as the deletion.

### 2.3 A stop is fiber interruption, and it is the only stop

`RunStopper.terminate` (`runStopping.ts:289-332`) becomes: read `entry.fiber`, `fiber.interruptUnsafe()`, push `Fiber.await(fiber)` onto `settlements`. The `handle.interrupt()` call at `:313` and the whole parked branch at `:317-324` (`Deferred.doneUnsafe(parked.stopped, …)` + `Fiber.await(parked.fiber)` — interrupt-then-await, hand-rolled) collapse into that one call. `RunStop.accepted` stays synchronous: the entry has a fiber or it does not.

This answers the recorded objection head-on. The ruling table at `.agents/docs/proposed/simplification/2026-09-20-service-scope-ownership-ledger.md` refuses "`stopped` + `interrupt` replaced by fiber interruption" because "twelve synchronous host callers reach `interrupt()` … with no fiber handle, and `failIfLaunchStopped` races the `Deferred` at eleven sites before any fiber exists. The `Deferred` is what makes stop callable from a synchronous surface." New evidence on the tree: those callers reach the stop **by run id**, and the entry hands them a fiber synchronously; `Fiber.interruptUnsafe` is synchronously callable and the repo already stops fibers this way from a map at `runRoster.ts:481` and `runRegistry.ts:250`. The site count is also wrong — there are 16 `failIfLaunchStopped` sites, not eleven (`AgentLaunchContext.ts:278, 308, 317, 349, 394, 406, 434, 439, 541, 602`; `runAgent.ts:179, 187, 190, 199, 226, 234`) — and every one of them is inside the region that becomes the fiber's body. Manual interrupt-polling inside a mask is not a substitute for interruption; it is the cost of not having it.

`finalizeRunTerminal`'s stop precedence (`AgentRunLifecycle.ts:144`, `handle.stopRequested`) becomes `Cause.hasInterrupts` on the cause reaching the finalizer — which `toolUse.ts:925` and `AgentRunLifecycle.ts:684-688` already read.

**What survives, deliberately.** `ChildRunInterruptible`'s `AbortController` (`childRunLoop.ts:364`) stays. `.agents/docs/implemented/architecture/2026-08-01-architecture-rulings-ledger.md:288-320` rules it a permanent resident — "the one signal every child-run turn runs under, handed straight to `execa`'s `cancelSignal`, the Codex SDK and the Claude Agent SDK. The loop's stop must not interrupt its fiber: the turn's settlement, parent delivery and finalization all run after it" — and names the D25 lane's conversion as the thing it rejects. Proposals 1 and 2 both delete it and both claim the ratchet row shrinks; neither cites the ruling. The design keeps it and makes the ruling structural: after S4 the loop fiber and the run fiber are two fibers, so `ChildRunInterruptible.interrupt()` aborts the controller _and_ calls `runs.interrupt(childRunId)`, and the loop's own fiber survives to deliver. `config/ratchets/effect-migration-baseline.json`'s row is unchanged at `src/agent/runtime/childRunLoop.ts: 1`, `src/tools/claudeAgent.ts: 1`. (The ledger's prose names four residents; two have since been removed and the row now holds two — a ledger re-measure, not a licence.) `interruptBackgroundProcess` also survives, narrowed: its contract is the opposite of a run stop — reach a leaked OS process _without_ ending agent runs (#8155) — so it becomes a plain `RunHandle.backgroundProcess?: { kill(): void }` slot, not an interrupt handler.

### 2.4 The WAITING run suspends in place, and the loop hears about it on a Queue

This is the question the other two proposals decline, and the answer is to stop routing the turn boundary through a return value.

At the point `toolUse.ts` already commits the waiting batch (`:822-832`: snapshot, `turn.end`, stream closure facts, `waiting` step, one `appendBatch`), after the existing `session.settlePublications(runId, { consume: false })` barrier at `:820`, the run offers the boundary on a queue the caller supplied, then falls through to the same `followUps.wait` at `:779` a root takes. One optional port on the run's policy, supplied only by `childRunLoop` for a native child:

```ts
readonly onTurnBoundary?: (b: TurnBoundary) => Effect.Effect<void>;
// TurnBoundary = { turnIndex, usage, outcome, terminal: boolean }
readonly turnPermit?: <A, E, R>(turn: Effect.Effect<A, E, R>) => Effect.Effect<A, E, R>;
```

Ordering is unchanged from today, where `childRunLoop` runs `deliverTurn` after `executeAgent` returned.

**The delete range is precise, and this is where proposal 1 hangs.** Only the two `return { state, waiting: true }` statements change — `toolUse.ts:752` and `:855`. The `stopAfterCycle` finishes immediately around them (`:749-751` and `:848-851`) stay exactly as they are, with their comments: "A one-cycle launch stops here rather than suspending: the headless in-band child has no orchestrator to resume it, so a WAITING park would leave the run hanging." Proposal 1's delete range `742-752` / `844-855` swallows them and hangs every `inBandSubagentRun` child. The in-band single-cycle child never reaches a turn boundary and needs no queue.

`childRunLoop`'s native arm becomes:

```ts
const turns = yield* Queue.unbounded<TurnBoundary>();
const runFiber = yield* Effect.forkChild(runs.launchRun(runId, runProgram(turns)));
for (;;) {
  const boundary = yield* Effect.raceFirst(
    Queue.take(turns),
    Fiber.await(runFiber).pipe(Effect.as(null)),
  );
  if (boundary === null) break;             // the run ended without a boundary
  const delivery = yield* deliverTurn({ …, turn: boundary, … });
  if (boundary.terminal) { pendingDelivery = delivery; break; }
  yield* submitPendingDelivery(delivery, …);  // interim turns wake inline, as today
}
yield* Fiber.await(runFiber);                 // the run's own run.end lands first (#8093)
yield* submitPendingDelivery(pendingDelivery, …);
```

The race against `Fiber.await(runFiber)` is the arm the earlier blocking-park attempt lacked: the loop never blocks on a boundary that can no longer come, and the run never blocks on the loop because the queue is unbounded. The #8093 ordering is preserved and simplified — the terminal delivery now waits on the fiber that writes `run.end`. The loop's `raceFirst` arm must map a failure exit of `runFiber` onto the same "failed turn" shape `attemptTurn` produces today (`childRunLoop.ts:417-446`), or error reporting regresses; that is the one piece of new logic the queue costs.

**Delivery stays on the loop fiber, in the parent's context.** Proposal 1's `settleTurn` callback runs the parent delivery on the _child's_ fiber, under the child's claim, writing to the parent's aggregate, and turns a delivery failure into the child run's failure. The queue costs one element more than a callback and buys exactly that separation back.

**The budget permit moves inside the turn.** `gateTurn` (`childRunLoop.ts:1105-1120`) is `budget.withPermit(Effect.uninterruptible(base(signal)))` raced against an abort arm — and the race arm exists _because_ of the mask inside the permit. Delete both: the permit becomes `run.policy.turnPermit` applied around `runTurn` inside `toolUse.ts`, so a WAITING child holds no concurrency slot. Proposal 1 puts the re-take before the park and therefore has, as written, the throughput bug its own risk list warns about.

**What deletes with this, all downstream of the same fact:** `runs.park`, `ParkedRun`, `makeParkedRuns`, `RunRegistryInit.parked`, `RunRegistry.isParked`, the roster's four park accessors, `sessionLayer.ts:342`'s `parkedRuns`; the duplicate terminal block at `AgentRunLifecycle.ts:555-625` and the `suspended` flag; `claimTerminalFinalize` and `terminalClaimed` — safely, because the second writer is gone first, and `childRunLoop.ts:1341`'s `childRun.finalize` is guarded by `if (childRun)` and so reaches only agent-CLI children, which have no run program of their own; `WaitingToolUseFlowResult` / `isWaitingFlowResult` and the `executeAgent.ts:587-590` invariant assertion; `resumeToolUseTurn` (`executeAgent.ts:723-760`), `AgentEngine.resumeToolUseTurn` (`nativeSubagentStrategy.ts:83-86`), the native strategy's `runTurn` / `isTerminal` and `toDeliveryResult`'s WAITING fold (`:160-166`); and the second follow-up consumer — `childRunLoop.ts:984-993`'s `claimChildRun` / `attachInput` / `queueLease` / `RunInput.make` for the _native_ path only (they stay for agent-CLI children, which have no flow). Carry proposal 1's caveat: `childRunLoop.ts:980-983` documents why the loop claims before any startup read, so the flow's claim has to move to that same point, not merely inherit it.

The per-turn cost that disappears is the real reason generations exist: today every turn of a native child rebuilds `buildAgentLaunchContext` — a fresh trace residency, a fresh `Run:` stage, a fresh `UsageMonitor`, a fresh `RunHandle`, a fresh `run.activate` row (`AgentLaunchContext.ts:415-456, :473, :546`).

### 2.5 The claim rides the fiber's scope, and is never the liveness value

The entry's fork wraps `Effect.acquireRelease(acquireRunOwnership(runId), () => session.releaseRunLease(runId))`, so the DB claim's lifetime is exactly the fiber's. That collapses `acquireResumedRunOwnership` (`runAgent.ts:247`, `executeAgent.ts:733`) and the `releaseRunLease` sites (`executeAgent.ts:697, 711`; `childRunLoop.ts:871, 1377`; `AgentRunLifecycle.ts:607`; `runAgent.ts:333`) onto one pair. `releaseRunLease`'s internal ordering (`SessionHandle.ts:455-513`) is unchanged; it becomes the release finalizer.

**The claim must not become the liveness value** — refuting, with new evidence, step 2 of `.agents/docs/proposed/architecture/2026-09-20-single-owner-liveness-and-one-fold.md` where it says "The claim alone decides liveness". `Database.acquireClaims` is idempotent for the current owner: `proveReclaimable` skips rows whose `ownerId === identity.ownerId` (`Database.ts:560-566`) and the return filters them out (`Database.ts:1053-1055`). Two in-process generations would both "hold" it, so it can refuse neither. It is also coupled to a publication drain, and a predicate that drains is not a predicate. The claim answers "may this process append to this aggregate"; the fiber answers "is a program of mine running this run". Two facts, two owners. Everything else in that step — one entry per run, one map, metadata cannot outlive or predate liveness — is adopted, with the fiber as the entry's identity.

### 2.6 Where interruption may and may not land

The rule, stated once: **inside a run program, every `ledger.appendBatch` and `session.commit` is `Effect.uninterruptible`; nothing else is.** §0d shows most of it is already true. The work is deleting the eight region masks and replacing each with the narrow guarantee it stood in for:

| Mask                               | Replaced by                                                                                                                                                                            |
| ---------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `executeAgent.ts:601`              | the existing `Effect.scoped`; its finalizers already run on interruption                                                                                                               |
| `executeAgent.ts:715`, `:760`      | `Effect.acquireRelease` on the resumed claim (the rollback at `:733-753` and the release at `:695-712` become its release arm)                                                         |
| `AgentLaunchContext.ts:631`        | `Effect.acquireRelease` for the residency (`:415`+`:433`), the trace attach (`:435`) and the stage (`:473`+`:481`); `Effect.uninterruptible` on the `run.activate` commit (`:447-456`) |
| `childRunLoop.ts:1112`             | `budget.withPermit` with no mask, which also deletes the compensating race arm                                                                                                         |
| `childRunLoop.ts:1394`, `:1409`    | `Effect.onExit(exit => Effect.uninterruptible(terminal))` — the `toolUse.ts:878-887` pattern, for the reason it gives                                                                  |
| `inBandSubagentRun.ts:362`, `:401` | `Effect.acquireRelease` on `registerChildRun` (`:175-190`); `Fiber.join(completion)` and the durable read-back stay interruptible                                                      |

**The ordering is a hard rule, grafted from proposal 2:** convert the acquisitions to `acquireRelease` _before_ dropping the mask above them, and drop `runUntilStopped`, `ctx.stopped` and all 16 `failIfLaunchStopped` sites _in the same commit_ as each other. Removing a mask while the Deferred race survives leaves the run with two stop paths and makes the race loser's interrupt indistinguishable from a host interrupt.

The result is the property that makes this the right shape: **a stop and a crash land in the same place.** An interruption unwinds to the last committed row batch; a `SIGKILL` leaves the last committed row batch. Resume re-enters from the rows in both cases, and no second path — no park fiber's `termination`, no fabricated CANCELLED shell — is exercised by only one of them.

## Primitives

- Entry identity: `fiber?: Fiber.Fiber<unknown, unknown>` on `RunEntry` (src/agent/runtime/runRoster.ts:38-50), written in the same synchronous turn as the fork and removed by `fiber.addObserver` — the pattern already at runRoster.ts:230-236. It reproduces `FiberMap`'s contract (node_modules/effect/src/FiberMap.ts:464-467 registration-before-reentry) while carrying the handle, activation and lane the map cannot.
- Admission: `Effect.forkChild(operation)` + `setFiber(runId, fiber)` with no yield between, inside `withPerKeyLane`'s existing synchronous `refuseClaim` (runRoster.ts:291-327), then `Fiber.join(fiber)`. The lane stays because `withInactiveRunStep`/`holdInactiveRun` genuinely queue; everything else refuses.
- Stop: `entry.fiber.interruptUnsafe()` by run id, settled with `Fiber.await(fiber)` — modelled on `FiberMap.remove`, which is `Fiber.interruptAs` (node_modules/effect/src/FiberMap.ts:1192), i.e. today's `Deferred.doneUnsafe(parked.stopped)` + `Fiber.await(parked.fiber)` (runStopping.ts:321-322) with the latch removed. Synchronously callable, as runRoster.ts:481 and runRegistry.ts:250 already prove.
- Drain: a loop over the entry map's head awaiting each fiber, the shape of `FiberMap.awaitEmpty` (node_modules/effect/src/FiberMap.ts:1638), replacing `awaitDrained`'s raceAllFirst listener/re-check loop (runRoster.ts:391-404) whose re-check arm exists only because the listener registry can miss a change.
- WAITING park: `followUps.wait` = `Effect.map(input.take, taken)` (FollowUps.ts:224) on the run's own fiber at toolUse.ts:779 — unchanged from the root path. No new primitive; the child simply stops being denied it.
- Turn boundary: `Queue.unbounded<TurnBoundary>()` + `Queue.offer` at the waiting batch (toolUse.ts:822-832, after the settle barrier at :820) / `Queue.take` in the child loop — producer/consumer inversion in place of a returned `{ waiting: true }`.
- Deadlock-free handshake: `Effect.raceFirst(Queue.take(turns), Fiber.await(runFiber).pipe(Effect.as(null)))` — the loop never blocks on a boundary that can no longer come; the queue is unbounded so the run never blocks on the loop.
- Atomic acquisition: `Effect.acquireRelease` replacing acquire-then-`addFinalizer` at AgentLaunchContext.ts:415/:433 and :473/:481, and on `registerChildRun` (inBandSubagentRun.ts:175-190) and the resumed claim (executeAgent.ts:695-753).
