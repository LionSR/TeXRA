# DeepSeek Harness: source evidence for the TeXRA architecture review

Reviewed revision: `f3803c96974ad4a94195fb97e5c637e9c2a3afe3` of `deepseek-ai/deepseek-harness`. This note separates verified mechanisms from recommendations for TeXRA. The minimal SDK profile and the richer subagent/approval composition are different deployments.

## Findings

**1. One active loop owner is a useful principle; its Promise machinery is not something TeXRA should copy.** `AgentMachine` has the exclusive phases `idle`, `maintenance`, and `running`. It reserves the running phase synchronously, before starting asynchronous work. Messages arriving during maintenance or after cancellation set a pending wake; `whenIdle()` rechecks the activity identity so a replacement driver cannot escape its wait. Disposal cancels, waits for the driver, disposes its scope, drains persistence, and only then releases registrations. This is a concrete ownership discipline, not merely a short loop file. TeXRA can express the same guarantees through its existing Effect scope and single loop, without adding another scheduler. Sources: [agent.ts:53–61, 170–258][loop], [index.ts:492–544][dispose].

**2. Input acceptance, input removal, and an answer are different facts.** Follow-up input targets the next turn; steering targets the next step; injection does not wake an idle agent. Inbox removals caused by cancellation explicitly persist `outcome: 'canceled'`, whereas claims omit that outcome. This avoids claiming that discarded input was consumed. Duplicate message IDs are rejected across the currently pending queues; this is not historical retry idempotency. The SDK subscribes before submitting, waits for the inserted message bearing its returned ID, then observes until root-session idle and returns the last assistant text in that interval. Thus the comparison correctly rejects a per-message answer guarantee, but should acknowledge the acceptance anchor. Separately, server `session/wait` waits for descendants and checks that the root remained idle at the same event sequence. Sources: [inbox.ts:108–112, 205–228][inbox], [client/api.ts:203–257][run], [server.ts:304–320][wait].

**3. Tool arguments become immutable before permission.** The pipeline snapshots and freezes JSON arguments. Its pre-execution decisions are only allow, deny, cancel, or ask: argument rewriting is explicitly excluded because the call is already logged and displayed. After extensible policy and any approval, deny-only guards run; an earlier approval cannot override their rejection. Cancellation is checked again before dispatch. The body is awaited even after cancellation, preserving a meaningful “finished using the resource” boundary. For TeXRA, the useful design is one final operation: normalize or rewrite first, validate it, decide permission for that exact operation, record it, and execute it. A general hook system is unnecessary. Sources: [pipeline.ts:116–229][pipeline], [contracts.ts:348–391][tool-contract], [pipeline.ts:258–285][body].

**4. The measured minimal profile already checkpoints before external effects.** `sdk-minimal/cordis.patch.yml` mounts both JSONL persistence and `session-checkpoint-policy`. The policy awaits `sessions.flush` before constructing the downstream model stream and before a top-level tool body; rejection prevents dispatch, and cancellation during the flush prevents the tool body. Nested tools reuse the outer call's durable record. The comparison already depicts these checkpoints; its 200 ms batching figure must not be read as the only durability guarantee. TeXRA should keep this ordering directly in the owning execution path, rather than make correctness depend on optional policy composition. Sources: [sdk-minimal:172–179][profile], [checkpoint-policy/index.ts:29–81][checkpoint].

**5. Approval history is not a durable suspended computation.** In the richer composition, the approval service appends `approval/asked`, awaits an in-memory answer, and appends `approval/decided`. Its rebuildable state contains policy and whether a turn is open, not a pending continuation. Recovery produces `TOOL_OUTCOME_UNKNOWN` when a tool-call record survives without a result, and `TOOL_NOT_STARTED` when only the assistant's request survives. Therefore the comparison's “crash during approval means unknown” needs the qualification that the call record survived. This conservative outcome does not mean the body ran. There is no automatic replay of the tool's side effect. `sdk-minimal` does not mount the approval service; an ask without that service is denied. TeXRA should retain its durable request/decision mechanism rather than imitate this weaker restart contract. Sources: [approval/index.ts:83–109, 242–260, 293–330][approval], [repair.ts:14–39, 116–192][repair], [pipeline.ts:432–469][ask].

**6. Durable child history does not establish durable parent delivery.** Natural child completion waits for idle, flushes, then rechecks activity, event sequence, pending input, and descendants before closing. These rechecks are substantial and tested. After cleanup, however, notification is a separate operation against the exact live parent object. Failure is warned; an absent or replaced parent receives nothing. Cold resume reconstructs a child when a new message is delivered; the inspected path does not reconstruct an undelivered completion notice. This establishes a crash interval between child persistence and parent enqueue, not a demonstrated defect against a promised exactly-once contract. For TeXRA, commit the child's terminal record and the parent's input in one SQLite transaction when they share a database. If they do not, use a durable pending-delivery record and a stable deduplication key; do not add both mechanisms. Sources: [manager.ts:1042–1109][finish], [manager.ts:1194–1245][delivery], [manager.ts:1345–1403][cold].

**7. String service names are not untyped service contracts.** Cordis `Context` is extended through TypeScript declaration merging (`tools: ToolsService`, `approval: ApprovalService`); required services have explicit `inject` declarations, and optional services use `ctx.get`. The comparison's “dependencies hidden in strings” wording misses these checks. The stronger criticism is that source-level imports do not describe the effective deployment: YAML activation, optional services, scope inheritance, and hook order jointly determine behavior. TeXRA already has Effect layers; explicit typed construction of its required capabilities is preferable to importing another configurable plugin framework. Sources: [tools/index.ts:32–35][typed-tools], [agent-loop/index.ts:292][inject], [approval/index.ts:25–28,168][approval].

## Verified

The checkout's HEAD was verified against the full commit above. Source and existing test assertions were read; no peer source was edited. No tests were executed because this checkout has no `node_modules`; no dependencies were installed. In particular, reviewed assertions cover [durable cancellation][test-inbox], [flush before dispatch and cancellation during flush][test-checkpoint], [hard-crash tool recovery][test-crash], [shutdown persistence under both mounting orders][test-shutdown], and [new child work arriving during final flush][test-child].
