# pi-durable source review for the TeXRA architecture

The useful lesson is precise ownership of decisions and durable correspondence between inputs and results. A small `startRun` function is a consequence of those choices, not evidence that the underlying execution machinery is small.

This review uses `earendil-works/pi` at `c3d8ce44d3231c7e46071d2d859f41ca7d39d21b`. The comparison page labels this “pi-durable 1.4.0”, but the checkout contains substantial **unreleased** changes. In particular, commit adoption, deferred progress persistence, and the removal of `watchEvents` are above the 1.4.0 release heading. [CHANGELOG.md:3–21,135](https://github.com/earendil-works/pi/blob/c3d8ce44d3231c7e46071d2d859f41ca7d39d21b/packages/durable/CHANGELOG.md#L3-L21).

## Ownership is an invariant, not a launch category

Task ownership has two cases: conversation-owned or task-owned. Conversation ownership is independently ownerless or task-owned. Background execution and abandonment after restart are separate properties. History ancestry is also separate from ownership. Thus root/child, fresh/resumed, waiting, and execution ownership are not alternatives in one union. [types.ts:383–427](https://github.com/earendil-works/pi/blob/c3d8ce44d3231c7e46071d2d859f41ca7d39d21b/packages/durable/src/types.ts#L383-L427).

The scheduler is the sole authority for task lifecycle decisions. Reservation, abort marking, runtime commits, and finalization run on the serialized Session mutation path; handlers and joins run outside it. A finished handler does not imply a finished parent: its outcome remains `completing` until ordinary owned work ends, including children created in that same transaction. Wait dependencies are checked for cycles. [scheduler.ts:236](https://github.com/earendil-works/pi/blob/c3d8ce44d3231c7e46071d2d859f41ca7d39d21b/packages/durable/src/harness/scheduler.ts#L236), [scheduler.ts:1909–1953](https://github.com/earendil-works/pi/blob/c3d8ce44d3231c7e46071d2d859f41ca7d39d21b/packages/durable/src/harness/scheduler.ts#L1909-L1953).

An invocation becomes unusable when it ends: its watches stop, timers stop, and signal aborts. Every queued runtime write rechecks invocation validity on the serialized path, preventing a completed or cancelled invocation from writing later. Merely passing an abort signal would not establish this property. [scheduler.ts:2032–2043](https://github.com/earendil-works/pi/blob/c3d8ce44d3231c7e46071d2d859f41ca7d39d21b/packages/durable/src/harness/scheduler.ts#L2032-L2043), [scheduler.ts:2329–2352](https://github.com/earendil-works/pi/blob/c3d8ce44d3231c7e46071d2d859f41ca7d39d21b/packages/durable/src/harness/scheduler.ts#L2329-L2352).

**Borrow:** one owner of activation validity and terminal decisions, with writes checked against that ownership. **Do not borrow:** the entire generic task framework. Its 2,528-line scheduler handles task definitions, checkpoints, sleeps, dependency graphs, definition replacement, restart limits, and ownership reconciliation. TeXRA already has Effect and a history-driven run loop; another task engine would duplicate those mechanisms. The comparison explicitly assigns this scheduler to its storage bucket, so the advertised loop-size ratio does not measure equivalent lifecycle responsibilities.

## Cancellation, closure, and restart have different meanings

Cancelling a wait removes that observer only. Aborting work first writes a durable abort mark, then waits for its invocation; cancelling that latter wait leaves the mark intact. A submission can be withdrawn only while queued: after placement, `abort()` returns `already_placed`. [util.ts:9–25](https://github.com/earendil-works/pi/blob/c3d8ce44d3231c7e46071d2d859f41ca7d39d21b/packages/durable/src/harness/util.ts#L9-L25), [scheduler.ts:531–557](https://github.com/earendil-works/pi/blob/c3d8ce44d3231c7e46071d2d859f41ca7d39d21b/packages/durable/src/harness/scheduler.ts#L531-L557), [submissions.ts:123–136](https://github.com/earendil-works/pi/blob/c3d8ce44d3231c7e46071d2d859f41ca7d39d21b/packages/durable/src/harness/submissions.ts#L123-L136).

Startup changes surviving `running` records to `pending`, incrementing restart counts, then reconciles cancellation inherited from owners. Clean shutdown signals and joins invocations before returning their durable records to `pending`; it does not count as a crash. Scheduling is explicitly enabled by `resume`, submit, or wait. Read-only opening does not recover tasks. [scheduler.ts:377–427](https://github.com/earendil-works/pi/blob/c3d8ce44d3231c7e46071d2d859f41ca7d39d21b/packages/durable/src/harness/scheduler.ts#L377-L427), [scheduler.ts:501–521](https://github.com/earendil-works/pi/blob/c3d8ce44d3231c7e46071d2d859f41ca7d39d21b/packages/durable/src/harness/scheduler.ts#L501-L521).

**Borrow:** explicit contracts for stop-waiting, request-abort, close, and recover. Use Effect scopes and interruption to implement them; do not reproduce pi's Promise maps and AbortController bookkeeping. No conclusion about multiple simultaneous writable processes follows from these single-Session mechanisms.

## An input receipt must distinguish placement from an answer

Each submission has durable identity and states `queued`, `placed`, `done`, or `unanswered`. A placed input has its transcript entry; a completed input additionally has the final answer entry. Waiting checks the current record and registers the observer on one serialized path, avoiding a completion between those two operations. Observers wake only from durable submission changes. [types.ts:485–530](https://github.com/earendil-works/pi/blob/c3d8ce44d3231c7e46071d2d859f41ca7d39d21b/packages/durable/src/types.ts#L485-L530), [submissions.ts:109–145](https://github.com/earendil-works/pi/blob/c3d8ce44d3231c7e46071d2d859f41ca7d39d21b/packages/durable/src/harness/submissions.ts#L109-L145).

`requestId` deduplicates within a conversation before writing. It rejects reuse for another submission type, but intentionally accepts different content with the same key and type: the original wins. The test explicitly supplies different text. This is a documented identity policy, not content-based equivalence. [submissions.ts:207–214](https://github.com/earendil-works/pi/blob/c3d8ce44d3231c7e46071d2d859f41ca7d39d21b/packages/durable/src/harness/submissions.ts#L207-L214), [harness-submissions.test.ts:82](https://github.com/earendil-works/pi/blob/c3d8ce44d3231c7e46071d2d859f41ca7d39d21b/packages/durable/test/harness-submissions.test.ts#L82).

The run stores its participating submission IDs. Steers join that list; finishing assigns the same final answer to all those inputs, or an explicit failure reason. Consequently correspondence is **many inputs to one answer**, not one answer per input and not a proof that the model addressed every instruction. A dedicated test batches two follow-ups into one successor answer. [generation.ts:943–952](https://github.com/earendil-works/pi/blob/c3d8ce44d3231c7e46071d2d859f41ca7d39d21b/packages/durable/src/harness/generation.ts#L943-L952), [live.ts:268–283](https://github.com/earendil-works/pi/blob/c3d8ce44d3231c7e46071d2d859f41ca7d39d21b/packages/durable/src/harness/live.ts#L268-L283), [harness-inbox.test.ts:158–179](https://github.com/earendil-works/pi/blob/c3d8ce44d3231c7e46071d2d859f41ca7d39d21b/packages/durable/test/harness-inbox.test.ts#L158-L179).

**Borrow:** persistent input identity, explicit placement, and durable terminal result referencing the answer. A receipt meaning only “consumed” cannot support waiting for an answer. Avoid a second receipt store if these facts can be represented by TeXRA's existing authoritative rows and projections.

Recovery is not exactly-once external execution. Tools persist execution intent before calling the effect; recovery repeats only if both the saved and current policies say `safe`. Otherwise it reports that execution may have partially occurred. The subagent recovery test reuses a child by owner ID and supplies a stable request ID itself; this is caller-written idempotency, not automatic deduplication of arbitrary effects. [tool.ts:180–212](https://github.com/earendil-works/pi/blob/c3d8ce44d3231c7e46071d2d859f41ca7d39d21b/packages/durable/src/harness/tool.ts#L180-L212), [harness-ownership.test.ts:1257–1308](https://github.com/earendil-works/pi/blob/c3d8ce44d3231c7e46071d2d859f41ca7d39d21b/packages/durable/test/harness-ownership.test.ts#L1257-L1308).

## Persistence precedes publication

Storage commits atomically, then synchronously calls `adopt(seq)` before the next commit. SQLite calls it after its transaction returns. Adoption updates cached state and internal observers; external commit notifications are scheduled before waits are released. Once storage begins, caller cancellation cannot interrupt its completion. [types.ts:1307–1315](https://github.com/earendil-works/pi/blob/c3d8ce44d3231c7e46071d2d859f41ca7d39d21b/packages/durable/src/types.ts#L1307-L1315), [sqlite/storage.ts:187–211](https://github.com/earendil-works/pi/blob/c3d8ce44d3231c7e46071d2d859f41ca7d39d21b/packages/durable/src/storage/sqlite/storage.ts#L187-L211), [session.ts:890–938](https://github.com/earendil-works/pi/blob/c3d8ce44d3231c7e46071d2d859f41ca7d39d21b/packages/durable/src/session/session.ts#L890-L938).

A failure before adoption discards staged changes. A failure after durable adoption keeps the committed state visible and fails the Session; it never pretends to roll back durable history. Deferred streaming progress is explicitly weaker: memory may lead persistence, with a default one-second loss window. It must not carry authoritative lifecycle decisions.

**Borrow:** this ordering invariant and distinction between durable facts and disposable progress. With SQLite as TeXRA's sole authoritative store, the invariant need not introduce a general multi-backend storage protocol.

## Verified

Verified checkout HEAD, clean worktree, source implementations, and relevant existing test bodies. Particularly useful tests cover cancellation without cancelling shared work (`harness-ownership.test.ts:869`), restart with one child submission (`:1257`), batching (`harness-inbox.test.ts:158`), reopen (`harness-submissions.test.ts:178`), observer-before-wait ordering (`:279`), and failures before/after adoption (`session-adoption.test.ts:89–127,229–251`). Tests were **not executed**: this checkout has no root or durable-package `node_modules`; no dependencies were installed. These are source-supported conclusions, not a report of passing tests.
