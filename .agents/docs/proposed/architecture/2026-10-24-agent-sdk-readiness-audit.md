# Agent SDK readiness: current-state audit and progress delta

Baseline for comparison: the design note
[`2026-10-21-harness-general-package-design.md`](./2026-10-21-harness-general-package-design.md)
("The harness as a general package: surface first, two structural moves"),
whose audits read `main` at `08455c8`. This note re-measures the same surfaces
against the working tree at `a20cc39` (2026-10-24) and reports what has landed,
what remains, and the standing recommendation.

## Verdict

**The codebase is already well-aligned, and the plan for the rest already
exists.** There is no new diagnosis to make and no independent refactor to
propose: the 2026-10-21 design is the authoritative answer to "improve Agent
SDK readiness," and it was reached by a wider process (seven read-only audits
plus a scored four-design comparison) than a single audit pass can match. The
right next action is **not** another plan and **not** an autonomous refactor —
it is to execute that design's remaining lanes under owner review, because four
owner questions in it are still open and its largest lanes touch the repo's
two most-edited files.

What follows is therefore a progress check against that design, plus the few
cleanup opportunities that sit outside its lanes.

## Step 2 — Abstractions to remove (findings, cross-referenced)

The design's deletion ledger is the canonical list; nothing here contradicts it.
Re-verified as still-present today:

1. **~211 root exports that should not be public** (241 → ~30). Of the original
   246: 43 serve only TeXRA's hosts (`HostInteractions` with VS Code event
   names, presets, `WorkspaceAgentsController`, `decideRunModel`) and 37 are
   internal plumbing (`setLogSink`, `withForkFailureReporting`, path helpers).
   This is the single largest abstraction-leak and the first thing an embedder
   trips over.
2. **`export *` barrels in `shared/schemas/index.ts`** (47). Barrel re-exports
   are exactly the indirection the repo's own anti-shim/anti-barrel conventions
   forbid; they also make the deep-import baseline necessary.
3. **`defineBuiltinPlugin`** (`tools/plugins.ts`) — an unexported second plugin
   path giving built-ins `Runs | RunCall | ScriptCalls | IssuingScript` that app
   plugins cannot get. The design deletes it; engine tools stay in `tools/`,
   every other built-in becomes a plain `definePlugin` behind the fence.
4. **`Continuation` taking the internal `SessionHandle`** instead of a public
   `RunPark`. The one place the authoring contract reaches into harness internals.
5. **`toolUseHelpers.ts`** — replaced by `progress(text)` → transient
   `stream.chunk` (design lane 4b). Note: the 2026-10-21 lane-4 re-check already
   confirmed the card-producer path is one-writer-per-run, so this is a surface
   simplification, not a correctness fix.
6. **The deep-import baseline + its suite** — removable *as a consequence* of 1–4,
   not on its own. It is a symptom (1003 frozen internal specifiers), not a cause.

Deliberately **not** flagged as removable (the design's re-check already ruled
these load-bearing, and today's tree agrees): activate's cancels, the three
grant rules, the three `run.config` producers, the `followup.consumed` copies,
`admitSwitch`'s cross-protocol refusal. These look like duplication but each
carries a distinct fact; collapsing them would be a regression. Flagging them
would be the audit's mistake, so they are recorded here as checked-and-kept.

## Step 3 — Surface-area simplifications

- Adopt the **five named subpaths** the design specifies: `./schemas` (named
  manifest), `./plugins` (authoring closure), `./node`, `./host`
  (host-composition only, no stability promise), and `./promise` last. This is
  what turns 241 + 283 + 119 scattered names into a readable public contract.
- Add the thin **`Run` methods** (`text`, `followUp`, `stop`, `decide`,
  `transcript`) over the existing request unions — the edge today forces
  embedders to pair `stream.start`/`stream.chunk` ids and send
  `session.request({ kind: 'followUp.send' })` by hand.
- **Inject TeXRA vocabulary as data** rather than hardcode it: the `texra.`
  namespace (prefix at the store boundary so stored keys do not migrate),
  discipline teams/presets, icons, the LaTeX prompt section, the canned
  validation model (→ cli), and llm branding (→ bind facts).
- `./promise` is an owner decision, not a mechanical one — it argues against the
  2026-09-21 Effect-only ruling. Keep it last; it is one deletable file.

## Step 4 — Subagent / independent-unit boundaries

The harness already has first-class subagent machinery, so "designing subagent
boundaries" is largely **recognizing boundaries that exist** and making them the
package seams, not inventing new ones:

- **Delegation is already a tool family**: `packages/harness/src/tools/delegation/`
  (`AgentTool`, `subagentRun`, `inBandSubagentRun`, `detachedChildRun`,
  `childRun`, `proposalFlow`). A child launched from a parent's tool call runs
  in that call's fiber with its **own** input queue — the loop architecture
  already enforces that a subagent never reads the parent's follow-up queue from
  context. This is the natural agent/subagent boundary and it is sound.
- **`executeAgent` vs `session.runs.launch`** is the real seam: `launch` requires
  the composition root's `SessionOwner` (no tool can reach it), `executeAgent` is
  for when you already own the `runId` (subagent dispatch). Keep this split; it
  is the boundary between "the host starts a run" and "a run starts a child."
- **Child-run concurrency** already has a budget design
  (`2026-08-15-child-run-concurrency-budget.md`) and `childRunBudget.ts`. No new
  boundary needed.
- **The storage half of `session/`** (row schemas/codec, versions, folds,
  publisher, store) is the one genuinely *new* split the design proposes: keep it
  as a lint zone that imports nothing above it, so it can become
  `@texra-ai/history` by rename when a second embedder appears. That is the only
  "could run as an independent unit" boundary worth drawing now; the rest are
  runtime boundaries that already hold.

Conclusion for step 4: the agent/subagent decomposition is already correct. Do
not add agent framework layers; the open move is the history lint zone, and it
is already in lane 2b.

## Cleanup opportunities outside the lanes

The design's "Still open after this design" list names these; still true today
and not blocked on any lane, so they are safe incremental wins:

- ~350 lines of duplicated lowering across the llm adapters, plus OpenRouter's
  hand-rolled transport.
- `sessionViewUpdate.ts` at ~1,166 lines (a core-quality hotspot; find the data
  structure behind it, do not split mechanically).
- Four CLAUDE.md rules with no automated check: the barrel ban, the single-caller
  ban, renderer `Date.now()`, and silent degradation outside harness/llm. Adding
  a ratchet for the barrel ban would also protect the `export *` cleanup in lane 1
  from regressing.

## Recommendation

1. **Do not run the structural lanes autonomously.** Lanes 1 and 2b touch
   `runRegistry.ts` and `SessionEvents.ts` (the most-edited files) and the design
   explicitly sequences them after specific in-flight PRs; four owner questions
   remain open. These need a human in the loop.
2. **Answer the four owner questions** (Promise entry, `./host` placement,
   history-as-package timing, the `texra.` namespace boundary) — they gate lanes
   1, 3 and 8.
3. **Sequence**: Lane 1 first (largest surface win, lowest structural risk among
   the big lanes), then lane 3 (vocabulary as data), then 2b (session merge, the
   riskiest), then 4b (fence), then 5/7, then 6/9 at release.
4. The daily simplifier/debt grooming already in flight is the right background
   cadence; keep it.
